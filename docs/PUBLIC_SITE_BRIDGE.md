# Main Site ↔ VPS public bridge

The public Jekyll site and the Next.js dashboard remain separate deployments.
The VPS is the source of truth for recruitment, roster and guild raid data.

## Public endpoints

- `GET /api/site/guild` — sanitized roster, guild raid progression/rankings and published scheduled raids.
- `GET /api/site/applications` — sanitized recruitment status list. Discord, BattleTag and availability text are never returned.
- `POST /api/site/applications` — validated application intake from allowed public-site origins.

`POST` is protected by an origin allowlist, request-size checks, rate limits, a honeypot and server-side field validation. New applications are stored in the dashboard document store/PostgreSQL and a Discord message reference is persisted so moderation updates can edit the original Discord message.

## Source of truth

- Applications: `guildApplications` document collection backed by PostgreSQL in production.
- Guild roster/progression: server guild sync (`guildRoster.ts`), including Raider.IO guild progression and rankings.
- Scheduled raids: dashboard raid collection, only `published` raids are exported publicly.

Configure the allowed site origins with `PUBLIC_SITE_ORIGINS`.

## Automatic raid season detection

`GET /api/site/guild` also exposes `raid_seasons`, generated by the VPS rather than by Main Site templates.

- Battle.net Journal API identifies the newest expansion and its raid journal entries.
- Raider.IO `mythic-plus/static-data` identifies the active `is_main_season` from its regional `starts`/`ends` window.
- Raider.IO `raiding/static-data` supplies raid slugs, encounter counts and raid `starts`/`ends` windows.
- The resolver keeps the latest successful snapshot if either upstream API is temporarily unavailable.
- Main Site treats this server snapshot as the source of truth; `_data/raids.yml` is only an offline fallback.
