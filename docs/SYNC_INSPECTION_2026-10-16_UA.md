# Інспекція синхронізації, заявок і CurseForge

Дата: 16.10.2026, Київ. Парний реліз: Dashboard **3.9.1**, Site **4.1.1**.

Виправлення підготовлено й перевірено у вихідних кодах. VPS і конфігурація Cloudflare цим сеансом не змінювалися. На живих доменах виконувалися лише читання; тестові заявки та Discord-повідомлення туди не надсилалися.

## Підтверджена причина розриву зв’язку

Публічний сайт віддає сторінку, але його браузерні запити `/api/bridge/*` перехоплює попередній Cloudflare Worker. Він повертає JSON 404 із заголовком `X-Guild-Worker-Request-Id`. У той самий час API дашборда відповідає HTTP 200 і повертає склад гільдії. Тому початкове серверне відображення може працювати, а наступне оновлення та POST заявки — ні.

| Перевірка живого середовища | Спостереження |
|---|---|
| Site `/api/bridge/status` | HTTP 404, заголовок старого Worker |
| Site `/api/bridge/guild` | HTTP 404, заголовок старого Worker |
| Site `/api/bridge/applications` | HTTP 404, заголовок старого Worker |
| Dashboard `/api/site/guild` | HTTP 200, контракт `mistblossom.public-guild.v1` |
| Site `/site-api/v1/status` до встановлення релізу | HTTP 404 від Next.js, без заголовка старого Worker |

Остання перевірка доводить, що новий namespace проходить повз виявлений старий маршрут. Він стане робочим після розгортання Site 4.1.1. Без оновлення живого контейнера новий код нічого не змінить на домені.

Друга помилка форми: `credentials: omit` вимикав cookies навіть для власного домену. Це могло втрачати `cf_clearance` після перевірки Cloudflare. Тепер браузер надсилає same-origin cookies, а сервер сайту передає дашборду лише службову авторизацію та перевірену адресу клієнта.

## Виправлені потоки

| Дія | Публічна адреса | Внутрішнє джерело |
|---|---|---|
| Склад, рейди, прогрес | `/site-api/v1/guild` | Dashboard `/api/site/guild` |
| Список і статуси заявок | GET `/site-api/v1/applications` | Dashboard GET `/api/site/applications` |
| Створення заявки | POST `/site-api/v1/applications` | Dashboard POST → PostgreSQL |
| Перевірка інтеграції | `/site-api/v1/status` | Автентифікований Dashboard `/api/site/status` |
| Обкладинки CMS | `/site-api/v1/media/:sha256` | Dashboard `/api/site/media/:sha256` |
| Авторські моди | `/site-api/v1/mods` | Серверний CurseForge API |
| Публічна живість процесу | `/site-api/v1/health` | Процес сайту |

Внутрішній Docker healthcheck `/api/health` збережено для liveness. Це не браузерний канал синхронізації. Старі site route-файли `/api/bridge` і `/api/media` видаляються підготовкою збірки навіть при розпакуванні поверх попередньої версії.

- Форма має блокування повторного натискання, узгоджену серверну валідацію, приватну квитанцію, обмежений timeout і повідомлення про невизначений результат. Timeout браузера довший за запит до дашборда.
- Успішне надсилання очищує кеш списків заявок. Дедуплікація PostgreSQL попереднього релізу збережена.
- Склад і заявки використовують нові маршрути, same-origin cookies, ETag/304 та фонове оновлення. Для 304 також оновлюється час перевірки й позначка застарілості.
- Помилки старого Worker, Cloudflare challenge, службового токена, Origin, мережі та контракту розрізняються. HTML або пошкоджений JSON не показуються як успішні дані.
- Внутрішній дашборд із неправильним bridge-токеном повертає JSON 401 замість перенаправлення чи неясного 421. Адміністративні права при цьому не розширено.
- Відповіді синхронізації забороняють CDN-кешування. Зберігається тільки обмежений контрольований кеш застосунку.
- `make deploy` перевіряє не лише локальний процес, а й справжні публічні маршрути статусу, складу та заявок через Cloudflare. Невдала перевірка запускає наявний механізм повернення попереднього здорового образу.

## CurseForge: окрема відмова 403

Відмова CurseForge не є наслідком PostgreSQL або Worker сайту. Потрібна серверна авторизація зовнішнього API. Чинний ключ на VPS у цьому сеансі недоступний, тому його пошкодження чи відкликання не оголошується доведеним.

Виправлено конкретну можливу причину: Docker Compose підставляє змінні у значеннях із `$`, якщо їх не захищено одинарними лапками. Підготовка парних env тепер зберігає наявний CurseForge key буквально. Для безпечного введення повного ключа додано `deploy/configure-curseforge.py`; скрипт не друкує ключ і створює резервну копію env з правами 600.

Оновлено клієнт CurseForge: об’єднання одночасних запитів, кеш успішної відповіді на 5 хв, пауза після 401/403 на 5 хв, повтори після інших збоїв із паузою, обмеження розміру відповіді, перевірка схеми та автора. Дата зміни береться з `dateModified`. Ключ залишається тільки на сервері.

Підтверджені раніше дані при тимчасовому збої позначаються як збережені. За їх відсутності довідковий каталог має явну позначку. Він не оголошується актуальними даними CurseForge. Сторінка отримала фонове оновлення та кнопку повторної перевірки через той самий API сайту.

Якщо після правильного передавання повного ключа API повертає `curseforge_access_denied`, потрібен чинний ключ із доступом або усунення обмеження з боку CurseForge. Код застосунку не може надати зовнішній доступ замість провайдера.

## Встановлення на VPS

Команди нижче передбачають чинні каталоги `/srv/mistblossom` та `/srv/lihvodruida-site`, Docker Compose v2, наявні сертифікати й робочий PostgreSQL. Для повного першого переходу також див. `UNIFIED_INTEGRATION_2026-10-16_UA.md` у комплекті.

### 1. Резервна копія й парне оновлення

Перед заміною зберегти env, налаштування Nginx, БД і поточні образи. На чинному дашборді:

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.9.1-sync-fix.zip
unzip -t /tmp/lihvodruida-site-v4.1.1-sync-fix.zip
unzip -o /tmp/lihvodruida-dashboard-v3.9.1-sync-fix.zip -d /srv
unzip -o /tmp/lihvodruida-site-v4.1.1-sync-fix.zip -d /srv
python3 /srv/mistblossom/deploy/prepare-unified-env.py --site-dir /srv/lihvodruida-site
```

Архіви містять відповідно кореневі папки `mistblossom` та `lihvodruida-site`. Робочі секрети до архівів не включені. Скрипт env зберігає поточні значення, узгоджує bridge token і буквально записує наявний CurseForge key. Різні вже задані токени зупиняють підготовку до перезапису.

```bash
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
docker compose -p mistblossom run --rm --no-deps nginx nginx -t
docker compose -p mistblossom up -d --no-deps --force-recreate nginx
cd /srv/lihvodruida-site
make check
make deploy
curl --fail https://lihvodruida.pp.ua/site-api/v1/status
```

Очікуються `integration: ready`, `service: lihvodruida-site` та `api_base: /site-api/v1`. У відповіді не повинно бути `X-Guild-Worker-Request-Id`. Новий deploy перевіряє також контракт складу й списку заявок; один тільки healthy Docker більше не означає успішне оновлення.

### 2. Завершити відмову від старого Worker

Після готовності нового маршруту в Cloudflare Workers Routes прибрати прив’язку старого Worker до `lihvodruida.pp.ua/api/*` та відповідного www-маршруту, якщо він існує. Не змінювати інші домени або чинні маршрути навмання.

Для точного перегляду додано скрипт; API token вводиться приховано. Потрібні права читання/редагування Workers Routes саме цієї зони. Спочатку перегляд:

```bash
python3 /srv/lihvodruida-site/deploy/retire-legacy-worker.py --zone-id YOUR_ZONE_ID
```

Після перевірки виведеного списку можна застосувати:

```bash
python3 /srv/lihvodruida-site/deploy/retire-legacy-worker.py --zone-id YOUR_ZONE_ID --apply
```

Скрипт допускає лише точні API-маршрути публічного домену та www, перед видаленням перевіряє готовність нового сайту й зберігає список маршрутів для відновлення. Загальний маршрут `/*` автоматично не видаляється. Самі Worker scripts не видаляються. Активного Cloudflare-підключення для виконання цієї дії в цьому сеансі немає.

Додати для `/site-api/v1/*` правило обходу кешу, якщо зона має власне примусове Cache Everything; перевірити, що власні WAF-правила не вимагають інтерактивної перевірки для API. Стандартні заголовки no-store уже виставляє застосунок. Перезавантажити відкриті вкладки після оновлення, щоб вони отримали новий JS із новими маршрутами.

### 3. Перевірити CurseForge без розкриття ключа

```bash
cd /srv/lihvodruida-site
node scripts/check-deployed.mjs --curseforge
```

Це лише читання. Якщо є `curseforge_key_missing`, `curseforge_configuration` або `curseforge_access_denied`, ввести чинний повний ключ на сервері й пересоздати сайт:

```bash
python3 deploy/configure-curseforge.py
make deploy
node scripts/check-deployed.mjs --curseforge
```

`make restart` не завантажує змінений env у вже створений контейнер. Ключ не потрібно надсилати в чат чи вставляти у відкриту команду. Успішна перевірка CurseForge вимагає джерело `curseforge` і `stale: false`; показ довідкового каталогу її не задовольняє.

### 4. Приймання дій після встановлення

1. Відкрити `/guild`, залишити вкладку відкритою й перевірити фоновий запит `/site-api/v1/guild` та час останньої перевірки.
2. Надіслати одну погоджену тестову заявку зі своїм контактом. Зберегти номер і приватну квитанцію; звірити запис у панелі та чинне Discord-сповіщення.
3. Повторити ті самі дані в межах вікна дедуплікації: має повернутися той самий номер без другого запису.
4. Змінити статус через панель. Сайт має отримати його наступним опитуванням списку (інтервал 30 с, короткий серверний кеш 15 с; до приблизно 45 с за нормальної мережі).
5. Змінити тестовий гайд і обкладинку; звірити сторінку, RSS і sitemap після кешу CMS до 60 с.
6. На `/mods` перевірити свіжі дані та успіх `check-deployed.mjs --curseforge`.

## Виконані перевірки поставки

- Dashboard 3.9.1: TypeScript, ESLint, повний `build:ci` та production standalone (7/7).
- Site 4.1.1: типи, контракти, кеш, форми, обробка помилок і CurseForge; 27/27 тестів із підключеним справжнім route handler дашборда та контрольованими БД/Discord.
- Оркестрація деплою: 16/16 сценаріїв, включно з відкатом, коли локальний процес здоровий, але публічний маршрут зламаний.
- Підготовка env: 4/4, включно зі збереженням буквальних `$` без виконання shell-коду.
- Зібраний production standalone сайту: 7/7 HTTP-сценаріїв, зокрема CMS, обкладинка, квитанція, дедуплікація, 304, старий Worker та відмова upstream.
- Справжній Chromium: 4/4 сценаріїв на мобільному й desktop viewport. SSR/гідратація складу; форма з Cloudflare-cookie й одним POST; автоматичне отримання нового статусу без перезавантаження/зміни пошуку; оновлення каталогу модів. Браузер звертається до справжнього зібраного сервера, а контрольований upstream замінює лише зовнішні залежності.
- Структура ZIP, CRC і SHA-256 кожного вкладеного файла звіряються з підготовленими вихідними кодами, включно з повторною перевіркою після збереження архівів.

Docker daemon, справжній PostgreSQL і доступ до конфігурації VPS/Cloudflare у цьому сеансі відсутні. Тому фактичний Docker build, nginx -t, живі SQL-конкурентні сценарії, доставка Discord і чинність реального CurseForge key не позначені як перевірені. Команди їх приймання наведено вище.

Збережено попереднє усунення Jekyll, Firebase/Firestore runtime, GitHub Issues/Contents та статичного знімка складу. Виявлена чинна прив’язка старого Worker потребує завершення на стороні Cloudflare; новий сайт її вже не використовує.
