# Оптимізація продуктивності й реакції — v3.8.81

Дата: 14.10.2026, Київ. Основа — повний v3.8.80; бот залишається v3.6.7.
Збережено попередні виправлення Host/HTTP 421 та негайний запуск обробки кнопок.

## 1. Фонові віджети: без бар’єра між парами запитів

Раніше ресурси розбивалися на пари. Наступна пара запускалася лише після
завершення обох запитів попередньої, навіть якщо один слот уже звільнився.
Тепер спільний browser-safe helper settleWithConcurrency одразу бере наступний
ресурс у вільний слот. Клієнтський ліміт залишився 2; порядок результатів
збережено. Помилка одного віджета не скасовує інші.

## 2. Серверний batch фонового API

/api/background/refresh раніше послідовно читав до 3 незалежних ресурсів.
Після перевищення 4 секунд він міг перестати обробляти решту запитаних ресурсів.
Тепер запускає до 3 читань паралельно й повертає результат кожного у вхідному
порядку. Кожен ресурс проходить ті самі перевірки доступу. Сесія, CSRF/origin,
rate limit та ліміт кількості ресурсів збережені. Це оптимізація читань;
паралельного виконання адміністративних змін не додано.

## 3. Recovery та retention черг Discord

Кожне читання outbox раніше спершу сканувало processing-записи для відновлення
завислих відповідей. Під час активного спорожнення черги це повторювало однакову
перевірку на кожній задачі.

Тепер одночасні перевірки об’єднуються; успішний recovery scan повторюється
не частіше ніж раз на 15 секунд у межах процесу та того самого об’єкта БД.
Після помилки scan не вважається успішним і доступний для повторної спроби.
Результати відповідей та leases не кешуються. Нові готові відповіді надалі
перевіряються на кожному читанні outbox без 15-секундної паузи.

Запит recovery відбирає claimedAt, старші за 4 хвилини, до застосування LIMIT.
Раніше перші 150 свіжих processing-записів могли приховати старий завислий.
Транзакція перед зміною повторно перевіряє стан та строк запису.

Retention у ingress/outbox також відбирає тільки записи з простроченим
відповідним deadline до LIMIT. Свіжі зашифровані записи не завантажуються
масово й не проходять непотрібні транзакційні читання.

Компроміс: виявлення давно завислої відповіді може відкластися до наступної
15-секундної recovery-перевірки плюс час виконання/опитування. Це стосується
відновлення аварійного виконання після 4 хвилин, а не звичайної кнопки.

## 4. Менше повторних запитів власного ID бота

Стабільний ID/ім’я облікового запису /users/@me зберігаються на 5 хвилин
окремо для хешу кожного bot token. Максимум — 4 облікові записи у кеші.
Зміна токена чи закінчення TTL потребує нового запиту. Помилки не кешуються
як успіх. Коротка затримка відображення зміненого імені бота можлива до TTL.

Склад учасників, роль самого бота, перелік ролей, дозволи та право керувати
ролями залишаються свіжими. Кеш ID не є джерелом авторизації.

## Перевірки та вимірювання

Новий npm run check:response-performance виконує реальні TypeScript-модулі
через вбудований Node 24 TypeScript transform. Зовнішні API, HTTP-адаптер Next
і БД в ізольованих сценаріях замінено контрольованими залежностями.
Перевірку включено у npm run verify та npm run build:ci.

**16/16 нових поведінкових тестів пройдено:**

- вільний слот запускає наступний віджет до завершення повільного запиту;
- concurrency обмежена; порожній список нічого не запускає;
- три серверні ресурси стартують незалежно, повертаються у правильному порядку;
- помилка одного ресурсу ізольована, четвертий ресурс не запускається;
- origin/session/permissions блокують недозволені читання;
- 30 швидких outbox polls виконують 1 recovery scan замість попередніх 30;
- recovery знаходить старий запис після 150 свіжих;
- конкурентні leases не видають одну готову відповідь двічі;
- помилка recovery не запам’ятовується як успіх;
- outbox retention виконує 1 транзакцію для 1 простроченої відповіді, пропускаючи 150 свіжих;
- ingress retention не змінює свіжу квитанцію;
- повторні role-control snapshots повторно читають roles/member, але не ID;
- відкликані права діють одразу при закешованому ID;
- ротація токена й TTL примушують нове читання ID;
- помилка ID lookup допускає повторну спробу;
- кеш ID обмежений після серії ротацій токенів.

Також пройдено:
- тести бота: 52/52, включно з HTTP-перевіркою швидкого проходження натискання;
- internal-cron-proxy: 21/21;
- live-refresh: 13/13;
- page-performance: 13/13;
- UI-standardization-performance: 20/20;
- security-performance: 97 інваріантів;
- platform-hardening: 15/15;
- footer-version: 9/9;
- api-security: 92 mutation route files;
- imports: 1481 посилання у 369 source files;
- inspect-ci: 468 файлів, 0 blocking issues.

Це локальні перевірки логіки та контрольовані підрахунки запитів. Відсоток
прискорення або p95 на живому VPS не вимірювали. Повні npm run verify,
Next.js/Docker build, typecheck і lint тут не виконані: dashboard dependencies
не встановлено. Перевірки PostgreSQL query plan з реальною БД також не виконані.
Схему та індекси БД у цьому випуску не змінено.

## Встановлення

Повний архів включає попередні виправлення. Резервну копію коду зробити перед
заміною; вміст guild_header_work розпакувати в корінь проєкту, зберігши власні
.env та .env.production.

Якщо v3.8.80 із ботом v3.6.7 уже встановлено:

```sh
docker compose build dashboard
docker compose up -d --no-deps --force-recreate dashboard
docker compose ps
docker compose logs --since=5m dashboard bot cron
```

При оновленні зі старішої версії потрібні обидва образи:

```sh
docker compose build dashboard bot
docker compose up -d --no-deps --force-recreate dashboard bot cron
```

Build dashboard виконує build:ci, включно з новими перевірками. Перезапуск
старого образу без build новий код не застосує. Міграції та зміни токенів не
потрібні. На VPS у межах цієї роботи зміни не встановлювалися.
