# Mistblossom Vanguard Dashboard — опис функціоналу

## 1. Коротко

Dashboard — це приватна панель керування для гільдії **Mistblossom Vanguard**. Вона об’єднує профілі учасників, Battle.net персонажів, Discord-імена, заявки до гільдії, рейди, Discord-embed повідомлення, правила та контент сайту.

Проєкт побудований на **Next.js App Router**, працює як серверний застосунок і зберігає профілі, рейди й заявки у власному **PostgreSQL**, а Discord-дії виконує напряму через Discord Bot API.

## 2. Основні ролі

### Учасник

Бачить тільки потрібні для себе речі:

- свій профіль;
- своїх Battle.net персонажів;
- вибір мейна;
- вибір рейдової ролі;
- рейди й запис на рейд;
- правила.

Не бачить:

- заявки інших людей;
- профілі інших людей;
- технічні статуси;
- інструменти керування Discord;
- інструменти керування контентом;
- кнопки модерації.

### Офіцер

Бачить і керує:

- заявками до гільдії;
- профілями учасників;
- рейдами;
- рейдовими складами;
- звичайними Discord embed повідомленнями;
- модераційними діями по заявках.

Не має доступу до частини дій гільдмайстра, наприклад редагування правил, якщо це обмежено роллю адміністратора.

### Гільдмайстер / адмін

Бачить усе:

- заявки;
- профілі;
- рейди;
- Discord embed editor;
- правила;
- статистику правил;
- контент сайту;
- системні статуси інтеграцій;
- повні службові блоки.

## Склад гільдії

Сторінка `/guild` доступна учасникам, наставникам новачків, офіцерам і гільдмайстру. Вона показує live-склад гільдії без попередньо згенерованих файлів:

- список персонажів із Battle.net Guild Roster API;
- Raider.IO M+ рейтинги `ALL`, `DPS`, `HEALER`, `TANK`;
- item level, клас, спек, роль, фракцію, реалм і avatar;
- статистику зверху: середній RIO, середній item level, максимум RIO/item level;
- блоки “Тип броні” та “Середній RIO гільдії”;
- фільтри за RIO, item level, класом, спеком, роллю, фракцією та пошуком.

Оновлення працює через runtime endpoint `/api/guild/refresh`. Результат кешується у власному PostgreSQL і в кеші процесу. Привʼязки персонажів до профілів кешуються через `PROFILE_CHARACTER_LINK_CACHE_SECONDS` і не створюються, якщо один персонаж знайдений у кількох профілях.

## 3. Авторизація

### Discord login

Основний спосіб входу — Discord OAuth.

Після входу система:

1. перевіряє Discord user id;
2. отримує ролі користувача на сервері;
3. визначає доступ через групи доступу, налаштовані на `/dashboard/groups`; Discord role ID зберігається в групах, а не в env;
4. створює підписану server-side session cookie;
5. створює або оновлює профіль у базі.

### Emergency token login

Для аварійного доступу існує `ADMIN_DASHBOARD_TOKEN`. Це fallback для адміна, який потрібно тримати секретним і ротувати після використання.

### GitHub OAuth

У коді є fallback routes для GitHub OAuth, але основна модель доступу зараз побудована навколо Discord.

## 4. Профіль учасника

Профіль — центральне місце для учасника.

### Що зберігається

- Discord provider id;
- display name;
- avatar;
- stable profile id;
- бажане реальне/зручне ім’я;
- Battle.net sync state;
- список збережених персонажів;
- main character;
- raid role preference;
- останній синхронізований Discord server nickname.

### Поле `Ім’я`

Учасник може задати ім’я, яке використовується для серверного Discord nickname.

Формат nickname:

```text
Ім’я [Мейн, Альт1, Альт2]
```

Приклад:

```text
Дмитро [Khayen, Krouli, Sebas]
```

Правила:

- перший персонаж у квадратних дужках — завжди мейн;
- максимум 3 персонажі;
- якщо Discord-ліміт 32 символи перевищено, система скорочує список, але пріоритетно залишає мейна;
- власника сервера бот перейменувати не може через обмеження Discord hierarchy, тому для owner показується режим копіювання.

### Discord nickname sync

Після збереження імені користувач може застосувати серверний nickname.

Система:

1. будує nickname plan;
2. перевіряє поточний server nickname;
3. якщо nickname не збігається з шаблоном, показує блок “Зараз на сервері”;
4. для звичайного учасника викликає Discord API для зміни nickname;
5. для owner сервера дає скопіювати готовий формат.

## 5. Battle.net персонажі

Battle.net OAuth використовується для отримання персонажів користувача.

### Основна логіка

1. Учасник натискає підключення Battle.net.
2. Система відкриває Battle.net OAuth.
3. Після callback система отримує profile/account дані.
4. Сканує персонажів.
5. Фільтрує персонажів, які належать до гільдії `WOW_GUILD_NAME`.
6. Кандидати тимчасово зберігаються у профілі з TTL `BATTLENET_CANDIDATE_TTL_MINUTES`.
7. Учасник додає потрібних персонажів у профіль.

### Збережені персонажі

Для кожного персонажа зберігаються:

- ім’я;
- realm;
- region;
- class;
- specialization;
- role;
- item level;
- media/avatar;
- profile url;
- timestamp останнього оновлення.

### Мейн

Мейн використовується для:

- Discord nickname;
- пріоритетного показу в профілі;
- запису на рейд;
- визначення ролі, якщо ручна роль не задана.

### Автооновлення перед рейдом

Перед записом на рейд система намагається оновити дані збережених персонажів без повторного Battle.net логіну.

Порядок:

1. спочатку оновлюється мейн;
2. потім інші персонажі;
3. якщо Battle.net тимчасово недоступний, запис не ламається — використовується останній збережений snapshot.

## 6. Роль у рейді

У профілі є вибір рейдової ролі:

- Auto;
- Tank;
- Healer;
- DPS.

Пріоритет:

```text
якщо роль вибрана вручну → використовується вона
якщо роль не вибрана → використовується роль мейна
```

Роль прив’язана до поточного мейна. Якщо мейн змінено або видалено, ручна роль очищається.

## 7. Рейди

Рейдова система дозволяє офіцерам створювати рейдові оголошення, публікувати їх у Discord і збирати склад.

### Основні поля рейду

- назва;
- тип складності: normal, heroic, mythic;
- дата;
- час;
- канал Discord;
- опис із Markdown;
- consumables: own/guild;
- loot mode;
- composition;
- min item level;
- max players;
- thumbnail/image;
- role mentions для Discord;
- статус: draft, published, closed.

### Публікація в Discord

Офіцер або адмін може:

- зберегти чернетку;
- опублікувати рейд у Discord;
- оновити існуюче Discord-повідомлення;
- закрити рейд;
- видалити рейд.

Після змін складу оновлюється тільки конкретне Discord-повідомлення цього рейду, а не всі рейдові повідомлення.

### Запис на рейд

Користувач може вибрати:

- Going / Підписатися;
- Late / Затримаюсь;
- Skipped / Пропускаю.

Запис працює з сайту і з Discord-кнопок.

### Видимість для учасника

Звичайний учасник бачить:

- базову інформацію рейду;
- правила/посилання;
- кнопки запису;
- детальний склад паті;
- середній item level рейду;
- мінімальний item level рейду.

Звичайний учасник не бачить:

- item level окремих персонажів;
- службові адмінські кнопки;
- технічні дані;
- чернетки.

Офіцер і адмін бачать повний склад, item level персонажів і службові попередження.

### Live-оновлення

Сторінка рейду має live sync:

- snapshot перевіряється приблизно кожні 10 секунд;
- якщо змінився склад або статус, сторінка оновлюється через `router.refresh()`;
- кнопки запису працюють без повного reload.

## 8. Заявки до гільдії

Заявки читаються з GitHub Issues.

### Що підтримується

- список заявок;
- статуси: review, accepted, declined;
- фільтри по статусу, класу, пошуку;
- live фільтри без звичайного form submit;
- debounce пошуку;
- query params у URL;
- масова зміна статусів;
- модераційну подію в PostgreSQL;
- синхронізація статусних labels.

### Джерело даних

Заявки зберігаються у колекції документів `guildApplications`.

Статуси зберігаються через labels:

- `status:review`;
- `status:accepted`;
- `status:declined`.

Код також чистить legacy/broken labels старих версій.

## 9. Discord embed editor

Панель дозволяє створювати й редагувати Discord embed повідомлення.

### Звичайні embed

Доступно для офіцера і адміна:

- content above embed;
- embed title;
- description;
- color;
- author;
- footer;
- fields;
- role mentions;
- редагування існуючого повідомлення через message link.

### Rules embed

Доступно для адміна.

Підтримує:

- guild rules;
- raid rules;
- кнопки accept/decline;
- видачу ролей після прийняття;
- kick після відмови;
- статистику правил через Worker endpoint.

### Dynamic preview

Редактор має:

- live preview;
- режим ПК/телефон;
- Discord Markdown preview;
- counters для Discord-лімітів;
- warnings для markdown проблем;
- блокування публікації при перевищенні жорстких лімітів.

## 10. Статус інтеграцій

Для staff є compact panel “Стан системи”.

Перевіряє:

- Discord;
- Battle.net;
- PostgreSQL;
- власний PostgreSQL.

Статус оновлюється вручну або автоматично приблизно раз на хвилину.

## 11. Контент сайту

Адмін може керувати матеріалами сайту:

- новини;
- гайди;
- slug;
- description;
- body;
- categories;
- tags;
- images;
- update/delete.

Файли створюються або оновлюються через GitHub Contents API у гілці `GITHUB_CONTENT_BRANCH`.

## 12. Безпека

Система має кілька рівнів захисту:

- signed session cookie;
- OAuth state cookie;
- HMAC для profile id;
- trusted origin checks;
- allowed hosts;
- optional Cloudflare-only mode;
- CSP middleware з nonce;
- noindex/noarchive headers;
- rate limits для чутливих дій;
- body size limits;
- server-only secrets;
- розділення member/moderator/admin UI.

## 13. Мобільний UX

Останні зміни стандартизують:

- шрифти;
- відступи;
- мобільні контейнері;
- bottom navigation;
- toast на мобільному;
- touch-friendly кнопки;
- компактні картки;
- однакову сітку метрик.

Мета — зробити телефонну версію схожою на зручний застосунок, а не просто на стиснутий desktop сайт.

Live-синхронізація Discord-доступу: панель періодично перевіряє актуальні ролі користувача на Discord-сервері через бота й заново рахує права з ENV-мапінгу ролей.
