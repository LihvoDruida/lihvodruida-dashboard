# Узгоджена синхронізація Site 4.2.0 і Dashboard 3.11.0

Парне оновлення після Site 4.1.1 і Dashboard 3.10.1. Обидва архіви повні й містять попередні виправлення CMS, заявок, приватного транспорту та відмови від legacy-джерел. Живий VPS і Cloudflare в цьому сеансі не змінювалися.

## Яку прогалину закрито

Раніше сайт покладався на окремі TTL: склад — 60 с, заявки — 15 с, CMS — 60 с. Відкрита стаття взагалі не перевіряла зміни в CMS. RSS дозволяв зовнішнє кешування ще на 300 с. На стороні дашборда були додаткові кеші складу й рейдів, тому одного скидання кешу сайту було недостатньо.

Тепер сайт перевіряє версії відповідних даних у PostgreSQL. Змінена версія скидає кеш потрібного ресурсу, а браузер отримує сигнал для фонового оновлення.

| Потік | Нова поведінка |
|---|---|
| CMS → відкрита стаття або каталог | Перевірка змін у фоні, оновлення через Next.js без повної навігації |
| Зняття з публікації | Наступний цикл синхронізації прибирає статтю з відкритої сторінки та публічного каталогу |
| CMS → RSS і sitemap | Один актуальний CMS-знімок; HTTP/CDN no-store, видалені матеріали не залишаються через старий TTL |
| Модерація заявки | Зміна версії заявок скидає кеш усіх поточних фільтрів; відкрита сторінка перечитує свій список |
| Оновлення складу або рейду | Версія складу змінюється; публічний producer перечитує PostgreSQL без додаткового довгого кешу |
| Порожній або недоступний upstream | Холодний збій повертає помилку; допустимі збережені дані позначаються застарілими |
| Запит, що почався до зміни | Старий результат не може замінити новіший кеш після його інвалідації |

## Протокол

Додано приватний `GET /api/site/sync` на дашборді. Він потребує того самого `PUBLIC_SITE_BRIDGE_TOKEN`, що й чинний внутрішній транспорт. Ключ читає тільки сервер сайту через `DASHBOARD_INTERNAL_URL=http://dashboard:3000`.

Відповідь `mistblossom.public-sync.v1` містить три непрозорі версії: `content`, `guild`, `applications`, та час перевірки. Вона не містить текстів чернеток, контактів заявників або службового токена.

Версії обчислюються за ідентифікаторами й версіями рядків PostgreSQL (`xmin`, `updated_at`). Тому зміни бачать різні процеси та контейнери, включно з прямим SQL-редагуванням, яке не оновило прикладне поле дати. Для складу враховано також рейди, налаштування та перехід київської дати.

Чернетки CMS не входять у публічну ревізію. Для запиту заголовків опублікованих матеріалів додано частковий індекс у `schema.sql`; його застосовує штатне оновлення дашборда.

Публічний сайт надає лише безпечну відповідь `/site-api/v1/sync`. Метадані на сервері об’єднуються й кешуються на 3 секунди. Видима онлайн-вкладка перевіряє їх приблизно раз на 15 секунд із невеликим jitter. За нормально доступних сервісів оновлення відкритої сторінки зазвичай потребує одного циклу плюс час запитів — це не гарантія фіксованої затримки під час збоїв або у прихованій вкладці.

Нова readiness перевіряє capability `sync:revisions:v1`. Site 4.2.0 не оголошує інтеграцію готовою з дашбордом, який ще не підтримує цей механізм.

## Додаткові виправлення

- Кеш має покоління: завершення старого запиту після інвалідації не зберігає застарілий результат і не стирає новий pending-запит.
- Тимчасова недоступність перевірки версій не позначає кеш як свіжий. Холодний кеш не підміняється порожніми даними.
- Якщо CMS змінився між сторінками пагінації, сайт один раз повторює збір знімка. Змішані ревізії не видаються користувачу.
- Публічний producer складу обходить додатковий кеш читання PostgreSQL. Читання публічного розкладу не запускає auto-close операції рейдів.
- При зміні версії заявки зберігаються пошук і фільтри сторінки; запит оновлення, отриманий під час іншого читання, не губиться.
- sitemap має керований route handler із no-store та датою фактичної зміни матеріалу. Стара `src/app/sitemap.ts` видаляється підготовкою збірки при оновленні поверх попереднього дерева.
- Публічна перевірка деплою тепер перевіряє також новий sync endpoint. Docker healthy сам по собі не підтверджує зв’язок через Cloudflare.

## Встановлення обох проєктів

Спочатку зберегти БД, env, конфігурацію Nginx і поточні образи. Каталоги залишаються `/srv/mistblossom` та `/srv/lihvodruida-site`.

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.11.0-site-sync.zip
unzip -t /tmp/lihvodruida-site-v4.2.0-dashboard-sync.zip
unzip -o /tmp/lihvodruida-dashboard-v3.11.0-site-sync.zip -d /srv
unzip -o /tmp/lihvodruida-site-v4.2.0-dashboard-sync.zip -d /srv
python3 /srv/mistblossom/deploy/prepare-unified-env.py --site-dir /srv/lihvodruida-site
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
cd /srv/lihvodruida-site
make check
make deploy
node scripts/check-deployed.mjs
```

Оновити спочатку дашборд, потім сайт. Попередній Site 4.1.1 може працювати з новим дашбордом під час переходу. Новий сайт потребує нового sync endpoint; readiness має зупинити встановлення несумісної пари.

Нових секретів або відкритих портів немає. Потрібні чинний однаковий bridge token і приватна Docker-мережа. Якщо перший перехід ще не завершено, налаштування Nginx, сертифікатів і старого Cloudflare Worker описані в `SYNC_INSPECTION_2026-10-16_UA.md`.

Після розгортання перезавантажити відкриті вкладки для нового JavaScript. Очистити попередні збережені копії `/feed.xml` і `/sitemap.xml` у власному CDN-кеші або дочекатися закінчення старого TTL: новий no-store не видаляє вже створені копії автоматично. Власні правила примусового кешування не повинні кешувати `/site-api/v1/*`.

Доступ CurseForge лишається окремим: HTTP 403 зовнішнього API потребує чинного серверного ключа та дозволів. Ця синхронізація не надає доступу до чужого API.

## Виконані перевірки

| Перевірка | Результат |
|---|---|
| Парні тести сайту та дашборда | 32/32, без пропусків |
| SQL синхронізації на PostgreSQL WASM і авторизація route | 6/6 |
| Production standalone сайту | 7/7 |
| Справжній Chromium, site API та зібраний сервер | 6/6 |
| Повні `build:ci` обох проєктів | Успішно |
| ESLint дашборда, типи обох проєктів, diff checks | Успішно |

Парний тест використовує справжні функції створення/редагування CMS, справжній SQL producer ревізій та споживача сайту. Сховище CMS контрольоване; його записи відображаються в ізольованій PostgreSQL WASM для перевірки протоколу. Перевірено чернетку, публікацію, зміну тексту, RSS/sitemap і зняття з публікації до закінчення звичайного TTL кешу.

Браузерна перевірка працює зі зібраним production-сервером сайту та контрольованим upstream. Вона підтвердила оновлення відкритої статті без повної навігації, її зникнення після unpublish, очищення RSS/sitemap та зміну статусу заявки. Живі заявки, матеріали й Discord-повідомлення не створювалися.

SQL виконано на PostgreSQL WASM, а не на живій БД VPS. Docker build, nginx -t і фактичне розгортання на сервері в цьому сеансі не виконувалися. Архіви перевіряються на центральний каталог ZIP, CRC та SHA-256 кожного файла, включно з повторною перевіркою після збереження.

## Приймання на VPS

1. `GET /site-api/v1/status` має показати `integration: ready`; `/site-api/v1/sync` — три версії без старих Worker-заголовків.
2. Відкрити статтю на сайті. Змінити текст у дашборді й дочекатися фонового оновлення без F5.
3. Зняти тестову статтю з публікації; перевірити відкриту сторінку, каталог, RSS і sitemap.
4. Змінити статус погодженої тестової заявки; звірити сайт, зберігши поточний пошук і фільтри.
5. Оновити склад або розклад штатним інструментом дашборда; перевірити відповідний розділ сайту й час даних.
