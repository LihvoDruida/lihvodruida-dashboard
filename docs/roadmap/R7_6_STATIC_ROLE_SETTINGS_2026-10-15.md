# R7.6 — Discord-ролі Статика

Dashboard **3.8.99**, bot **3.6.9**, contract **1.1.1**. 15.10.2026.

Форма налаштування ролей на `/dashboard/settings` тепер перевіряє підтвердження сервера, зберігає вибір під час повторного читання, має постійні повідомлення стану й локальний пошук ролей. Інші форми налаштувань залишаються окремими пакетами R7.

## Відтворені дефекти

Попередній компонент із повного архіву 3.8.98 перевірено тим самим Chromium-стендом. Сім baseline-проб підтвердили дефекти; вони не позначають стару поведінку правильною.

| Випадок | 3.8.98 | 3.8.99 |
|---|---|---|
| HTTP 200, `ok:false`, settings присутнє | Повідомлення про успішне збереження | GET-звірка без повтору POST |
| Початкове читання з `ok:false` | Рендер конфігурації як дійсної | Помилка, без селекторів конфігурації |
| Успішний запис вимикає кнопку | Результат не отримує фокус | Фокус на постійному status |
| Незбережений вибір | Немає dirty-маркера | Загальні live-refresh guards бачать чернетку |
| Discord warning | Немає кнопки перечитати ролі | Доступний GET-only refresh |
| POST і GET-відновлення зірвалися | «Перевіряємо…» лишалося після завершення | Остаточний непідтверджений стан |
| Збереженої ролі вже немає в каталозі | Відсутня у селекторі | Явна недоступна опція з ID |

## Поведінка форми

GET приймається лише з явним `ok === true` і перевіреним мінімальним контрактом: рядкові snowflake ID або порожні неналаштовані ролі, коректні властивості каталогу, унікальні ID, boolean доступності, nullable warning та guildName. Некоректний payload не перетворюється на порожній успішний каталог.

POST підтверджує успіх лише з `ok === true` і двома різними непорожніми ролями, що відповідають надісланому вибору. HTML, truthy-рядок, неповний payload або інша пара ролей запускають звірку через GET. Автоматичного повтору запису немає. Якщо збережені ID збігаються з вибраними, форма повідомляє саме цей факт; це не доводить завершення всіх побічних дій попереднього запиту.

HTTP 400 не завжди означає відсутність запису: чинний серверний `saveStaticSettings` спочатку записує конфігурацію, потім журнал аудиту, а маршрут перетворює помилку на 400. Тому 400/409/408/5xx звіряються читанням. При невідповідному збереженому стані причина HTTP 400 лишається в результаті, включно з відмовою змінити роль за наявності активних підписантів. Відомі відмови 401/403/413/415/422/428/429 показуються без recovery. Серверний маршрут і послідовність його записів цим пакетом не змінювалися.

Незбережені ID зберігаються після ручного GET, збою та recovery; успішне читання оновлює збережену конфігурацію й каталог окремо від вибору. Чернетка позначена `data-dirty`, запис — submitting/busy, тому чинні RSC/background guards можуть відкласти оновлення. Це пам’ять змонтованої форми, без нового сховища для reload або іншої вкладки.

Кнопка «Оновити ролі» доступна й після Discord warning. Читання має окрему помилку та status; успішне читання не стирає результат відхиленого запису. Запис і читання взаємно блокуються, дубльована дія в одному запитному каналі ігнорується. Дедлайн GET — 12 секунд під загальною межею 15; POST — 20 секунд, увесь save/recovery — 40 секунд. Демонтаж скасовує запити; пізній результат не публікується в компоненті.

Постійні status-регіони мають atomic live announcement і програмний фокус. Після явного запису або перечитування фокус переходить до відповідного результату, якщо користувач не перейшов до іншого елемента. Пошук і селектори блокуються на час запиту. Введення та Enter у пошуку не зберігають права.

## Пошук і виміряна робота

Пошук за назвою або ID працює в отриманому каталозі без GET/POST. Нормалізований NFKC/uk-UA індекс перебудовується лише при зміні масиву ролей; Map використовується для перевірки поточного вибору. Фільтрація проходить індекс лінійно; індекс не робить пошук константним.

У контрольованому Chromium-сценарії з **250 ролями** обидва селектори разом містять **502 опції** до пошуку. Один збіг за українською назвою звужує їх до **8 опцій**, зберігаючи дві вибрані ролі й порожню опцію в кожному селекторі. Запитів під час пошуку — **0**. Індексний тест читає назви 250 разів при побудові та не перечитує їх під час 100 наступних пошуків. Це лічильники операцій на контрольованих даних, без заяви про production latency або FPS.

Вибрані наявні ролі залишаються у результатах навіть без збігу з пошуком. Для відсутньої ролі є disabled-опція; фільтр не створює вигадані доступні ролі. Відсутність збігів має власний текст. Роль учасника досі потребує manageable; роль РЛ може бути вище ролі бота, оскільки її перевіряють, а не видають.

## Перевірки

- `npm run check:static-role-settings` — **14/14**: контракт GET/POST, unconfigured стан, warning, невалідні типи й дублікати, точна пара ролей, Unicode/ID-пошук, збереження вибору, 250 ролей і 100 пошуків.
- `npm run check:static-role-settings-browser` — **21/21**, production React і чинні global/module CSS у Chromium 153.0.8010.0. Перевірено сім дефектів, GET retry, чернетку, focus, невідповідні підтвердження, застосований запис із втраченою відповіддю, блокування дій, дедлайн, unmount, обидва HTTP 400, ієрархію, Enter у пошуку, 250 ролей і дев’ять ширин 320–1920 px. Runtime-помилок немає.
- У timeout-сценарії лише тестовий таймер 20 000 мс прискорено до 150 мс; перевірено реальний abort і наступний GET. У production тривалість дедлайну не змінена.
- Повний `npm run build:ci` — exit 0, включно з TypeScript, 20 наявними route-сценаріями Статика, регресією очищення 17/17, аудитами та inspect:ci (517 файлів, 0 блокерів).
- `npm run lint` і фінальний ESLint змінених файлів — exit 0. Production build Next 16.3.5 завершився за 8 секунд на локальному теплому кеші.
- Standalone — **6/6**, 4 057 файлів, 84 368 216 байтів; packaged Sharp render, ресурси, відсутність source/CI у пакеті та запуск готового Next server перевірено локально. [Машинний звіт](R7_6_VALIDATION_2026-10-15.json).

Швидка перевірка додана до `verify` та `build:ci`. Browser-suite окрема, потребує зовнішніх Playwright, esbuild і Chromium; production-залежностей не додано. Для локального стенда використовуються `MISTBLOSSOM_QA_MODULES`, `MISTBLOSSOM_QA_CHROMIUM`, `MISTBLOSSOM_QA_OUTPUT`. Baseline приймає `MISTBLOSSOM_TEST_STATIC_ROLE_SOURCE` із попереднім компонентом та його CSS-модулем. Next Link замінено на звичайне посилання тільки в тестовому bundle; навігацію Next цей стенд не перевіряє.

## Межі

Збережено чинні серверні права, перевірку ролі РЛ, ієрархію бота, заборону зміни ролі учасника за активних підписантів, текст/версії та явне прийняття правил. SQL-схема, API-маршрути, cron, бот і контракт не змінювалися. Цей пакет не додає серверної ревізії для конкурентного редагування конфігурації або атомарності запису конфігурації разом з аудитом.

Живі PostgreSQL/Discord, Docker/VPS та NVDA/TalkBack у цьому запуску не перевірялися. Приймання R6 користувач проведе пізніше. Наступний обмежений пакет — **R7.7: налаштування журналу та Security mirror**; інші форми й повний R7 залишаються відкритими.
