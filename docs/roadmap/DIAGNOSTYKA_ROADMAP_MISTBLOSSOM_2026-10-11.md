# Діагностика функціоналу та план розвитку Mistblossom Vanguard

Дата: 11.10.2026. База перевірки: повний проєкт v3.8.68, версія архіву 9, після оновлення палітри керування.

## 1. Основний висновок

Перший наступний реліз має виправляти цілісність даних, повторну публікацію та керованість автоматизації. Розширення можливостей варто починати після цих виправлень.

Штатна `verify` і 45 тестів бота пройшли. Додаткові поведінкові перевірки відтворили п’ять дефектів та одне небезпечне обмеження керування. Отже, успішні поточні перевірки не закривають усі важливі сценарії.

Пріоритетний порядок:

1. Атомарність змін у PostgreSQL.
2. Єдина операція публікації одного рейду без дублів.
3. Повний пошук і справжня серверна пагінація профілів.
4. Призупинення очищення під час активного запуску.
5. Збереження чернеток груп і вихід із завислого запиту.
6. Завершення існуючих сценаріїв, скорочення ручних дій та узгодження дизайну.
7. Нові модулі.

Цей документ містить діагностику й план. Виправлення, описані нижче, ще не внесені у вихідний код.

Перевірки PostgreSQL-алгоритму виконано із детермінованим замінником SQL-запитів, що зберігає їхній порядок і знімки даних; живий PostgreSQL у цьому середовищі не запускався. Discord-публікації відтворено із замінником Discord API. Це підтверджує поведінку коду за вказаних умов, але не встановлює, що такий інцидент уже стався на робочому сервері.

Реальні облікові записи, Discord-учасники, повідомлення й робоча база не змінювалися. Не перевірялися живий Docker-стек, production-метрики, мережеві затримки, налаштування Developer Portal та відновлення production-бекапу.

Прийняття правил гільдії, Статика й інших типів виключене з пропозицій щодо скорочення взаємодій. Чинні вимоги, перевірки та явне прийняття правил зберігаються. Наявні захисні тести цих механізмів запускалися як частина загальної регресії.

## 3. Підтверджені проблеми: виправляти першими

P1 — високий пріоритет через ризик для даних або незворотних операцій. P2 — помітний функціональний дефект чи втрата роботи користувача. Інцидент рівня P0 на робочому сервері цією перевіркою не підтверджено.

| ID | Пріоритет | Проблема | Доказ |
|---|---|---|---|
| D01 | P1 | Паралельні `set(merge)` / `update` можуть затерти зміни іншого запиту | Дві різні зміни профілю залишили лише одну; два increment(1) дали 1 замість 2 |
| D03 | P1 | Два запити публікації одного чернеткового рейду створюють два оголошення | Два виклики створення; останній messageId замінив перший |
| D02 | P1 | Каталог і пошук обмежені першими 200 профілями | За 301 запису каталог показав 200; наявний Target250 не знайдено |
| D06 | P1 | Активний запуск очищення блокує команду «Призупинити» | За зайнятого lease функція відмовила до запису паузи |
| D04 | P2 | Перемикання групи стирає незбережену чернетку | Змінена назва повернулася до початкової після переходу в іншу групу |
| D05 | P2 | Незавершений запит очищення блокує керування без дедлайну | Через 120 секунд браузерного часу busy=true, кнопки вимкнені, помилка не показана |

### D01. Втрата паралельних змін

Джерело: `dashboard/src/lib/db/documentStore.ts`, методи `PgDocumentRef.set`, `update`, `write`; орієнтири — рядки 303–344. Реальні споживачі: `profiles.ts`, збереження імені, режиму відображення, граматичного роду та інших полів.

Поза явною транзакцією код читає весь документ, змінює копію та записує весь JSON через UPSERT. Два запити можуть прочитати одну стару версію. Другий запис повертає старі значення полів, змінених першим.

Відтворення:

- Початок: preferredName=Old, grammaticalGender=neutral.
- Одночасно: preferredName=New і grammaticalGender=male.
- Фактично: preferredName=Old, grammaticalGender=male.
- Для count=0 два одночасні increment(1) дали count=1.

Рекомендоване виправлення: атомарні операції адаптера. Для складних merge/sentinel-операцій — транзакція з перевіркою конфлікту й обмеженим повтором або блокуванням потрібного документа; для простих patch/increment — коректний SQL update. Окремо обробити відсутній документ і одночасне створення. `update` має зберігати семантику «не створювати відсутній документ».

Не достатньо обгорнути один конкретний endpoint: дефект знаходиться у спільному адаптері. Наявні `runTransaction` використовують REPEATABLE READ з повтором конфліктів; висновок D01 стосується насамперед прямих нетранзакційних викликів.

Готовність: інтеграційні тести на справжньому PostgreSQL доводять збереження незалежних полів і правильну суму паралельних increment; перевірені merge, вкладені поля, delete/update та create-конфлікт. Транзакційні повтори не повторюють зовнішню Discord-дію. Підстави щодо ізоляції: [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

### D03. Дубль публікації рейду

Джерела: `raids.ts → publishOrUpdateRaid` (5180–5350), `saveAndMaybePublishRaid`; `api/raids/publish/route.ts`; `discordAdmin.ts → discordApi` (366–376).

Якщо два запити мають один знімок чернетки без messageId, обидва переходять у створення повідомлення. Стан публікації зберігається після Discord POST. На відтворенні отримано два повідомлення, а останнє збереження залишило тільки другий messageId.

Транспорт додає випадковий nonce та зберігає його для повторів одного REST-виклику. Це корисний чинний захист, але два окремі виклики отримують різні nonce.

Виправлення: збережена операція публікації з ключем рейд/канал/ревізія, ексклюзивне виконання на рівні сховища, повторне читання рейду під захистом операції та стабільний nonce для однієї публікації. Після неоднозначного результату потрібен стан звірки, а не новий POST із новим ключем. Локальний Map у `idempotency.ts` не забезпечує збереження між перезапусками чи процесами.

Готовність: два паралельні запити дають одну публікацію; повтор після рестарту повертає відомий результат; збій після Discord POST і перед DB commit не створює нове оголошення без звірки. Перенесення в інший канал є окремою контрольованою операцією. Аналогічний сценарій публікацій опитувань треба перевірити окремо — відтворення D03 проводилося саме для рейду.

Discord перевіряє nonce протягом кількох хвилин, тому він доповнює збережений стан операції: [Create Message](https://docs.discord.com/developers/resources/message#create-message).

### D02. Неповний каталог профілів

Джерела: `app/profiles/page.tsx` (217–243), `profiles.ts → listDashboardProfiles` (1274–1348).

Сторінка просить limit=500; бібліотека обмежує його до 200. Пошук, частина фільтрації та сортування виконуються після читання цієї порції. Видима пагінація ділить вже обрізаний набір. Це також спотворює загальні показники каталогу, якщо їх трактувати як показники всіх учасників.

Виправлення: серверні пошук/фільтри/сортування до LIMIT; курсорна пагінація зі стабільним додатковим ключем; окремий count/агрегати з тими самими правами й фільтрами. Підвищення 200 до 500 лише відсуне дефект.

Готовність: знаходяться записи за межами першої порції на наборах 201/501/2000 профілів; між сторінками немає дублів і пропусків; права доступу застосовані до вибірки та агрегатів; відсутній результат показується лише після коректного пошуку.

### D06. Пауза автоматизації під час роботи

Джерело: `discordMemberCleanup.ts → pauseDiscordCleanup` (76–84). Функція потребує той самий lease, який тримає активний worker. За зайнятого lease вона просить повторити паузу пізніше й не записує enabled=false.

Це підтверджене обмеження керування, особливо небажане для системи виключення людей. Worker уже перевіряє актуальні settings перед виключенням (215–216), тому основа для керованої зупинки є.

Виправлення: окремий атомарний stop/pause-сигнал, який можна записати під час роботи worker. Перевіряти його перед наступною незворотною дією; конфігураційні зміни ролі й строку залишити захищеними. UI має підтверджувати запит паузи та показувати, чи є вже відправлена дія.

Готовність: натискання паузи під час запуску приймається; worker припиняє починати наступні DELETE після спостереження сигналу. Уже відправлений DELETE неможливо надійно скасувати — це має бути чесно відображено. Наявні захисти бота, owner/admin, ролей, joined_at і uncertain зберігаються.

### D04. Чернетка редактора груп

Джерело: `AccessGroupsManager.tsx` (105–129). Відображається лише форма вибраної групи; перемикання демонтує попередню форму. Поля використовують defaultValue без окремого сховища чернеток.

Браузерне відтворення: «Група 2» → назва «Незбережена назва» → інша група → назад → знову «Група 2».

Виправлення: стан чернетки за ID групи, індикатор незбережених змін, явне скидання та обробка конфлікту серверної версії. Зберігати чернетки між вкладками; для виходу зі сторінки визначити контрольоване відновлення. Надання прав не робити непомітним автозбереженням.

Готовність: назва, ролі й усі checkbox-и відновлюються після перемикання; після успішного save чернетка стає чистою; чужа серверна зміна не перезаписується мовчки.

### D05. Завислий запит блокує керування

Джерело: `DiscordMemberCleanupPanel.tsx → jsonRequest` (20–24), `action` (90–99). У fetch немає заданого дедлайну чи скасування. Busy знімається лише після завершення promise. Відтворення незавершеного POST через 120 секунд залишило всі відповідні кнопки вимкненими без повідомлення про помилку.

У проєкті вже є `dashboardApiClient.ts` та `apiHttp.ts` із таймаутом і контрольованими повторами; цей локальний helper обходить спільний механізм.

Виправлення: використати спільний клієнт, додати скасування на виході й окремі стани «оновлення списку», «збереження налаштувань», «перевірка». Після таймауту POST зчитати стан операції; не повторювати мутацію автоматично. Перевірити інші прямі fetch, зокрема StaticRoleSettingsClient.

Готовність: незавершений GET/POST має обмежене очікування, зрозумілий результат і відновлення керування; пізня відповідь старого запиту не перезаписує нову; в одному кроці відновлення не виникає другого виключення чи публікації.

## 5. Мінімізація взаємодій із сайтом

Мета — скоротити повторні введення, навігацію за технічними кнопками, ручне оновлення та повтор роботи після помилки. Автоматизація незворотних дій потребує явного керованого правила й збереженого стану.

Наведені скорочення — цілі сценаріїв, а не виміряні середні показники поточних користувачів. Обирати мейна, бажану роль та рішення про модерацію має користувач; система може підставити відомі значення.

| Сценарій | Поточне місце тертя | Пропозиція | Ціль |
|---|---|---|---|
| Ім’я → Discord-нік | Окремі збереження імені та «Застосувати» | «Зберегти й синхронізувати» з фоновою операцією й видимим статусом; для owner — копіювання | 2 окремі підтвердження → 1 |
| Додавання персонажів | Кандидати вже додаються пачкою; наступні налаштування можуть вимагати нових переходів | Один підсумковий крок: вибрані персонажі, мейн і роль; неоднозначний вибір залишається явним | Один завершений сценарій замість кількох роз’єднаних |

## 6. Дизайн і продуктивність існуючих систем

### Дизайн

- Палітру брати зі спільних tokens.css; уже виправлену бурштинову палітру керування зберегти.
- Узгодити loading/empty/error/success/paused/partial/uncertain на всіх робочих сторінках. «Немає даних» і «Дані не завантажились» мають різні причини й дії.
- Єдина основна дія для кожної задачі; додаткові інструменти — у контексті конкретного учасника, рейду чи налаштування.
- Зберігати вкладки, пошук, сортування та розкриті списки у URL або доречному локальному стані.
- Перевіряти довгі українські назви, порожні списки, 1000+ записів, disabled/focus/hover, клавіатуру й мобільні форми.
- Існуючі вкладки ManagementSections вже підтримують стрілки, Home/End і збереження змонтованих панелей. Цей механізм варто застосувати до інших багатозадачних редакторів із контролем ваги DOM.
- Дизайн сторінки логування не включати до нового перероблення.

Орієнтир для вкладок і фокусу: [WAI-ARIA Tabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/).

### Продуктивність і Discord

1. Спочатку виправити вибірки профілів, потім вимірювати SQL через EXPLAIN ANALYZE на репрезентативних даних. Індекси додавати для реальних запитів.
2. Звести прямі браузерні fetch до існуючого API-клієнта; узгодити дедлайни й скасування. Для довгих процесів відокремити створення задачі від очікування її завершення.
3. Зберігати поточні single-flight, обмежені черги й backoff. Виміряти сукупні виклики dashboard і bot з одним bot token; їхні локальні обмежувачі зараз живуть у різних процесах.
4. Подієве оновлення використовувати разом із періодичною звіркою після перепідключення Gateway. Суцільний повний скан після кожної події не потрібний.
5. Перед виключенням залишити перевірку поточного учасника, ролей, дати вступу, ієрархії, права бота, актуальності правила та lease.
6. Глибина розкритого UI-списку не має визначати обсяг повторних читань кожні 10 секунд. Зараз cleanup відновлює всі розкриті сторінки послідовними запитами по 25; для великих списків додати ревізію/оновлення змінених рядків або обмежене вікно.
7. Після атомарності й поведінкових тестів розділяти великі доменні файли: raids.ts — 6705 рядків, profiles.ts — 3543, raidPolls.ts — 3436. Розмір сам по собі не є функціональним багом; мета — відокремити сховище, політику, публікацію та відновлення.

Частий tick сам по собі не дорівнює важкому Discord-скану. У поточному очищенні idle-виклик перевіряє збережену чергу і повертається без Discord API; активний режим — 10 секунд, idle — 60. Оптимізувати треба роботу за tick і готові дедлайни, зберігаючи heartbeat та швидку керовану паузу.

Discord визначає ліміти для bot token та ресурсних бакетів; їх слід читати з відповідей: [Rate Limits](https://docs.discord.com/developers/topics/rate-limits). Для member-подій і повного списку потрібна правильна конфігурація GUILD_MEMBERS: [Gateway](https://docs.discord.com/developers/events/gateway). Initial ACK має вкладатися у 3 секунди; interaction token має обмежений строк використання: [Receiving and Responding](https://docs.discord.com/developers/interactions/receiving-and-responding).

### Експлуатація

- Доповнити існуючі health/heartbeat показниками прострочених задач, затримки черги, конфліктів запису, частки 429 та незавершених операцій.
- Показувати сповіщення про проблему один раз на інцидент зі згортанням повторів.
- Провести відновлення бекапу в ізольовану БД та контроль структури/даних після restore.
- Оновити ARCHITECTURE.md: опис ACK до пересилання не відповідає поточному durable ingress, який зберігає receipt перед ACK.
- Узгодити опис production overlays і локального встановлення залежностей. Успішна production-збірка має два вже відомі попередження Turbopack щодо динамічного доступу до файлів welcome-card; перевірити tracing/пакування окремо.
- Серверну авторизацію зберігати в кожній мутації, а UI-приховування застосовувати як зручність: [Next.js Authentication](https://nextjs.org/docs/app/guides/authentication).

## 7. План реалізації та критерії переходу

Оцінки S/M/L відносні: S — одна локальна зона; M — кілька пов’язаних модулів; L — сховище/Discord/міграції та наскрізні перевірки. Це не календарний прогноз.

| Пакет | Обсяг | Залежність | Умова завершення |
|---|---|---|---|
| R1. Цілісність сховища — D01 | L | Перший | Реальний PG concurrency-suite; незалежні зміни й counters не губляться |
| R2. Надійна публікація — D03 | L | R1 | Паралельність, рестарт, збій після зовнішньої дії; одна відома публікація |
| R3. Каталог профілів — D02 | M | Контракт атомарних змін R1 | Пошук усієї вибірки, права, count і стабільна пагінація на великих наборах |
| R4. Кероване очищення — D06/D05 | M | R1 | Пауза приймається під час роботи; дедлайн; стан після невизначеного POST; строгий відбір збережений |
| R5. Чернетки редакторів — D04 | M | Контракт revision-конфлікту | Перемикання, вихід і повернення не стирають роботу |
| R6. Завершення існуючих сценаріїв | L, кількома невеликими релізами | R1–R5 | Профіль/нік, фільтри, контекстні дії, статуси й відновлення виміряні за сценаріями |
| R7. Дизайн і навантаження | M/L по модулю | Надійні дані й сценарії | Узгоджені стани, адаптивність, доступність; виміряні SQL/API/DOM без довільного збільшення частоти |
| R8. Нові можливості | Окремо на кожну | Стабільні R1–R7 | Підтверджена користь і власні критерії успіху |

Не об’єднувати всі R1–R7 у один великий реліз. Зміни сховища мають окремий відкат і перевірку сумісності; автоматизації — окремі контрольовані перемикачі.

Для кожного пакета: відтворення до виправлення → поведінковий тест → реалізація → відповідна регресія → перевірка сценарію у браузері/ізольованому середовищі. Не обмежуватися тестом на наявність рядка чи назви функції.

Перед застосуванням до робочої гільдії потрібні: резервна копія з перевіреним відновленням; перевірка конфігурації бота; звірка запису через Discord і сайт; restart-recovery; контрольоване випробування модерації в тестовій гільдії.

## 8. Нові можливості — після стабілізації

| Ідея | Користь | Оцінка | Як перевірити потребу |
|---|---|---|---|
| Супровід новачка й випробувальний термін | Наставник, стан підготовки профілю, наступний крок, результат випробування | M/L | Чи зменшились ручні нагадування офіцера; вимоги прийняття правил не змінювати |
| Персональний пульт у Discord «Мій стан» | Профіль, поточний запис, майбутні рейди й посилання на конкретну незавершену задачу | M | Чи зменшились переходи на сайт для простого перегляду; права ті самі, що в UI/API |
| Аналітика фактичної відвідуваності й ротації складу | Прозорі дані для рейд-лідера та резерву | L | Спочатку визначити джерело фактичної присутності; статус «Піду» не вважати фактом участі |

Це пропозиції нових наскрізних сценаріїв. Календарний ICS, повторні рейд-пули, масове додавання персонажів, базові нагадування, live-оновлення та on-demand прев’ю вже існують; їх розвиток належить до R6/R7.

Найближча рекомендована робота — R1: виправлення атомарності адаптера PostgreSQL і додавання поведінкових інтеграційних перевірок. Вона прибирає спільний ризик для подальших змін у багатьох модулях.

## 9. Технічні докази відтворень

Застосовано фактичні методи/функції джерел без зміни їхнього алгоритму. Для бібліотечних сценаріїв залежності замінені контрольованими реалізаціями; браузерні сценарії використовували фактичні компоненти з тестовими даними.

| Відтворення | Очікувана коректна поведінка | Отримано |
|---|---|---|
| D01, паралельні merge | New / male | Old / male |
| D01, два increment(1) | count=2 | count=1 |
| D02, 301 профіль, limit=500 | Доступ до всіх сторінок та Target250 | limit=200; Target250 → 0 результатів |
| D03, один draft, два запити | Одна контрольована публікація | Два create; messageId 1 затертий messageId 2 |
| D04, редагування → інша група → назад | Чернетка збережена | Початкове значення |
| D05, незавершений POST, +120 секунд | Дедлайн і відновлення керування/звірка | busy=true; кнопки disabled; немає помилки |
| D06, pause за зайнятого lease | Записана пауза для worker | Відмова до запису налаштувань |

Вихідний проєкт і переданий ZIP під час діагностики не змінювалися.
