# R6.6 — контекстна та масова обробка заявок

Версія dashboard: **3.8.82**, бот: **3.6.7**. Дата: 14.10.2026, Europe/Kyiv.
Основа — повний v3.8.81; попередні Host/Discord latency/performance виправлення збережені.

## Де зупинилися

Звірено вихідний DIAGNOSTYKA_ROADMAP_MISTBLOSSOM_2026-10-11 та IMPLEMENTATION_STATUS.
Останнім завершеним функціональним підетапом був **R6.5 / v3.8.78 — огляд трьох
автоматизацій**. Версії 3.8.79–3.8.81 були виправленнями й оптимізаціями.
R6.6 продовжує незавершений пункт R6 щодо заявок і часткових пакетних результатів.

## Що реалізовано

- Біля заявки на розгляді — явні «Прийняти» / «Відхилити». Вибір зі списку
  та окрема кнопка «Застосувати» більше не потрібні. Остаточне рішення не
  показується як збережене до підтвердження сервера.
- Після завершення є перехід до наступної доступної заявки в поточному порядку
  списку. Кнопка прокручує та переводить фокус до наступного рішення.
- Вибір лише поточних видимих заявок на розгляді; максимум 50. Підтвердження
  масової дії показує кількість і остаточне рішення. Завершені, зайняті та
  непевні заявки не включаються до нового пакета.
- Після пакета показуються окремі результати кожної заявки: змінено, вже
  розглянуто, Discord не підтверджено або результат непевний. Збережений статус
  може відрізнятися від запитаного, якщо інший модератор уже завершив заявку.
- Немає оптимістичного повернення старого статусу після втрати HTTP-відповіді.
  Дія отримує стан «не підтверджено» та кнопку звірки. POST має дедлайн 45 с,
  не повторюється автоматично; GET звірки має дедлайн 10 с.
- GET /api/applications/[number] читає тільки статус зі сховища: номер, статус,
  state й updatedAt. Потрібні сесія та applications.view; контакти, Discord
  references, історія модерації та інші поля не повертаються. GET не змінює
  заявку, не редагує повідомлення й не надсилає повідомлень Discord.
- Якщо GET підтвердив остаточний статус, показується саме він без твердження
  про доставку в Discord. Якщо заявка ще відкрита на розгляді, доступна нова
  явна дія; автоматичного повтору попереднього рішення немає.
- Видалення лишилося окремою дією власника з явним підтвердженням. Додано
  дедлайн; після непевного видалення повторна кнопка блокується до перевірки
  через оновлення списку.

R6.3 зберігає URL-фільтри, подання й позицію списку. Контекст вибору заявок не
зберігається як дозвіл на майбутню модерацію після зміни фільтрів/сесії.

## Захист остаточного рішення

Було недостатньо перевірити review через GET перед записом: два модератори
могли одночасно побачити старий стан. setIssueStatus тепер повторно читає
заявку й перевіряє review/open у транзакції, яку вимагають single/bulk routes
та Discord-модерація. Тільки переможець записує остаточний статус та event.
Другий виклик повертає actual status / alreadyModerated без повторних дій Discord.

Discord-виклики знаходяться поза транзакцією, після commit. Повтор SQL-транзакції
не повторює зовнішню дію. Суперечливі рішення однієї заявки в одному bulk-запиті
відхиляються до змін; однакові дублікати об’єднуються. Bulk зберігає чинний
обмежений паралелізм, авторизацію, CSRF/origin, rate limit та аудит.

Якщо збереження рішення підтверджено, а Discord не відповів, результат є
частковим, а не «статус не змінено». Аудит записує фактичний статус, факт
зміни/пропуску та підтвердження Discord; непевна помилка не видається за rollback.

## Межі

R6.6 не додає нової збереженої outbox-операції для Discord-сповіщень заявок.
Якщо після commit процес перервався, звірка статусу підтвердить рішення,
але не доведе доставку повідомлення. Для синхронізації не треба повторно
приймати/відхиляти заявку. Розширення діагностики й відновлення публікацій
залишається окремим наступним пакетом.

Правила прийняття гільдії/Статика, доступи наставника та дизайн журналу не
перероблялися. Сам факт прийняття заявки не означає автоматичне прийняття
правил або надання Discord-ролей.

## Оновлення

Резервна копія поточного коду; вміст guild_header_work розпакувати в корінь
проєкту, зберігши свої .env/.env.production. Оновити всі процеси dashboard
узгоджено, щоб старі екземпляри не обробляли рішення за старою семантикою.

```sh
docker compose build dashboard
docker compose up -d --no-deps --force-recreate dashboard
docker compose ps
docker compose logs --since=5m dashboard bot cron
```

SQL-міграції та нової cron-задачі немає. Бот не змінений від v3.6.7. Якщо
попередні v3.8.79/v3.8.80 ще не встановлені, застосувати також їхні наявні
інструкції для bot/cron; усі потрібні файли є в повному архіві.

На VPS цей реліз не встановлювався. Формат документів сумісний, але відкат
коду поверне попередню семантику захисту рішень. Усі оновлені moderation routes
мають працювати на тій самій версії.
