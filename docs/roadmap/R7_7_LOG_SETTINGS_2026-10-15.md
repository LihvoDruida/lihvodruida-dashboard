# R7.7 — налаштування журналу та Security mirror

Dashboard **3.8.103**, bot **3.6.9**, shared contract **1.1.1**. 15.10.2026.

Завершено обмежений пакет для блоку «Зберігання та Security mirror» на `/dashboard/logs`. Дизайн сторінки журналу, таблиця, фільтри, експорт і retention у 3 дні збережені. Правила прийняття та відеофон із 3.8.102 входять до повного архіву без змін.

## Відтворені проблеми

Оригінальний компонент із 3.8.102 перевірено окремим baseline-стендом. Шість браузерних проб підтвердили такі дефекти:

| Випадок | Попередня поведінка | Нова поведінка |
|---|---|---|
| Перемикання mirror без збереження | Індикатор уже заявляє новий стан | Індикатор показує збережений стан; чернетка позначена окремо |
| HTTP 200 з `ok: "true"` | Повідомлення про успішне збереження | Невірне підтвердження; одне GET-звіряння без повтору POST |
| Тестова відправка ще триває | Канал і збереження залишаються доступними | Одна дія за раз, поля блокуються до результату |
| Неправдивий truthy-відгук тесту | Повідомлення про успішну доставку | Потрібна явна квитанція для збереженого каналу |
| Збереження з клавіатури | Лише toast, без сталого результату й відновлення фокуса; RSC refresh | Постійний status, керований фокус; без повного оновлення сторінки |
| Чернетка містить інший канал | Тест непомітно використовує старий канал | Тест доступний після збереження поточного вибору |

Додатково виправлено серверний тест: його рівень тепер відповідає збереженому порогу. Раніше Warning не проходив при налаштуванні «Тільки Error». При візуальній перевірці також знайдено конфлікт CSS: глобальна галочка checkbox деформувала повзунок mirror. Локальні правила тепер зберігають круглу ручку в обох станах і поважають reduced motion.

## Збереження, читання та чернетка

Форма відокремлює збережені значення від чернетки. Порожній числовий input залишається порожнім під час редагування, а не перетворюється на 0. Діють серверні межі: 32–1024 МБ, 5 000–250 000 записів, 50–500 рядків браузера. Некоректний стан не відправляється; валідація повторюється в API.

Успіх підтверджує тільки `ok === true`, коректний обʼєкт налаштувань із джерелом `database` та збіг усіх змінюваних полів. Власник може змінювати ліміти; адміністратор без прав власника змінює лише mirror. POST адміністраторів не призначає колонки бюджетів у SQL `ON CONFLICT DO UPDATE`, тому паралельне збереження власника не затирається старими значеннями цих колонок.

GET `/api/dashboard/logs/settings` перевіряє чинний доступ до журналу, повертає свіжий стан, доступність PostgreSQL і права редагування, із `no-store`. Строге читання не підміняє помилку БД типовими значеннями ENV. Помилка початкового серверного читання показує непідтверджений стан і блокує запис/тест до успішної перевірки. Неконфігурований PostgreSQL також не дає записувати або тестувати.

За неоднозначної відповіді збереження виконується одне GET-звіряння, без повторного POST. Це стосується і HTTP 400: аудит записується після налаштувань, тому його помилка може повернути 400 вже після зміни конфігурації. При збігу GET показує саме відповідність збережених значень; завершення аудиту цим не доводиться. При невідповідності чернетка зберігається. Якщо GET теж недоступний, нове збереження блокується до успішного ручного перечитування. Явні відмови 401/403/413/415/422/428/429 не повторюються й не запускають recovery.

Ручне перечитування та нові серверні props не стирають незбережений вибір. Зміна прав під час запиту залишається чинною після його завершення. Поля позначено `data-dirty`, запити — `data-submitting`/`aria-busy`; це дозволяє наявним live-refresh guards відкласти фонове оновлення. Чернетка живе у змонтованому компоненті, без нового сховища для reload.

## Тестова відправка та журналювання

Тест виконується тільки після явного натискання, за збереженою конфігурацією. Усі перевірки цього релізу використовували контрольовані відповіді, без надсилання повідомлень у живий Discord.

Сервер перевіряє права й CSRF, обмежує тест до 3 запитів за хвилину на адміністратора/IP та читає конфігурацію свіжою один раз. Та сама конфігурація визначає рівень події й канал відправки. Звичайне дзеркало зберігає кеш коректних налаштувань на 10 секунд; за помилки читання PostgreSQL воно не перемикається на ENV defaults.

Вихідний запит Discord має дедлайн 8 секунд. Автоматичного повтору POST немає. HTTP 2xx сам по собі не доводить доставку: відповідь Discord мусить містити ID повідомлення та потрібний `channel_id`. HTML, інший канал, відсутня квитанція або втрачена відповідь позначаються як непідтверджена доставка. Клієнт також перевіряє ID повідомлення та збіг збереженого каналу. При невизначеності пропонується перевірити Discord перед новим ручним натисканням. Відомі відмови доступу/конфігурації показують конкретну причину.

Секрети маскуються перед форматуванням і обрізанням тексту, включно з діагностикою сховища й помилками Discord. Збережено вимкнені mentions, антиспам-дедуплікацію, відсікання routine signature probes і правило: поза VPS дублюється тільки категорія Security. Локальний запис тесту містить результат, канал і ID підтвердженого повідомлення.

## Доступність і виміряна робота

Постійні `role=status` мають live announcement, `aria-atomic` та керований фокус. Фокус після явної дії переходить на результат, якщо користувач не перемістив його самостійно. Демонтаж скасовує запити; пізня відповідь не змінює компонент. Усі дії взаємно блокуються.

Клієнтські межі: GET — 12 секунд під загальною межею 15; save POST — 20 секунд під загальною межею 40 для POST і звіряння; test POST — 12 секунд під межею 15. У timeout-сценаріях тільки тестові таймери 12/20 секунд прискорено до 150 мс; production-дедлайни не змінені.

Виміряні операції на стенді:

- Старий явний save викликав 1 `router.refresh`, новий — 0. Ця дія не запускає повного RSC-оновлення журналу.
- 100 послідовних редагувань channel ID: 0 GET, 0 POST, 0 тестових відправок, 0 RSC refresh; останній введений ID збережено.
- Неоднозначний save: 1 POST + 1 GET, без автоматичного повтору запису.
- Перевірено девʼять ширин від 320 до 1920 px, обидва положення перемикача та керування клавіатурою. Це контрольовані лічильники й геометрія, без заяв про production latency або FPS.

## Перевірки та межі

`check:log-settings` додано до `build:ci` і `verify`; браузерна перевірка залишається окремою й потребує Playwright, esbuild та Chromium. Production-залежностей не додано. Браузерний стенд запускає production React, чинний компонент і глобальні/module CSS; мережеві відповіді контрольовані. Це не приймання живого SQL чи Discord. Baseline можна повторити через `MISTBLOSSOM_TEST_LOG_SETTINGS_SOURCE` із попереднім компонентом.

Фінальні результати, сценарії й склад змін — у [R7_7_VALIDATION_2026-10-15.json](R7_7_VALIDATION_2026-10-15.json).

Схему БД, бот, cron і shared contract не змінено. Пакет не додає атомарності налаштувань разом з аудитом або захисту від одночасних змін mirror двома адміністраторами. Живі PostgreSQL/Discord, Docker/VPS та робота з NVDA/TalkBack не перевірені. R6 залишається відкритим до живого приймання; інші форми керування та решта R7 — наступні окремі пакети.
