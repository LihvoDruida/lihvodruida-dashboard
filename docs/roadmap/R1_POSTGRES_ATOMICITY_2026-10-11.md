# R1 — атомарність PostgreSQL

Реліз сайту **3.8.69**, 11.10.2026. Бот залишається 3.6.6. Підстава:
пакет R1 / дефект D01 з нового документа діагностики. Це окреме оновлення
сховища; R2–R8 залишаються наступними пакетами, як передбачено планом.

## Що виправлено

Раніше прямі merge/update читали JSON та записували його незалежними запитами.
Дві паралельні зміни могли повернути старе значення чужого поля. Тепер повний
цикл зміни одного документа відбувається на одному з'єднанні в транзакції.

- Прямі set/merge/update/create/delete беруть transaction-scoped advisory lock
  за парою collection/doc_id. Це захищає й створення відсутнього документа
  та працює між процесами; локального mutex немає.
- Прямі зміни використовують READ COMMITTED та читають після отримання lock.
  Merge/update додатково блокують існуючий рядок через FOR UPDATE.
- Update виконує UPDATE, а не UPSERT: відсутній або видалений документ
  спричиняє помилку й не створюється заново.
- Create використовує INSERT ON CONFLICT DO NOTHING та перевіряє результат.
  Лише один конкурентний create успішний; інші не перезаписують переможця.
- Batch/runTransaction зберігають спільний client, порядок відкладених записів
  та REPEATABLE READ. Конфлікт 40001 або deadlock 40P01 повторює всю
  транзакцію з обмеженим бюджетом; пакет відкочується цілком.
- З'єднання звільняється перед backoff. Після останньої спроби немає зайвої
  затримки. Звичайні помилки, lock timeout та невизначений обрив з'єднання
  автоматично не повторюються.

Формат documents, індекси, JSON, ідентифікатори, читання та Firestore fallback
не змінюються. Міграція схеми не потрібна. Full set зберігає значення явної
заміни документа; update вкладеної map замінює її, dotted update змінює поле.

Блокування живуть лише до commit/rollback. Складні транзакційні callbacks
мають містити лише роботу з БД: Discord HTTP та інші зовнішні дії виконуються
після успішного commit. Повторювати зовнішню дію всередині callback не можна.
Надійна публікація належить до R2.

## Перевірки

На справжньому локальному **PostgreSQL 16.15** старий адаптер відтворив D01:
preferredName повернувся до Old після паралельного збереження gender.
Оновлений адаптер пройшов **23/23** інтеграційні сценарії, включно з:

- 32 паралельними merge/update increment; результат рівно 32;
- 24 merge у новий документ, вкладеними змінами, delete та arrayUnion;
- видаленням рядка, поки update чекає на його блокування;
- прямим та транзакційним create-конфліктом;
- повтором stale snapshot, відкатом batch і реальним PostgreSQL deadlock;
- контрактами set/update, Timestamp, getAll, query та підколекціями;
- 48 приростами з двох незалежних процесів Node.

Ще **7/7** перевірок з ін'єкцією помилок перевіряють бюджет повторів,
COMMIT-конфлікт, класи помилок і release перед очікуванням.
Вони включені до verify та build:ci й не потребують запущеної БД.

Загальна verify (TypeScript, ESLint, регресії) успішна; тести бота — 45/45.
Production build:ci успішна на всіх 23 входах Docker builder. Next-збірка
тривала 31 секунду. Збереглися два попередні попередження Turbopack про
динамічне читання файлів discordWelcomeCard.ts; до R1 цей модуль не змінювався.

Integration-suite завантажує фактичні TypeScript-модулі адаптера й пулу,
використовує справжній pg та SQL, а не замінник PostgreSQL. Кожен запуск
створює випадкову окрему schema, застосовує штатну schema.sql та видаляє
лише власну schema. TEST_DATABASE_URL обов'язковий; підстановки робочого
DATABASE_URL за замовчуванням немає.

Докази локального запуску — R1_VALIDATION_2026-10-11.json поруч.
Робочий VPS, Discord та production-база під час перевірки не змінювалися.
Production Compose використовує PostgreSQL 17.11; цей Docker-стек тут
не запускався. Для перевірки саме його образу додано runner:

~~~bash
cd dashboard
npm run check:pg-transactions
npm run test:db:docker
~~~

Runner створює й видаляє тимчасовий контейнер postgres:17.11-alpine
без volumes, із випадковим паролем та портом лише на 127.0.0.1.
Не використовує production Compose. Потрібні Node 24, встановлені
залежності dashboard та доступний Docker daemon.

Якщо вже є окрема тестова БД:

~~~bash
TEST_DATABASE_URL='postgresql://test:password@127.0.0.1:5432/mistblossom_test' \
  npm run test:db
~~~

Локально PostgreSQL працював як окремий тимчасовий native process у sandbox
із єдиним UID; лабораторний shim обійшов лише перевірку UID під час старту.
SQL engine та locks не підмінялися. Shim не входить до проєкту та не потрібен
Docker runner.

## Застосування та відкат

1. Зберегти попередній образ dashboard та перевірений резервний backup БД.
2. Виконати integration-suite на окремій БД з production-версією PostgreSQL.
3. Призупинити cron і бот та зупинити всі старі dashboard workers перед
   перемиканням. Старий адаптер не бере нові advisory locks, тому змішаний
   запис старими й новими workers не має нової гарантії атомарності.
4. Зібрати й запустити оновлений dashboard штатним процесом розгортання,
   перевірити читання/збереження профілю й журнал, потім відновити бот і cron.
5. Контролювати lock timeout/serialization failures та затримки записів.
   Блокування обмежені чинними DATABASE_LOCK_TIMEOUT_MS і
   DATABASE_STATEMENT_TIMEOUT_MS; помилка повертається виклику явно.

Відкат — повернення попереднього образу/коду dashboard після зупинки нових
workers. Перетворення даних і зворотної міграції немає; старі читачі сумісні
з поточним JSON. Старий адаптер повертає ризик D01, тому відкат — аварійний
засіб, а не режим змішаного запису. Не перемикати DATABASE_URL на Firestore
заради відкату R1: без міграції це інше, потенційно неактуальне сховище.

Палітра, фон, сторінка логування й прийняття правил залишаються в наданій
версії. Нові модулі та перероблення UI до R1 не входять.

Підстава для блокувань:
[PostgreSQL 17 — Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html),
[Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html).
