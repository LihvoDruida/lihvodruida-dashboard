# R5 — чернетки груп і контроль паралельних змін

Dashboard **3.8.73**; бот **3.6.6**. Закрито D04 з погодженого документа пропозицій. Повний архів продовжує R4; на робочий VPS ці зміни не встановлено.

## Поведінка редактора

- Кожна група має окрему керовану чернетку: ID, назва, системна роль, ранг, іконка, Discord role ID і всі прапорці прав. Перемикання груп, пошук і «Показати ще» не скидають поля.
- Незбережені зміни позначені в редакторі й списку. «Скинути чернетку» потребує підтвердження, якщо є зміни, і стосується лише вибраної групи.
- Повернення та перезавантаження відновлюють чернетки у тому самому браузері. Ключ відокремлений за сервером і акаунтом. Різні вкладки мають окремі копії; дублювання вкладки з копією sessionStorage також перевіряє власника копії через BroadcastChannel. Іншу версію можна відновити тільки явно.
- Чернетка не записує права на сервер. Єдиний запис — явне «Зберегти зміни» або «Створити групу». Після підтвердження очищається лише збережена чернетка.
- Якщо групу змінили чи видалили, редактор зберігає локальні поля й блокує старий запис. Таблиця показує серверні та локальні значення, включно зі змінами окремих прав. Можна відмовитися від чернетки або підготувати її до нового явного збереження. Видалена група не відтворюється автоматично.
- Помилки відновлення, заблоковане сховище й перевищення квоти показуються користувачу. Пошкоджені дані автоматично не видаляються. За недоступного сховища поля залишаються в пам’яті до закриття сторінки. Межа копії — 100 чернеток / 131072 символи JSON; перевищення не спричиняє тихого видалення старих змін.

## Контракт сервера

`revision` — SHA-256 канонічного сирого документа. Це працює і для старих записів без поля версії. Новий запис отримує UUID покоління, тому повторне створення того самого ID не приймає стару ревізію.

Редагування й видалення вимагають `expectedRevision`. Відсутня передумова повертає **428**, змінена група — **409**. Створення явно передає `null` і вимагає відсутнього ID. Системні ID 1, 2, 3, 99 не можна створити поверх наявних або перейменувати.

Група, призначення Discord-ролі, зміна ID та документ `dashboardSettings/accessGroupsWriteGuard` записуються однією транзакцією. Поточні права адміністратора повторно читаються у цій транзакції. Відкликані права в базі блокують запис навіть зі старою сесією.

PgFirestore підтримує читання документа у транзакції, але не запиту колекції. Тому каталог читається після його контрольного документа; транзакція приймає цей каталог тільки якщо покоління не змінилося. Усі три шляхи запису — збереження, видалення й забезпечення системних груп — оновлюють контрольний документ. При конкуренції каталог перечитується до чотирьох разів. Повтор SQL-транзакції не є повтором HTTP-запиту чи зовнішньої дії.

Редактор і його GET читають актуальну базу без підміни кешованими/типовими правами. За недоступної бази показується помилка. Старий кеш для інших існуючих сценаріїв авторизації збережено.

Новий `/api/dashboard/access-groups` має перевірку сесії/прав, strict Origin/Referer, обмеження частоти, no-store та перевірку JSON до 8192 байт, включно з потоковим тілом без Content-Length. Помилка журналу після вже виконаного запису не змінює відповідь на «запис не виконано».

## Втрата відповіді та відновлення

POST не повторюється автоматично. Перед явним збереженням у чернетці фіксується UUID операції; сервер повертає й зберігає `lastMutationId`. Після тайм-ауту робиться тільки GET. Точний receipt підтверджує попередній запис; наступне введення не очищається старою відповіддю. Розмонтування скасовує локальний запит, але receipt дозволяє підтвердити серверний результат після повернення.

GET обмежений 12 секундами, POST — 20, уся операція з перевіркою результату — 35. Непідтверджений результат залишає чернетку. Видалення не повторюється після втрати відповіді; свіжий список показує, чи група ще існує.

## Сумісність і оновлення

SQL-міграції та нової таблиці немає; службовий документ і поля створюються автоматично. Оновити треба всі dashboard-інстанси, які змінюють групи: R4 не знає контрольного документа й revision-контракту. Не залишати змішані старі/нові writers. Після оновлення відкрити редактор заново; стара форма без ревізії буде відхилена.

Зміна ID тепер атомарна, але, як і раніше, **не переносить ручні призначення профілів** на інший ID. Редактор прямо попереджає про це перед перейменуванням. Перенесення таких посилань потребує окремого контрольованого сценарію; це пункт перевірки R6, а не виконана міграція цього релізу.

При відкаті закрити редактори, зупинити нові dashboard writers і відновити попередній код. Нові поля сумісні зі старим читанням; видаляти контрольний документ не потрібно. R4 знову дозволяє старий запис без перевірки ревізії, тому відкат повертає цей відомий ризик.

## Перевірки

- 21 сценарій реального PostgreSQL 16.15: втрачений запис R4 відтворено; CAS, конкурентне створення, унікальна роль, незалежні зміни, видалення/повторне створення, відкат перейменування, відкликання прав і забезпечення системних груп.
- 7 сценаріїв моделі чернеток: відновлення всіх полів, безпечні ключі, підтвердження лише своєї операції, збереження пізнішого введення, некоректні дані.
- 10 перевірок справжнього API-модуля з ін’єкцією сесії/БД та справжнім strict origin helper: авторизація, CSRF, потоковий ліміт, тип/формат тіла, 409, no-store, журнал і rate limit. Конкурентність сховища окремо перевіряє PostgreSQL-серія.
- 20 сценаріїв Chromium на справжньому компоненті, з локальним HTTP-каталогом: R4-дефект, усі поля/права, повернення, дві вкладки та скопійована ідентичність, конфлікт, втрата відповіді, reload під час запису, тайм-аут GET, видалена група, квота/пошкоджені дані. Перевірено також передачу прихованого ID для «Переглянути як» і явне видалення з невалідними локальними полями. 9 ширин 320–1920 px без горизонтального переповнення; 0 помилок JavaScript.
- Регресії R1/R2/R3/R4: 23 + 26 + 32 + 11 реальних PostgreSQL сценаріїв. Бот: 45 тестів.
- `build:ci`, TypeScript, перевірки форм/безпеки/імпортів, CSS/UI-аудити та inspect:ci пройшли. Виробнича збірка — 11 секунд; збережено два попередні попередження трасування `discordWelcomeCard.ts` (273/487). Вхідні файли 23 Docker COPY звірено з джерелом: 561 файл, 0 відмінностей. Зібраний standalone повертає 401 для GET/POST нового API без сесії, 303 на login для редактора, 403 для недовіреного Origin. Докладні результати — `R5_VALIDATION_2026-10-11.json`.

Немає живих виключень учасників, публікацій Discord або перевірки доступу реальним токеном. Native PostgreSQL у QA використовує локальний UID shim через обмеження тестового контейнера; він не входить до архіву. Контейнерний runner доповнено R5, але Docker у цьому середовищі не запускався. Кольорові токени, фонові зображення, прийняття правил і сторінка логування збережені.
