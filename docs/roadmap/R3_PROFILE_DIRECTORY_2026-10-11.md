# R3 — повний каталог профілів, v3.8.71

Дата: 11.10.2026. Основа: повний архів R2 v3.8.70; бот залишається v3.6.6.

## Що виправлено

У D02 сторінка запитувала 500 профілів, бібліотека повертала максимум 200, а пошук, фільтри, сортування й показники працювали лише з цією порцією. Наявний Target250 не знаходився. Підвищення цього ліміту не усувало дефект.

Тепер `/profiles` використовує `listDashboardProfilePage` із `profileDirectory.ts`. PostgreSQL застосовує поточні групи й права, пошук, роль та стан Battle.net до LIMIT. Сторінка отримує до 20 повних профілів. Загальна кількість, кількість персонажів і підключень Battle.net рахуються для всієї доступної відфільтрованої вибірки, в одному SQL-запиті й з одним MVCC-знімком.

Пошук знаходить імʼя профілю, Discord-імʼя/login/ID, персонажів та реалми. Канонічні назви персонажів із `guildCharacterData` мають пріоритет над `externalCharacterData` і збереженою копією. Записи персонажів з невалідними ключами не рахуються; старі ключі з четвертим сегментом та Unicode нормалізуються перед дедуплікацією й канонічним пошуком. Імена груп і чинна роль відображаються з того ж набору груп, який визначив доступ.

Сортування виконується для всієї вибірки: активність; імʼя профілю; кількість персонажів із додатковим порядком за активністю. Кожний порядок завершується унікальним `doc_id`. Для імен використовується українська ICU-колація, якщо вона наявна; мінімальна інсталяція без неї використовує стабільний порядок `C`. Точність підрахунків не залежить від наявності ICU.

## Навігація й помилки

- «Назад» і «Далі» використовують курсори, зберігають пошук/роль/Battle.net/сортування в URL. Нова форма пошуку починає з першої сторінки. Показується фактична позиція `1–20 із N`, без фіктивного поділу обрізаного списку.
- Курсор привʼязаний до фільтрів, користувача, його прав, рангу, поточних груп і способу сортування. Він не надає прав: SQL завжди повторно застосовує доступ. Курсор містить тільки граничний ключ уже доступного профілю; секрети й токени в нього не потрапляють.
- Невалідний/застарілий курсор або порожній перехід після зміни каталогу повертає першу актуальну сторінку з повідомленням. Видалення граничного запису не заважає переходу, бо курсор містить його значення, а не вимагає наявності документа.
- Помилка читання БД/джерела груп не маскується кешованим порожнім результатом. Неналаштоване сховище має явний стан «Каталог недоступний».
- Firestore збережений для міграційної сумісності: повний послідовний перегляд порціями по 100, підрахунок усіх дозволених збігів, у памʼяті зберігається лише поточна порція та 20 кандидатів сторінки. Це повний пошук, але він потребує O(N) читань на запит; PostgreSQL є основним режимом.

Попередній недоступний після 200 записів метод `listDashboardProfiles` прибрано: єдиного його споживача переведено на новий контракт. Нормалізація, перевірки прав і груп для сторінки профілю лишаються спільними. Канонічна гідратація тепер обробляє всі ключі порціями по 600, не обриваючи великі набори на першій порції.

## Перевірки

| Перевірка | Результат |
|---|---|
| `test:profiles`, справжній PostgreSQL 16.15 | 32/32; набори 201/501/2000, пошук пізніх записів, проходження всіх 2000 у трьох порядках, зворотна навігація, права й агрегати, канонічні дані, Unicode/старі ключі, невалідні дати, зміна прав і видалення |
| `check:profile-directory`, фактичні функції з контрольованою Firestore-межою | 7/7; входить у `verify` і `build:ci` |
| Сторінка й навігація в Chromium | 320/390/768/1280 px, без горизонтального переповнення; справжні `ProfilesPage`, каталог і `ProfileAvatar`, контрольовані сесія та сховище |
| Пошук/форми/URL у браузері | Target250, фільтри при переходах, новий пошук без старого курсора, різні стани порожнього результату/недоступності, перенаправлення без сесії |

SQL перевірявся через EXPLAIN ANALYZE на тестових профілях. Матеріалізація проміжних сегментів прибрала повторну нормалізацію кожного ключа персонажа: на цьому локальному наборі p50 запиту зменшився приблизно з 339 до 104 мс; фінальний p95 — близько 176 мс. Окремий EXPLAIN пошуку — близько 199 мс. Це вимірювання тестового середовища, не гарантія швидкості VPS. Нові індекси не додано: основні витрати тут були у повторній обробці JSON, а пошук канонічних документів і читання сторінки використовують наявний `(collection, doc_id)`.

Інтеграційна серія створює випадкову приватну SQL-схему, відмовляється від production URL і прибирає тестові дані після завершення. У sandbox PostgreSQL 16.15 запущено на loopback з локальною адаптацією перевірки UID під час старту; SQL-двигун і запити не підмінені. Одноразовий Docker-раннер тепер включає R1/R2/R3 серії на PostgreSQL 17.11, але Docker тут не запускався. Firestore SDK/живі Discord-запити й production дані не використовувалися.

Підсумок збірки, регресійних перевірок і обмеження середовища: [R3_VALIDATION_2026-10-11.json](./R3_VALIDATION_2026-10-11.json).

## Запуск і відкат

SQL-міграція для R3 не потрібна. PostgreSQL 16+ підтримує використані функції; Compose проєкту вже використовує PostgreSQL 17. Перед оновленням залишається чинним порядок R2: [журнал публікацій і відкат](./R2_DISCORD_PUBLICATION_2026-10-11.md). Не очищайте `discordPublications` та не повертайте старі publisher-процеси поверх незавершених операцій.

```bash
cd dashboard
npm run verify
TEST_DATABASE_URL=postgresql://test:password@127.0.0.1:5432/mistblossom_test npm run test:profiles
# Або всі три SQL-серії в ізольованому контейнері:
npm run test:db:docker
npm run build:ci
```

Курсори попередньої версії/змінених прав безпечно скидаються. Старі посилання з `page=N` відкривають першу сторінку; нові посилання містять `cursor`. Навігація не є замороженим знімком між HTTP-запитами: якщо профіль змінює ключ сортування під час перегляду, позиція може змінитися. Для незмінного набору перевірено відсутність дублів і пропусків. Для експорту зі знімком потрібен окремий контракт — він не входить у R3.

Системні теплі кольори, фон, дизайн логування та прийняття правил не змінювалися. На VPS нічого не розгорнуто. R1–R3 завершені в коді; R4–R8 залишаються наступними пакетами. Наступний — R4: узгоджена пауза очищення та перевірка дедлайну під lease.
