# R6.1 — імʼя та Discord-нік за одне підтвердження

Dashboard **3.8.74**; бот **3.6.6**. Це перший окремий реліз R6 після R5, а не завершення всього пакета R6. На VPS не встановлено; реальні учасники, повідомлення та робоча база не змінювались.

## Сценарій користувача

У налаштуваннях власного профілю кнопка **«Зберегти й синхронізувати»** одночасно зберігає імʼя та створює фонове завдання. Браузерне порівняння справжніх компонентів R5/R6.1 підтвердило ціль дорожньої карти: два окремі підтвердження → одне. Введення, відкриття сторінки та читання стану не змінюють нік.

Картка показує оригінальне імʼя Discord, відомий серверний нік, підготовлений формат, чергу, виконання, результат або причину зупинки. Після успіху показується останній підтверджений нік; якщо персонажі змінили підготовлений формат, можна застосувати його явно. Власник сервера отримує збережене імʼя й кнопку копіювання; автоматичного PATCH для нього немає. Інші провайдери зберігають імʼя без Discord-задачі.

Чернетка й UUID незавершеного збереження живуть у sessionStorage окремо за профілем: перехід, повернення та перезавантаження тієї самої вкладки відновлюють поля. Новіше введення не стирається пізнішою відповіддю. Закриття вкладки може видалити її локальну чернетку; уже збережена серверна задача залишається. Пошкоджена копія не перезаписується мовчки; за недоступного сховища діє памʼять до закриття сторінки.

Зміна в іншій вкладці потребує перегляду та нового явного збереження. Якщо відповідь POST загубилась, клієнт виконує тільки GET. Збіг receipt перевіряється разом із ревізією: наступна зміна старим endpoint не може очистити чернетку лише тому, що зберігся UUID попередньої дії. Непідтверджений результат блокує новий запис до явного перегляду.

GET має дедлайн 12 с, POST — 20 с, POST + перевірка — 35 с. Після виходу локальний запит скасовується. Статуси активної задачі читаються з БД до 12 разів за видимої вкладки; повторний перегляд доступний кнопкою. Браузерний GET не звертається до Discord.

## Атомарність і виконання

`/api/profile/identity` працює тільки з profileId перевіреної власної сесії; переданий клієнтом ID не використовується. Режим impersonation відхиляється. POST має strict Origin/Referer, 20 спроб/10 хвилин, потоковий ліміт 2048 байт, перевірку форми JSON та no-store.

Збереження вимагає SHA-256 expectedRevision і UUID v4 operationId. Ревізія включає імʼя, UUID покоління та ідентичність провайдера. Імʼя + покоління + запис `profileNicknameSyncJobs/{profileId}` створюються однією транзакцією. Відсутній профіль не створюється частково. Інші поля профілю зберігаються. Відсутня ревізія — 428; конкурентна зміна — 409. Повтор точної дії читає receipt, але не створює нову задачу; UUID з іншим payload відхиляється.

Задача має lease 120 с. Discord-дія виконується після SQL-транзакції. Перед PATCH, після всіх очікувань REST-лімітера, повторно перевіряються lease, профіль, його провайдер, сервер і підготовлений нік. Зміна джерела зупиняє стару дію. Активний lease не дозволяє замінити завдання іншою операцією.

Виконання починається через Next.js after() після відповіді. Надійний fallback — незалежний worker `/api/dashboard/discord/profile-nicknames/automation` щохвилини. Він читає тільки готову чергу (до трьох профілів за tick), а не склад сервера; порожня черга робить **нуль Discord-запитів**. Важка перевірка ніків і попередження залишаються на старому 15-хвилинному розкладі. Повторні GET/перевірки користувача не створюють новий intent.

Для PATCH використовується чинний REST-клієнт і `retry: "never"`. Ознака dispatched записується перед відправленням. Після мережевої невизначеності, 5xx або рестарту вже відправлена операція звіряється через GET, без нового PATCH. Точний збіг підтверджує результат; розбіжність дає uncertain. Збережений початковий target використовується для receipt навіть якщо список персонажів змінили після відправлення.

Отриманий 429 означає відмову у PATCH: завдання чекає не менше server retryAfterMs і свого backoff. Недоступне читання до відправлення також має обмежені повтори; після пʼятої спроби автоматичні повтори припиняються. 403, відсутній учасник і неправильна конфігурація мають окремі причини. Помилка журналу/реєстрації after() не перетворює вже збережене імʼя на помилково заявлений невиконаний запис.

«Звірити Discord» повторює лише перевірку uncertain; «Повторити синхронізацію» — новий явний intent. Для uncertain перед новою зміною є підтвердження, що поточний нік може бути замінений. Це не гарантія глобального exactly-once: Discord не надає CAS для ніків, а зовнішній модератор може змінити їх між нашим читанням і відправленням.

Підстави API: [Modify Guild Member](https://docs.discord.com/developers/resources/guild#modify-guild-member), [Permission Hierarchy](https://docs.discord.com/developers/topics/permissions#permission-hierarchy), [Rate Limits](https://docs.discord.com/developers/topics/rate-limits). Новий код користується існуючим транспортом; токени, права та розклад повних сканів не розширено.

## Сумісність, запуск і відкат

SQL-міграції немає: колекція завдань та поле identityRevision створюються у чинному document store. Оновити dashboard і контейнер cron разом; старий cron не знає новий endpoint. За відсутності cron after() зазвичай почне задачу, але сам по собі не забезпечує відновлення після аварійного завершення процесу.

Старі endpoints імені та ніку залишаються для чинного прийняття правил; їхні форми та перевірки не змінені. Зміна імені старим шляхом робить ревізію задачі неактуальною. Сторінки правил і логування, бурштинові токени, фонові ресурси та код бота збережені. Новий клієнт завантажується окремим dynamic import лише для увімкненого редактора налаштувань.

Перед відкатом завершити або зафіксувати невизначені задачі, зупинити новий worker і dashboard writers; потім повернути R5. Збережені завдання сумісні як додаткові дані, але старий код їх не виконує. Ніки, які Discord уже змінив, відкат коду не повертає автоматично.

## Перевірки

- Справжній PostgreSQL 16.15: **30 сценаріїв**, включно з SQL fault і відкатом обох записів, конкурентними збереженнями/workers, ABA, lease, зміною провайдера/персонажів перед відправленням, 429, receipt після рестарту та нульовим Discord I/O у спокої. Повторюваний runner: `npm run test:identity` з ізольованим TEST_DATABASE_URL.
- Справжній API-модуль з перевіркою Origin та контрольованими сесією/сховищем: **11 сценаріїв**, `npm run check:profile-identity`; включений у verify/build:ci.
- Chromium: **20 сценаріїв**, 9 ширин 320–1920 px, нуль помилок JavaScript. HTTP-замінник дозволяє перевіряти втрату відповіді та конфлікти без робочих токенів. Legacy-форму правил перевірено саме з R6.1-компонента, без увімкнення нового редактора.
- PostgreSQL-регресії R1–R5: **23 + 26 + 32 + 11 + 21**. Бот: 45/45. `build:ci`, TypeScript, ESLint, усі функціональні/захисні перевірки та CSS/UI-аудити пройшли; inspect:ci: 445 файлів, 0 blocking issues. Залишились два попередні tracing warnings у незміненому discordWelcomeCard.ts. Зібраний standalone: 5 перевірок auth/Origin; вхід 23 Docker COPY звірено побайтово: 571 файл, 0 відмінностей. Підсумок: `R6_1_VALIDATION_2026-10-11.json`.

Перевірки не включають живі Discord-акаунти, Docker engine, бойову базу, Developer Portal чи deploy на VPS. Native PostgreSQL у QA використовує ізольований UID shim через обмеження середовища; він не входить до проєкту. Docker runner доповнено новою серією, але контейнерний запуск тут не заявляється виконаним.

## Наступні частини R6

Окремо залишаються персонажі → мейн/роль в одному підсумковому кроці; збереження фільтрів та повернення до списків; контекстні дії й часткові результати; інші статуси автоматизацій. Безпечне перенесення ручних групових призначень при зміні ID групи також ще не реалізоване. R7/R8 не позначено завершеними.
