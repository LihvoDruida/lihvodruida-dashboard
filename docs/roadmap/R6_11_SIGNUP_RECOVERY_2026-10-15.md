# R6.11 — контрольна діагностика та відновлення запису

Dashboard **3.8.92**, bot **3.6.9**, контракт **1.1.1**. База — повний пакет 3.8.91. Перевірено 15.10.2026.

## Підтверджені дефекти

На реальному компоненті 3.8.91 в ізольованому Chromium відтворено:

| Сценарій | До виправлення | У 3.8.92 |
|---|---|---|
| У формі вибрано другого персонажа, батьківські дані оновились новим масивом | Вибір скидався на першого зі збережених props | Відкрита чернетка залишається; повторне відкриття бере актуальний запис |
| Вибрано участь, фокус прибрано зі списку, надійшла live-подія | Викликався router.refresh з відкритою формою | Форма має data-dirty/data-submitting; глобальне оновлення чекає її закриття |
| POST повернув HTTP 200 з HTML замість JSON | Успіх, закриття форми й подія мутації | Успіх потребує явного ok:true; вибір та пояснення залишаються у формі |
| Зависло читання нагадувань | Нескінченне завантаження | Дедлайн 12 секунд, явна помилка й повторне читання без втрати вибору |
| Втрачена відповідь POST | Кнопки залишались заблокованими | Дедлайн 25 секунд, невизначений результат, доступне закриття; POST автоматично не повторюється |

Окремий тест реального HTTP-модуля 3.8.91 показав: пошкоджений JSON проходив до виклику handleRaidSessionAction зі статусом going. Невідома або відсутня дія також ставала going. Тепер JSON має бути об’єктом, а дія — відомим варіантом участі; некоректний запит відхиляється до доменної мутації. Старі явні alias-и maybe/50/50/5050/half/skip збережені.

## Поведінка після збою

Запити використовують наявні dashboardApiJson і useDashboardRequests: дедлайн охоплює читання відповіді, замінені та демонтовані запити не публікують стан, синхронний lock зупиняє подвійне підтвердження. Серверне повідомлення про відмову видно у формі. Після втрати відповіді форма радить перевірити склад рейду перед повторною дією: тайм-аут не доводить, що сервер скасував запис.

Відкрита форма резервує локальний вибір до підтвердження або скасування. Персонаж, участь, роль і ручний клас/спек ініціалізуються поточними props під час відкриття. Глобальне налаштування нагадувань перечитується; недоступне сховище не підміняється значенням true. Скасування не зберігає нагадування. Успішний POST закриває форму та надсилає одну подію оновлення.

Discord-меню з окремими списками класу й спеціалізації збережене; кнопок «спеки 1/2» та «2/2» немає. Нових SQL-міграцій і змін cron у цьому пакеті немає.

## Перевірки

- **12/12 HTTP-сценаріїв**: origin, відсутня сесія, rate limit, manual/character payload, бізнес-відмова, пошкоджений JSON, невідомі дії та старі alias-и, приватність і недоступність нагадувань. Завантажуються реальні модулі маршрутів; сесія, доменний запис і залежності сховища контрольовані.
- **15/15 браузерних сценаріїв**: до/після для п’яти UI-дефектів, повторне читання, серверна відмова, актуальний стан при повторному відкритті, ручний запис, подвійний submit, скасування, відновлення refresh і відсутність JS-помилок. Реальні React-компоненти, API-клієнт, request lanes та CSS; відповіді API контрольовані, Next navigation замінена вимірюваним адаптером.
- **9 ширин**: 320, 360, 390, 520, 760, 1024, 1280, 1600, 1920 px; без горизонтального переповнення, мобільний вигляд оглянуто візуально.
- **Повний build:ci — exit 0**: TypeScript, поведінкові/контрактні перевірки, CSS/UI-аудити, inspect:ci та production Next build. Окремий ESLint — exit 0.
- **55/55 тестів бота**, повний TAP-звіт із завершальними totals.

Повторно пройшли наявні перевірки: identity API 11; character setup API 10; заявки 20; публікації/відновлення 19; чернетки груп 7 та group API 10; перенесення призначень 8; спільна навігація 14, рейди/пули 10, гільдія 12; спостереження автоматизацій 22, внутрішній proxy 30; Discord-запис 29.

Відтворення UI можна повторити через `npm run check:raid-attendance-browser` у dashboard за наявності Playwright, esbuild та Chromium. Окреме розташування інструментів задає MISTBLOSSOM_QA_MODULES, шлях браузера — MISTBLOSSOM_QA_CHROMIUM, каталог тимчасових результатів — MISTBLOSSOM_QA_OUTPUT. Цей додатковий браузерний сценарій не вимагає Chromium під час Docker build. Швидкий HTTP-suite включено у verify/build:ci як check:raid-attendance.

Машинний підсумок: [R6_11_VALIDATION_2026-10-15.json](R6_11_VALIDATION_2026-10-15.json).

## Межі й подальший порядок

Це локальна контрольна діагностика з виправленнями, а не перевірка користувацького Discord/VPS. Живу PostgreSQL, Discord REST/Gateway, доставку справжнього DM та Docker Compose у цьому запуску не перевіряли. У production build залишаються два раніше відомі попередження Turbopack щодо динамічного доступу до файлів welcome-card; збірка успішна, окрема перевірка tracing залишається у R7.

R6.11 завершено в зазначеному локальному обсязі. Наступний контрольний крок — приймальна перевірка R6 на розгорнутому стенді з PostgreSQL/Discord: вхід і ролі, сайт↔Discord запис, публікація/відновлення та фактичні cron-спостереження. Після неї — R7: узгодження станів і доступності, вимірювання SQL/API/DOM та перевірка пакування welcome-card. Повне завершення R6/R7/R8 не заявляється.

Для відкату застосувати попередній повний пакет 3.8.91. Формат записів, bot та contract сумісні; окремого відкату БД немає. Розгортання на VPS не виконувалось.
