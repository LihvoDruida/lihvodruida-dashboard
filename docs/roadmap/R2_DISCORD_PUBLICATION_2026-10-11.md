# R2 — надійна публікація Discord, v3.8.70

Дата: 11.10.2026. Основа: повний перевірений R1 v3.8.69. Версія бота залишається 3.6.6.

Виконано пакет R2 з нового документа діагностики: D03 для рейдів та окрему перевірку і виправлення аналогічного шляху опитувань. R1 збережено. R3–R8 залишаються наступними окремими пакетами.

## Поведінка

- Публікація перечитує рейд із БД після отримання спільного між процесами lease. Другий одночасний запит отримує повідомлення, що дія вже виконується.
- Перед CREATE зберігається операція в `discordPublications`: ресурс, канал, ревізія вмісту, попередній ID, сталий nonce, час початку та стан. Зміна каналу або форми не обходить незавершену операцію.
- Підтверджений ID спочатку зберігається в операції; ID повідомлення в ресурсі та завершення операції записуються однією транзакцією. PostgreSQL-транзакції не тримаються під час HTTP.
- Після втраченої відповіді, 5xx, timeout або неповної відповіді система звіряє Discord, перш ніж продовжити. Якщо результат не підтверджено, повторний POST не виконується. Сталий nonce доповнює цей захист.
- При перенесенні нове посилання зберігається до видалення старого оголошення. Невдале видалення зберігає попереднє посилання в операції; повторне оновлення повторює очищення, а не створення.
- Вибраний у формі канал відокремлено від каналу фактичного оголошення (`discordMessageChannelId`). Старі документи підтримуються через відоме посилання/попередній канал. Фонові оновлення рейду використовують фактичний канал.
- Повтор POST нової форми рейду з тим самим `creationToken` зберігає одну чернетку; токен прив'язується до автентифікованого користувача. Старі клієнти без токена працюють, але не отримують цей захист повтору створення ресурсу.
- У редакторі є «Перевірити Discord» та поле посилання для незавершеного оголошення. Посилання перевіряється за ботом, каналом, часом і самим рейдом. Перевірка незавершеної події доступна також після закриття запису.
- Discord Scheduled Events мають окрему операцію створення. Відомий ID відновлюється після збою запису; неоднозначний результат звіряється за ботом і точними параметрами події. Налаштування, змінені під час HTTP, не перезаписуються старим станом синхронізації.
- Опитування використовують той самий механізм. Помилка подальшого запису не видаляє ресурс або вже підтверджене оголошення. Заплановане опитування повторно використовує збережений ID; щотижневий повтор відновлює одного наступника зі сталим ID та зберігає його голоси.
- Видалення рейду/опитування використовує той самий lease і не прибирає ресурс із незавершеним CREATE. Завершення операції не відновлює видалений документ.

## Стани та межі звірки

| Стан | Що відомо | Наступна дія |
| --- | --- | --- |
| `prepared` | Намір збережено; надсилання ще не розпочато | Одна спроба з тим самим збереженим вмістом |
| `sending` / `uncertain` | Discord міг прийняти запит | GET-звірка; без нового POST |
| `confirmed` | ID об'єкта збережено | Завершення запису посилання без CREATE |
| `complete` | Посилання й операція збережені | Оновлення відомого ID або окреме контрольоване перенесення |
| `rejected` | Є явна відмова API або перевірка до HTTP | Нова спроба після усунення причини |

Повідомлення звіряються не більш ніж за трьома сторінками по 100 записів. Відсутня історія або nonce не доводять, що оголошення не було створене. У такому випадку можна вказати його посилання; без підтвердження операція лишається незавершеною. Для події потрібен один точний збіг; нуль або кілька збігів не запускають новий CREATE. Звірка потребує доступу бота до каналу та історії. Автоматичного скидання невизначеної операції немає.

Це захист від неконтрольованого повторного надсилання, а не обіцянка абсолютного exactly-once від зовнішнього API. Старі дублі, які виникли до R2, автоматично не визначаються й не видаляються. Захист повтору нової форми рейду не є захистом від створення двох різних форм; у новій формі опитування окремого токена створення ресурсу поки немає.

Офіційні контракти Discord, перевірені під час R2:
[Create Message / nonce та історія](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx),
[Guild Scheduled Events](https://github.com/discord/discord-api-docs/blob/main/developers/resources/guild-scheduled-event.mdx).

У тестах виконується фактичний код операцій, lease, видавців і PostgreSQL-адаптера. Відповіді Discord контрольовані; у перевірках повних модулів каталоги, рендер вмісту й авторизаційні залежності замінені тестовими межами. Це не тест на живому сервері Discord. У лабораторії PostgreSQL 16.15 запускався з описаним у R1 локальним обходом стартової UID-перевірки; SQL-двигун не змінювався. Обхід та тестові дані не входять до архіву.

Для повторення на окремій тестовій БД:

```bash
cd dashboard
TEST_DATABASE_URL=postgresql://test:password@127.0.0.1:5432/mistblossom_test npm run test:publication
TEST_DATABASE_URL=postgresql://test:password@127.0.0.1:5432/mistblossom_test npm run test:db
npm run check:discord-publication
npm run verify
npm run build:ci
```

`npm run test:db:docker` запускає обидві PostgreSQL-серії в одному одноразовому контейнері `postgres:17.11-alpine`, без production volumes. Docker/PG17 тут не запускалися. Збірка має два попередні попередження трасування файлових шляхів у `discordWelcomeCard.ts` (273 і 487); R2 цей модуль не змінює. На VPS нічого не розгорнуто; живі Discord-публікації та production backup/restore не виконувалися.

## Оновлення та відкат

SQL-міграція не потрібна: операції використовують існуюче сховище документів. База з операціями має залишатися постійною між перезапусками.

Перед оновленням зупинити старі dashboard-процеси й запити планувальника, дочекатися завершення вже розпочатих дій, зробити резервну копію БД та запустити нову версію звичним способом розгортання. Старий видавець не використовує журнал R2, тому одночасна робота старої й нової версій не забезпечує цей захист. Бот та nginx зберігають свої попередні конфігурації.

Перед відкатом до R1 завершити звірку незавершених публікацій і зупинити видавців. Не видаляти `discordPublications` або збережені ID для «повторної спроби»: відкат до старого коду при невизначеному результаті може знову створити дубль. PostgreSQL-атомарність R1 залишається обов'язковою основою.

## Далі

R3 — повний каталог профілів без обрізання до 200. Потім R4 — надійна пауза очищення; R5 — чернетки редакторів; R6–R8 — наступні покращення UX, дизайну/продуктивності й функціоналу. Прийняття правил усіх типів не змінюється.
