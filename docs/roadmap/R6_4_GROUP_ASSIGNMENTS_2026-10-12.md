# R6.4 — безпечна зміна ID групи

Dashboard **3.8.77**, bot **3.6.6**. 12.10.2026, Europe/Kyiv.

## Виправлення

Раніше зміна ID переносила документ групи, але залишала dashboardProfiles.groupId без змін. Каталог міг підставити іншу групу за системною роллю. Вхід або запис зі старої сесії міг знову записати старий ID.

Тепер зміна групи, її збережених призначень і резервування старого ID виконуються однією транзакцією PostgreSQL. Переносяться профілі, у яких groupId точно дорівнює початковому ID. Оновлюються назва групи, ранг, системна роль і дата зміни. Персонажі, мейн, Battle.net, налаштування та невідомі поля зберігаються. Профілі без групи, інші групи й співпадіння лише за префіксом не зачіпаються.

| Сценарій | Результат |
|---|---|
| Зміна ID | Документ, призначення та перенаправлення комітяться разом |
| Старий ID у записі профілю | Адаптер записує актуальний ID і метадані групи |
| Повторне перейменування | Попередні перенаправлення ведуть прямо до нового ID |
| Створення або перейменування в зарезервований ID | 409; потрібно вибрати інший ID |
| Зайнятий ID, конфлікт ревізії або нестача прав | Зміна не виконується |
| Збій після оновлення профілів | Повний відкат профілів, групи та перенаправлень |
| Видалення групи зі збереженими призначеннями | 409; спочатку потрібно змінити групу профілів |
| Видалення порожньої групи | Чинна поведінка з перевіркою прав і ревізії |
| Firestore у режимі сумісності | Зміна ID відхиляється до записів; звичайне редагування доступне |

## Редактор і відновлення

Одна явна дія зберігає групу й переносить призначення. Після коміту показано точну кількість перенесених профілів, початковий і новий ID. Підсумок відновлюється через GET після втрати відповіді, при оновленні списку та після перезавантаження з незавершеною чернеткою. Повторного POST для підтвердження немає. Подальше звичайне збереження очищує попередній підсумок перенесення; перенаправлення залишаються.

Старий ID після перейменування зарезервований у dashboardAccessGroupRedirects. Повторне використання іншою групою створило б неоднозначність для старих сесій. Якщо актуальну порожню групу надалі видалено, запис через її старий зарезервований ID відхиляється. Видалення перенаправлень вручну не входить до інтерфейсу.

## Транзакції

Групові записи беруть ексклюзивний advisory lock каталогу перед перевіркою актуальної ревізії. Звичайні записи профілів беруть спільний lock цього ключа, тому незалежні профілі можуть записуватися паралельно. Lock існує лише до COMMIT/ROLLBACK; зовнішніх HTTP-дій усередині перенесення немає.

FOR SHARE/FOR UPDATE на рядку guard не дозволяє транзакції зі старим snapshot продовжити запис після зміни каталогу. Відсутній guard старих імпортів створюється без перезапису; конкурентний випадок також перевірено. Чинні обмежені повтори R1 заново виконують всю транзакцію лише для serialization/deadlock конфліктів.

Перенесення використовує три параметризовані SQL-запити: UPDATE призначень, UPDATE попередніх перенаправлень та INSERT резервування. Повні профілі не завантажуються в Node і не переписуються циклом окремих запитів. Перевірка видалення повертає лише scalar count. DDL і нових індексів немає.

Технічна основа: офіційні розділи PostgreSQL 16 про [ізоляцію транзакцій](https://www.postgresql.org/docs/16/transaction-iso.html) та [блокування](https://www.postgresql.org/docs/16/explicit-locking.html). Реалізацію підтверджують інтеграційні перевірки вихідних модулів.

## Перевірки й межі

Точні результати: [R6_4_VALIDATION_2026-10-12.json](R6_4_VALIDATION_2026-10-12.json). npm run test:group-migration використовує окремий TEST_DATABASE_URL, створює приватну схему та видаляє її. npm run check:group-migration включено у verify і build:ci.

Права, системні ID, revision-конфлікти та чернетки R5 збережені. Відмова аудиту не перетворює виконану зміну на повідомлення про невдале збереження. Права активних сесій оновлюються за чинним механізмом авторизації; перенесення не заявляє миттєве відкликання всіх cookie або зміну ролей Discord.

Механізм застосовується до перейменувань новим кодом. Історично втрачені призначення не можна безпечно відновити без відомого зіставлення старих і нових ID. Прямі SQL-письменники та старі адаптери не беруть спільного guard і не входять до гарантії конкурентних записів. Порожні групи, видалені без перейменування, зберігають попередній механізм повторного використання ID; повного foreign-key контролю legacy-призначень реліз не додає.

## Оновлення і відкат

Нової SQL-міграції та cron-задачі немає; службові документи створюються у чинному сховищі documents. Оновити всі процеси dashboard, які пишуть профілі, узгоджено. Не залишати старий і новий адаптери одночасно під час зміни ID. VPS, бойова БД, Discord та Battle.net у цьому сеансі не змінювалися.

Перед розгортанням використати штатний резервний бекап БД. До першої зміни ID можливий звичайний відкат коду. Після перенесень проста заміна коду на 3.8.76 небезпечна: вона ігнорує перенаправлення та резервування. Для такого відкату потрібна зупинка записів і узгоджене відновлення бекапу груп, профілів та службових документів або виправлення новою версією. Не видаляти лише перенаправлення, залишивши інші документи у новому стані.

Системні кольори, фон, прийняття правил і сторінка журналу збережені. Решта R6: контекстні наступні дії, навігація інших списків і стани автоматизацій.
