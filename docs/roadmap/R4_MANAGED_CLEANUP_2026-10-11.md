# R4 — кероване очищення Discord, v3.8.72

Дата: 11.10.2026. Основа: повний R3 v3.8.71; бот v3.6.6. Виправляються D06/D05 з вихідного документа діагностики. R1–R3 збережені.

## Пауза під час роботи

У R3 `pauseDiscordCleanup` вимагала той самий lease, який тримав worker. Справжня PostgreSQL-перевірка відтворила дефект: пауза відхилялася, `enabled` залишалося `true`.

Тепер пауза — окрема атомарна транзакція налаштувань і документа `dashboardSettings/discordMemberCleanupControl_<guildId>`. Вона записує `enabled=false`, новий токен покоління, час і автора паузи. Роль, строк, revision, результати перевірки й історія зберігаються. Команда не чекає lease чи завершення Discord HTTP. Власник сервера лишається єдиним користувачем, який може налаштовувати й призупиняти автоматичне очищення.

Worker перевіряє паузу до читання наступного учасника, після свіжої перевірки умов та безпосередньо перед DELETE, уже після всіх очікувань маршрутного/global bucket і локальної черги Discord REST. Останній контроль атомарно звіряє `enabled`, revision, токен паузи, власника й строк lease та попередню операцію. Лише після цього записуються `prepared` і одна поточна спроба. Транзакція БД не залишається відкритою під час HTTP.

Застаріле збереження налаштувань, розпочате до новішої паузи, не може тихо увімкнути очищення. Роль/строк надалі змінюються під worker lease. Явне нове збереження після паузи може відновити роботу.

Пауза не скасовує вже почату дію. Якщо остання перевірка дозволила її раніше за паузу, UI повідомляє про одну поточну спробу. Її підтвердження переноситься до «Виключені», а втрата відповіді — до «Потребують уваги». Далі worker бачить паузу й не починає наступне виключення. Між атомарним дозволом у БД і відправленням HTTP немає спільної транзакції з Discord; цей короткий інтервал також належить до вже початої спроби.

## Умови й відновлення

- Боти, власник сервера, адміністраторські/керовані/недоступні ролі та некоректна дата вступу лишаються захищеними. Зараховується лише відсутність ролей або рівно одна вибрана роль, без інших ролей; `@everyone` не рахується як окрема роль.
- Свіжий учасник читається після актуальних дозволів/ієрархії, ближче до дії. Якщо черга затримала відправлення більш ніж на 5 секунд після цього читання, DELETE не починається: наступний запуск знову перевірить умови. Ліміт роботи 30 секунд, порції по 5, календарні строки, перевірка повторного вступу й адаптивний інтервал збережені.
- До фактичного виклику `fetch` скасована/відхилена спроба не вважається невизначеним виключенням. Після відправлення DELETE таймаут/мережевий збій/5xx можуть бути невизначеними; автоматичного повтору для цього вступу немає. 400/401/403/404/429 лишаються явними відмовами.
- Фіналізація події й лічильника залишається атомарною та ідемпотентною. Невизначена фіналізація перевіряє `attemptId`, щоб стара спроба не замінила новішу.
- Поточна спроба очищається лише за власним `attemptId`. Після перезапуску покинуті `prepared` переходять до перевірки вручну; уже фіналізований запис очищає залишковий UI-сигнал без повторного підрахунку.

Discord не надає умовного DELETE за `joined_at` або набором ролей: зміна після останнього читання залишається можливою. R4 звужує це вікно й повторно перевіряє після довгого очікування, але не обіцяє атомарності між Discord і БД.

## Запити й інтерфейс

`DiscordMemberCleanupPanel` і `StaticRoleSettingsClient` використовують спільний `dashboardApiJson`, без автоматичного повтору POST. Новий `useDashboardRequests` має незалежні канали запитів, AbortController, загальний дедлайн і перевірку актуальності. Демонтування та заміна запиту скасовують його; стара відповідь і її `finally` не перезаписують новий стан.

| Дія | Дедлайн HTTP | Додаткове обмеження |
|---|---:|---|
| Список/стан/ролі, GET | 12 с | Усі сторінки одного оновлення списку разом — 15 с |
| Пауза, POST | 10 с | Після втрати відповіді — окремий GET стану |
| Налаштування, POST | 20 с | Після втрати відповіді — окремий GET стану |
| Ручна перевірка списку, POST | 40 с | Загальний канал дії — 45 с; відновлення через GET |
| Збереження ролей Статика | 20 с | Звірка GET у межах загальних 40 с |

Окремі стани завантаження списку, налаштувань, перевірки та паузи повертають правильні підписи кнопкам. Пауза доступна під час оновлення списку або ручної перевірки; вона скасовує очікування попередньої відповіді у браузері. Вкладки доступні під час завантаження. Перші 25 учасників, «Показати ще 25», збереження розгорнутої кількості під час фонового оновлення та клавіатурна навігація збережені.

Після невизначеного POST інтерфейс читає поточний стан, а не повторює дію. Стан «на паузі» показується за збереженими налаштуваннями. GET сам по собі не є підтвердженням конкретного запиту налаштувань чи завершення ручної перевірки: UI явно повідомляє про непідтверджений результат. Для Статика збережені ролі порівнюються з вибором; чернетка не стирається, якщо вони різні. Початковий збій GET ролей має кнопку повторного завантаження.

Системні теплі кольори, фон, дизайн логування та прийняття правил всіх типів не змінювалися. Нової частоти фонових запитів немає. Автоматичне прийняття правил, увімкнення очищення або надання прав не додавалося.

## Перевірки

Фінальні `verify` та `build:ci` пройшли; inspect перевірив 433 файли без блокерів. PostgreSQL-серії: R4 11/11, R1 23/23, R2 26/26, R3 32/32; бот 45/45. REST 16 сценаріїв, локальний HTTP 3, очищення 101 перевірка. Next.js 16.3.5 production build завершився за 19 секунд; збережені два попередні попередження трасування `discordWelcomeCard.ts`.

Фінальний машинний звіт: [R4_VALIDATION_2026-10-11.json](./R4_VALIDATION_2026-10-11.json).

- `test:cleanup`: справжня PostgreSQL 16.15, окрема випадкова схема; пауза із зайнятим lease, перед відправленням і під час DELETE, незалежний Node-процес, конкурентне увімкнення/пауза, втрачений lease, строгі ролі/повторний вступ/бот, права/власник, втрата відповіді, покинута й уже фіналізована спроба, застаріла перевірка після черги.
- `check:discord-rest`: фактичний REST-модуль; фінальний контроль після learned cooldown, звільнення дозволів після скасування та розрізнення скасування до відправлення. Регресії rate limits, nonce, retry і concurrency.
- `check:dashboard-requests`: справжній локальний HTTP; завислі заголовки/тіло GET, скасування та застосований POST із втраченою відповіддю, один POST і відновлення GET.
- Chromium: фактичні компоненти на 320/360/390/430/640/768/1024/1280/1920 px; пагінація 25→50, фонове оновлення без згортання, вкладки/клавіатура/owner-only; пауза під час завислої перевірки, дедлайн POST і GET, стара відповідь, abort при демонтуванні, відновлення ролей Статика.
- Регресії R1/R2/R3 виконуються на окремих приватних схемах PostgreSQL. Production builder перевіряється з 23 фактичними COPY-входами Dockerfile.

Живий Discord, production БД і VPS не використовувалися. Docker-раннер оновлено для чотирьох серій, але Docker у цьому середовищі не запускався; native PostgreSQL 16.15 використовує локальну адаптацію перевірки UID під час старту. Поведінка живого Firestore SDK тут окремо не перевірялася.

## Оновлення й відкат

SQL-міграція не потрібна. Новий control-документ створюється ліниво; для старої конфігурації використовується токен `legacy`. Історію, лічильники та чергу не скидати. Операції R2 також зберігати згідно з [порядком відкату R2](./R2_DISCORD_PUBLICATION_2026-10-11.md).

Перед production оновленням зробити резервну копію БД, зупинити cron і старі dashboard-процеси, дочекатися поточних дій/перевірити їх історію. Запустити всі dashboard-процеси з R4, перевірити в тестовому guild паузу під час дії та restart-recovery, потім відновити cron. Одночасно працюючі старі й нові worker-процеси не підтримуються: старий код не перевіряє новий сигнал після черги.

```bash
cd dashboard
npm run verify
TEST_DATABASE_URL=postgresql://test:password@127.0.0.1:5432/mistblossom_test npm run test:cleanup
# Або R1–R4 в одному ізольованому Docker-контейнері:
npm run test:db:docker
npm run build:ci
```

Для відкату спочатку призупинити очищення через R4, зупинити cron і всі worker-процеси, перевірити незавершені спроби. Після повернення R3 залишити автоматичне виключення вимкненим: R3 знову має дефект паузи. Не видаляти control/event документи для «повторної спроби» невизначеного виключення.
