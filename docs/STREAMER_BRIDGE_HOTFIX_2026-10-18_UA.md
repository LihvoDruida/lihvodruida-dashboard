# Виправлення маршруту стрімерів — Dashboard 3.14.1 / Site 4.6.1

18 жовтня 2026 року.

## Причина

У Dashboard 3.14.0 маршрут `/api/site/streamers` був реалізований і заявлений у capabilities, але його пропущено у `isPublicSiteBridgePath()` захисного proxy. Запит з Docker-хостом `dashboard:3000` через це отримував HTTP 308 на публічний домен замість JSON. Site навмисно використовує `redirect: error`, тому повертав `dashboard_unavailable`. Це помилка маршрутизації релізу, а не ознака відсутності ключів Twitch/YouTube/TikTok.

Попередні перевірки окремо тестували route handler і підмінений upstream, тому пропуск production proxy не виявили. Новий сценарій відтворив HTTP 308 до виправлення.

## Виправлення

- Dashboard: точний read-only маршрут `/api/site/streamers` додано до чинного site bridge. Внутрішній запит потребує правильного `PUBLIC_SITE_BRIDGE_TOKEN`; перевірки прав керування не змінені.
- Site: preflight тепер читає фактичний snapshot стрімерів, а не лише список capabilities. Збій виявляється до заміни поточного контейнера; діагностика не друкує секретів чи тіла upstream-відповіді.
- Локальний readiness також перевіряє snapshot стрімерів і потрібну capability. Перевірка `--local` додатково читає публічний streamer envelope.
- Нові перевірки проходять через справжній production proxy з валідним, хибним і відсутнім токеном. Перевірено, що токен сайту не відкриває API керування, а POST до read-only маршруту не отримує внутрішній виняток.
- Standalone Dashboard перевіряється справжнім HTTP-запитом із Host `dashboard:3000`: без токена — 401; з токеном маршрут досягає обробника (у тесті без бази — контрольований JSON 503 `database_unavailable`, без перенаправлення).
- Standalone Site перевіряє, що збій streamer upstream не проходить readiness або preflight навіть за наявності capability.

## Установлення

1. Оновити файли **повного стека Dashboard** з архіву 3.14.1, зберігши чинні env-файли та дані.
2. Із його кореня, де `docker-compose.yml`, виконати:

```bash
make rebuild-dashboard
```

Якщо оновлюєшся з версії до 3.14.0, використовуй `make up`, щоб також оновити cron. Для переходу 3.14.0 → 3.14.1 зміни cron не потрібні.

3. Оновити файли сайту з архіву 4.6.1, зберігши `.env`, і виконати:

```bash
cd /srv/lihvodruida-site
make up
```

Саме виправлення Dashboard 3.14.1 відновлює сумісність і з Site 4.6.0; Site 4.6.1 додає раннє виявлення подібної відмови. Не обходити public-routes перевірку й не прибирати rollback. Нові API-ключі або зміна Cloudflare для усунення цієї конкретної помилки не потрібні.

Підключення платформ і дозволи описані в `GUILD_STREAMERS_2026-10-18_UA.md`. Порожній список стрімерів — коректний JSON із `items: []`, навіть якщо платформи ще не підключено або перевірку каналів вимкнено.

## Межі перевірки

Перевірки виконано локально зі справжніми production-модулями та збірками, PGlite і контрольованими HTTP-відповідями. Виробничий VPS, реальні токени платформ і справжні Discord-повідомлення з цього середовища не змінювалися.
