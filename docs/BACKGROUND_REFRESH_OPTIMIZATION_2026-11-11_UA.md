# Dashboard 3.21.0 — оптимізація фонового оновлення

Оновлено спільну логіку, яку використовують віджети профілів, гільдії, рейдів, пулів та стану інтеграцій. Відеофон і попереднє очищення збережені.

## Поведінка

| Сценарій | Було | Стало |
|---|---|---|
| Зміна даних під час активного фонового запиту | Запланований повтор міг бути перезаписаний звичайним таймером; `force`, scope та ID губилися | Одна об’єднана черга зберігає ціль; після завершення запиту повтор виконується з паузою 2,5 с |
| Кілька змін під час очікування | Частина цілей могла загубитися | Для однієї scope об’єднуються ID, для різних scope виконується один ширший цикл по активних ресурсах |
| Два виклики одного ресурсу | Другий міг показати «пропущено», хоча перший працював | Другий чекає чинний запит, стан лишається «перевірка» |
| Повторний виклик зі слухача стану | До встановлення in-flight ознаки міг початися ще один запит | Спільний Promise зберігається до повідомлення слухачів; dispatch відкладено до наступної microtask |
| Закритий віджет | Збережений на 5 хв ресурс ще міг опитуватися загальним циклом | Нові запити лише для ресурсів із підключеними користувачами; кеш неактивних ресурсів позначається як застарілий і оновлюється один раз при поверненні, також після offline |
| Ідентична JSON-відповідь | Дані замінювалися новим об’єктом | Попереднє посилання на дані зберігається, щоб не запускати зайві залежні обчислення |
| Нестандартний результат selector-а | JSON-еквівалентність не гарантується | Для циклічних об’єктів і non-JSON контейнерів повторне використання посилання не застосовується |
| Перехід до іншого ключа ресурсу | Hook міг показувати попередні initialData | Початковий і server snapshot відповідають новим даним |
| Час localStorage помилково в майбутньому | Оновлення могло блокуватися надовго | Майбутній timestamp ігнорується |
| Запит пережив перший строк утримання кешу | Прибирання могло більше не заплануватися | Завершення запиту повторно планує прибирання за відсутності користувачів |
| Помилка підготовки запиту | Могла залишитися необробленим rejection | Потрапляє у стан помилки ресурсу зі збереженням попередніх даних |
| Request factory повернула null | Запит не потрібний | Не створюється помилковий cooldown, який завадив би наступному коректному запиту |

Вже початі запити не скасовуються лише через вихід останнього віджета: це зберігає коректність невизначеного результату POST та повторного монтування. Поточний запит можна повторно використати після швидкого повернення. Автоматичний retry для mutation POST не додавався.

## Перевірка

Додано `npm run check:background-resource-logic`: 23 поведінкові сценарії виконують справжні модулі з контрольованими React hooks, DOM-подіями, транспортом та годинником. Перевірка включена у `verify` та `build:ci`.

Негативний контроль на коді 3.20.0 відтворив:

- неправильний стан `skipped` замість `checking`;
- відсутній запит після зміни під час фонового оновлення;
- два запити замість одного при повторному виклику зі слухача.

Для останнього контрольованого сценарію кількість однакових запитів зменшено з 2 до 1. Це вимір конкретного тесту, а не оцінка загального прискорення VPS чи сторінок. Гарантована затримка доставки не заявляється: повтор чекає завершення запиту, мережу й чинні обмеження.

Фінальні результати: `VALIDATION_BACKGROUND_REFRESH_2026-11-11.md`.
Окремих SQL-міграцій немає. Production VPS, PostgreSQL та окремий Site не змінювалися. Нових залежностей немає.
