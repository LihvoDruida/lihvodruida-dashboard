# Архітектура: панель, бот і спільний контракт

Раніше все жило в двох місцях: Next.js на Vercel і Cloudflare Worker, який
приймав взаємодії Discord. Після переїзду на власний сервер система
складається з трьох частин.

---

## 1. Хто що робить

| Сервіс | Каталог | Відповідальність | Чого НЕ має |
|--------|---------|------------------|-------------|
| **Панель** | `dashboard/` | уся бізнес-логіка, база, сторінки, API | не приймає взаємодій з інтернету |
| **Бот** | `bot/` | підпис Discord, миттєвий ACK, маршрутизація, редагування interaction-відповіді, Recruitment Gateway | ні бази, ні Battle.net/GitHub секретів, ні бізнес-логіки |
| **Контракт** | `shared/` | розбір `custom_id`, перевірка компонентів | жодних залежностей і жодного домену |

Cloudflare Worker видалений із репозиторію повністю. Усе, що він робив,
розподілене між двома сервісами: перевірка підпису й ACK — у боті, статистика
правил, заявки, кеш і планові задачі — у панелі; постійний Discord Gateway — у боті.
Cloudflare Worker/KV/Vercel як runtime-компоненти більше не потрібні.

### Чому бот окремо

Discord дає рівно **3 секунди** на підтвердження взаємодії. Якщо ACK живе в
тому ж процесі, що й панель, то будь-який деплой, перезбірка чи довга
транзакція перетворюються на «Дія не вдалася» в клієнтах гільдії. Окремий
контейнер знімає цей звʼязок: бот піднімається за частку секунди і не
перезапускається разом із релізом панелі.

Побічно це дає ще дві речі: логи бота не тонуть у логах сайту, і сервіс, який
дивиться в інтернет, має мінімальну поверхню — кілька файлів ESM, Discord
public key і bot token. Доступу до PostgreSQL, Battle.net та GitHub у нього немає.

## 2. Шлях однієї взаємодії

Людина натиснула кнопку в Discord:

```
Discord
  │  POST https://guild.lihvodruida.pp.ua/discord/interactions
  ▼
nginx ──────────────────────────────► bot:8080
                                        │ 1. перевіряє підпис Ed25519
                                        │ 2. визначає домен за custom_id
                                        │ 3. ВІДПОВІДАЄ Discord "думаю" (<3 c)
                                        │
                                        │ 4. далі — уже без поспіху
                                        ▼
                              dashboard:3000 /api/discord/interactions
                                        │ перевіряє підпис ЩЕ РАЗ
                                        │ виконує логіку, пише в PostgreSQL
                                        │ повертає готове тіло відповіді
                                        ▼
                                       bot
                                        │ 5. перевіряє компоненти
                                        │ 6. PATCH @original у Discord
                                        ▼
                                     Discord
```

**Крок 3 і крок 6 — це пара.** Бот відповідає «думаю», і хтось **зобовʼязаний**
потім надіслати результат, інакше людина бачить вічне «застосунок думає».
Раніше цю пару замикав Worker, тепер — бот (`src/dashboardClient.mjs`).

**Крок 5 не косметичний.** Discord відхиляє повідомлення з однаковими
`custom_id` помилкою 400. Саме так одного разу зламався весь приватний пульт
голосування: при рівно двох сторінках кнопки «назад» і «вперед» вели на ту саму
сторінку, а номер сторінки входить у `custom_id`. Тепер бот ловить це перед
відправкою і показує текст без кнопок замість порожньої відповіді, а тест
`bot/test/contract.test.mjs` не дає такому регресу повернутись.

### Підпис перевіряється двічі

Це не надмірність. Бот перевіряє, щоб не пересилати сміття далі. Панель
перевіряє, бо інакше будь-хто з доступом до внутрішньої мережі міг би
надіслати підроблену взаємодію в обхід бота. Тому бот передає заголовки
`X-Signature-Ed25519` і `X-Signature-Timestamp` як є.

Ззовні маршрут панелі закритий на рівні nginx (`deny all`).

## 3. Спільний контракт `shared/`

Це найважливіша частина розділення.

Раніше кожна сторона тримала власну копію регулярних виразів для `custom_id`.
Двічі це закінчилось однаково: у панелі зʼявлялась нова дія, копію у Worker
забували оновити, і кнопка мовчки переставала працювати — Worker повертав
`null` ще до того, як запит доходив до панелі. Ні типи, ні збірка цього не
ловили, тільки прод.

Тепер обидві сторони імпортують `@mistblossom/discord-contract`:

```js
import { decodeRaidPollCustomId, interactionDomainFor } from "@mistblossom/discord-contract";
```

Пакет підключений як локальна залежність (`file:../shared`), тому це звичайний
імпорт, а не копіювання файлів при збірці. Додаєш дію в одному місці — вона
одразу відома і панелі, і боту.

Пакет свідомо **без залежностей і без доменної логіки**: тут лише розбір
рядків. Перевірки на кшталт «чи існує такий клас WoW» лишаються в панелі, бо
бот про них нічого не знає і знати не повинен.

## 4. Налаштування

У Discord Developer Portal → Interactions Endpoint URL:

```
https://<ваш-домен>/discord/interactions
```

Основні змінні бота (`bot/.env.production` і stack env):

```bash
DISCORD_PUBLIC_KEY=<публічний ключ застосунку>
DISCORD_APPLICATION_ID=<ID застосунку>
DISCORD_BOT_TOKEN=<bot token>
DISCORD_GUILD_ID=<guild id>
INTERNAL_API_TOKEN=<openssl rand -hex 32>
```

`INTERNAL_API_TOKEN` має збігатися зі значенням у `dashboard/.env.production` —
це спільний секрет пари «бот → панель».

Запуск:

```bash
docker compose up -d --build bot
docker compose logs -f bot
curl -fsS http://localhost:8080/health   # зсередини мережі
```

## 5. Перевірка після зміни

```bash
cd bot && npm test
```

Тести покривають те, що ламалось насправді: розбір усіх дій рейд-пулу, легасі
`custom_id` зі старих повідомлень, відхилення підробок, перевірку підпису
Ed25519 справжніми ключами, захист від повторного відтворення і ловлю
дублікатів `custom_id`.

Далі — руками, бо автотести не бачать Discord:

1. натисніть кнопку голосування в Discord — має відкритись пульт;
2. виберіть роль і день, натисніть «Проголосувати»;
3. перевірте, що публічний embed оновився, а сайт показує голос.

Це найважчий шлях у системі: він одночасно зачіпає підпис, ACK, транзакцію
в базі, редагування відповіді й перемальовування embed.

## 6. Типові проблеми

| Симптом | Причина | Що робити |
|---------|---------|-----------|
| «Застосунок думає» і нічого далі | бот не зміг відредагувати відповідь | `docker compose logs bot`; найчастіше не задано `DISCORD_APPLICATION_ID` |
| Discord пише «Дія не вдалася» одразу | бот не відповів за 3 секунди або не піднявся | `docker compose ps bot`, перевірити `DISCORD_PUBLIC_KEY` |
| 401 у логах бота | ключ застосунку не той або запит не від Discord | звірити `DISCORD_PUBLIC_KEY` із Developer Portal |
| «Панель відповіла 401» | розійшовся `INTERNAL_API_TOKEN` | звірити значення в `.env` і `dashboard/.env.production` |
| Кнопка не реагує взагалі | `custom_id` не описаний у контракті | додати шаблон у `shared/index.mjs` і тест |
| Текст приходить без кнопок | бот відсік некоректні компоненти | у логах буде `duplicates` або `tooLong` — шукати в білдері компонентів панелі |

## 7. Мапа файлів

| Файл | Призначення |
|------|-------------|
| `shared/index.mjs` | контракт `custom_id`, перевірка компонентів |
| `bot/src/server.mjs` | HTTP-сервер, ACK, вибір типу відкладеної відповіді |
| `bot/src/signature.mjs` | перевірка Ed25519 через `node:crypto` |
| `bot/src/dashboardClient.mjs` | виклик панелі + `PATCH @original` у Discord |
| `bot/test/` | тести контракту і підпису |
| `dashboard/src/app/api/discord/interactions/route.ts` | обробка взаємодій панеллю |
| `deploy/nginx/dashboard.conf` | `/discord/interactions` → бот, `/api/discord/interactions` → `deny all` |
| `docker-compose.yml` | сервіс `bot` |
