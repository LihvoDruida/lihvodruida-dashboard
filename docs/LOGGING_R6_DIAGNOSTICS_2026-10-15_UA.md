# Діагностика збереження й Discord — dashboard 3.8.95

15.10.2026. Bot 3.6.9 та contract 1.1.1 залишаються попередніх версій.

Це додатковий пакет логування для подальшого ручного приймання R6. R7.2 збережено; профіль і групи в решті R7 залишаються наступним функціональним кроком. Перевірку на живих PostgreSQL/Discord користувач проведе пізніше; цей пакет її не позначає виконаною.

## Що виправлено

На попередньому коді відтворено два дефекти: два записи одного HTTP-запиту без вхідного ID отримували різні requestId; збій PostgreSQL-сховища журналу міг надрукувати синтетичний пароль у console fallback. Тепер ID стабільний протягом життя об’єкта Request, а обидва fallback-и сховища та Discord-дзеркала проходять наявне маскування.

Вхідний ID перевіряється за форматом і довжиною. Поля details не можуть підмінити реальні event, time, requestId, method і path у консольному записі. Поле requestId також передається до структурованого сховища. Це кореляція серверних подій; новий HTTP response header не додається.

Запис у рейд тепер має окремий результат збереження та окремий результат фонового оновлення Discord. Неможливість зареєструвати after() після успішного запису зберігає ok:true і показує попередження про перевірку Discord. Відсутність підтвердження фонового sync не видається за втрату запису й не запускає повторний POST.

Профільні конфлікти, недоступність читання/запису, відкладений nickname worker та часткові результати публікацій отримали phase, outcome і доступний контекст операції. Виняток самого логера не перетворює підтверджений запис на невдалу HTTP-відповідь.

## Як знайти причину під час перевірки

Відкрити `/dashboard/logs` з відповідними правами, вибрати час і знайти точну назву події в полі «Пошук». У деталях доступні Request ID та діагностичний payload; можна завантажити відфільтрований експорт. Пов’язані події зіставляти за requestId, часом, resourceId або operationId. Якщо саме сховище журналу недоступне, дивитися консоль dashboard за той самий проміжок часу.

| Подія | Що перевірити |
|---|---|
| `raids.attendance.result` | `phase=commit`, `outcome=committed` означають підтверджений результат доменного запису. `discordSync=scheduled` означає лише реєстрацію фонового оновлення. |
| `raids.attendance.result`, `phase=discord_sync` | `outcome=unconfirmed`, `commitState=committed`: запис збережено, Discord окремо не підтверджено. false може означати й відсутність придатної публікації, тому це не твердження про помилку Discord REST. |
| `profile.identity.failed`, `profile.characters.failed` | `phase=read/write`; `outcome=conflict` для HTTP 409, `rejected` для інших оброблених 4xx, `unconfirmed` для неочікуваного винятку/503. |
| `profile.identity.accepted`, `profile.characters.setup_saved` | Підтверджений запис профілю, тривалість, ID ресурсу та наявний operationId. Прийнята зміна імені не означає вже змінений Discord-нік. |
| `profile.identity.worker_deferred` | `phase=schedule/worker`; operationId вказує збережений намір, до якого може повернутися наявна cron-черга. |
| `raids.discord_resync`, `polls.discord_resync` | `completed` або `partial` після явної синхронізації. Частковий результат потребує перегляду збереженого стану публікації. |
| `raids.discord_resync_failed`, `polls.discord_resync_failed` | `pending`/409 означає зайняту операцію; `unconfirmed` означає, що потрібно прочитати збережений стан перед наступною дією. |

Для attendance `phase=input` відрізняє некоректний ввід від `phase=commit`, де доменна політика повернула відмову. Неочікуваний виняток на етапі commit позначено unconfirmed: це не доказ відсутності запису в БД. HTTP-контракт існуючої помилки attendance збережено.

| nextAction | Дія оператора |
|---|---|
| `check_publication` | Відкрити збережений стан публікації рейду/опитування й перевірити Discord-повідомлення. |
| `read_saved_status` | Спочатку оновити стан; не повторювати зміну автоматично після непевної відповіді. |
| `check_profile_sync` | Переглянути стан синхронізації імені та черги; дати наявному виконавцю завершити намір. |

## Контекст без зайвих даних

Нові діагностичні події не копіюють тіло форми, ім’я, ключ персонажа або налаштування нагадування. `diagnosticErrorSummary` повертає лише errorKind і дозволений errorCode (наприклад 08006, 40001, ECONNRESET, ETIMEDOUT), без message, stack чи вкладеного cause. Невідомий код не потрапляє в payload. Наявне маскування токенів/паролів застосовується також до двох виправлених console fallback-ів.

Успішні GET профілів не створюють нових подій. Підтверджений фоновий attendance sync лишається debug з persist:false; за замовчуванням він тихий, навіть при тимчасовому ввімкненні DASHBOARD_DEBUG_LOGS не пишеться в SQL. Звичайні idle/poll тики не підвищено до info. Структуроване збереження лишається асинхронним без гарантії доставки під час аварійного завершення процесу. Перетворення всіх історичних console.warn у проєкті до цього пакета не входило.

## Локальні перевірки

`npm run check:operation-logging` виконує 25 поведінкових сценаріїв на справжніх production-модулях із контрольованими залежностями: кореляція, маскування fallback-ів, підміна метаданих, збереження з недоступним логером/after, тихий успішний sync, непевний Discord, профільні 409/503, deferred nickname worker, pending публікації та відсутність повторного бізнес-запису. Команду додано у verify й build:ci.

Машинний підсумок цієї перевірки та повної збірки: [LOGGING_DIAGNOSTICS_VALIDATION_2026-10-15.json](LOGGING_DIAGNOSTICS_VALIDATION_2026-10-15.json). Локальні mocks не замінюють приймання живих PostgreSQL/Discord. SQL-схему, частоту cron і дизайн сторінки журналу не змінено.
