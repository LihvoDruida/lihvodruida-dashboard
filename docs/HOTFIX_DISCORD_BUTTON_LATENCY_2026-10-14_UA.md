# Прискорення кнопок Discord — dashboard v3.8.80 / bot v3.6.7

14.10.2026, Київ. Повний проєкт на основі попереднього v3.8.79.
Попереднє виправлення HTTP 421 для profile-nicknames/automation збережено.

## Причина затримки

Після запису підписаної взаємодії бот повертав Discord deferred ACK, але
обробка запускалася лише фоновим опитуванням кожні 3 секунди. За один цикл
бралася одна задача. Готовий результат зберігався в outbox, який окремо
опитувався кожні 5 секунд, також із видачею однієї задачі.

Без навантаження це могло додавати до приблизно 8 секунд очікування таймерів
понад час виконання самої дії. Серія натискань створювала чергу, і очікування
зростало. Це підтверджена властивість коду; фактичну затримку живого VPS у цій
роботі не вимірювали. Старий експорт містить тривалість бізнес-дій, але не повний
час від натискання до появи відповіді, тому ним не можна довести end-to-end p95.

## Що змінено

- Після успішного збереження signed receipt і завершення відправлення HTTP ACK
  запускається внутрішній worker. ACK не чекає бізнес-логіки.
- Коли signed handler повернув результат, уже записаний в outbox, бот одразу
  запускає доставку відповіді. Не чекає наступного 5-секундного tick.
- Worker бере наступну готову задачу без паузи опитування. Після 10 проходів
  віддає керування event loop та продовжує через setImmediate.
- Сигнали запуску, що прийшли під час активного worker, не губляться.
  Одночасно в одному процесі працює лише один ingress і один outbox worker.
- Порядок обробки лишається послідовним; паралельного виконання бізнес-дій
  усередині одного worker не додано. Доставка вже готового результату не чекає
  завершення наступної бізнес-дії.
- Періодичні опитування 3/5 секунд залишено для відновлення після рестарту
  або пропущеного локального сигналу. Для звичайного натискання вони більше
  не є обов’язковими етапами очікування.
- Додано події discord.interaction.acknowledged, discord.interaction.processed,
  discord.interaction.delivered з interactionId та durationMs. Вони дозволяють
  розрізнити час прийняття запиту, виконання дії та HTTP-доставки у Discord.
  durationMs кожної події вимірює свій етап, а не весь час від натискання.

## Надійність і безпека

Залишено перевірку Ed25519 у боті та дашборді, обов’язковий запис до ACK,
зашифровану збережену чергу, bearer-авторизацію, транзакційні leases,
дедуплікацію бізнес-дій, retry/backoff і обмеження тіла HTTP-відповідей.
Локальний сигнал запуску не переносить бізнес-команду та не замінює запис у БД.

## Перевірки

**npm --prefix bot test: 52/52 пройдено.**

Додано тести для ACK-before-work, послідовного виконання серії задач,
одночасних сигналів, сигналу під час порожнього читання, черги з 25 задач,
передачі керування event loop та відновлення після помилки.

Окремий тест запускає справжній HTTP-сервер бота, генерує Ed25519-підпис,
моделює затриманий commit та проходить transport pipeline до PATCH відповіді.
Dashboard/БД і зовнішній Discord у ньому замінені локальним HTTP fixture.
Тест завершився приблизно за 0,2 секунди, без очікування recovery-таймерів.
Це контрольна локальна перевірка транспорту, не гарантія такої швидкості на VPS.

Також пройдені:
- check-internal-cron-proxy: 21/21;
- check-security-performance: 97 інваріантів;
- check-platform-hardening: 15/15;
- check-footer-version: 9/9;
- check-api-security: 92 mutation routes;
- inspect-ci: 465 файлів, 0 blocking issues.

Повний Next.js/Docker build, typecheck і lint у цьому середовищі не виконано:
залежності dashboard не встановлені. На робочому VPS зміни не розгорталися.
Повільний Discord API, БД або конкретний бізнес-handler ще можуть додавати
затримку; це виправлення прибирає підтверджені штучні паузи транспорту.

## Встановлення

Резервна копія поточного коду; вміст guild_header_work розпакувати в корінь
проєкту, зберігши власні .env / .env.production. Потім із кореня:

```sh
docker compose build dashboard bot
docker compose up -d --no-deps --force-recreate dashboard bot cron
docker compose ps
docker compose logs --since=5m bot dashboard cron
```

Потрібно оновити саме образ bot: простий restart старого образу цього виправлення
не застосує. Dashboard містить попередній Host hotfix і нову версію у футері.
Пересоздання cron очищає тимчасовий backoff від старих HTTP 421.
Міграції БД та зміни токенів не потрібні.

Після healthy-стану перевірити кнопку відкриття приватного меню, вибір ролі та
реєстрацію в рейд. Перевірити появу трьох нових interaction-подій у журналі.
За тривалих затримок зіставляти їх за interactionId; не робити багато повторних
натискань, доки попередня дія ще виконується.
