# Узгодження сайтів і завершення legacy-інтеграцій

**Дата:** 16.10.2026, Київ. **Парний реліз:** Dashboard **3.9.1** + Public Site **4.1.1**.

Вихідні проєкти: Dashboard 3.8.103 cms-docker-hotfix і Site 4.0.1 build-hotfix. Зміни підготовлено в наданих вихідних кодах; живий VPS не змінювався.

Додаткова інспекція Cloudflare, заявок і CurseForge та актуальне приймання: [SYNC_INSPECTION_2026-10-16_UA.md](SYNC_INSPECTION_2026-10-16_UA.md).

## Результат

Дашборд залишається власником БД, профілів, заявок, модерації, CMS і Discord-операцій. Публічний сайт має один явний канал до дашборда через Docker. Вимкнений або неправильно налаштований канал повертає помилку, а не перемикає сайт на іншу інфраструктуру.

| Потік | Реалізація |
|---|---|
| Склад, прогрес і розклад | Site → `http://dashboard:3000/api/site/guild` |
| Список і статуси заявок | Browser → Site `/site-api/v1/applications` → Dashboard GET |
| Створення заявки | Browser → Site `/site-api/v1/applications` → Dashboard POST → PostgreSQL |
| Рішення офіцера / дія Discord | Чинна модерація змінює той самий запис PostgreSQL; сайт читає його статус |
| Новини й гайди | Site → Dashboard `/api/site/content?page=N`, контракт v2 |
| Обкладинки | Browser → Site `/site-api/v1/media/:hash` → Dashboard → PostgreSQL |
| Готовність інтеграції | Site `/site-api/v1/status` → автентифікований Dashboard `/api/site/status` |

Публічний сайт не отримує `INTERNAL_API_TOKEN`, OAuth-секрети, bot token або доступ до PostgreSQL. Окремий `PUBLIC_SITE_BRIDGE_TOKEN` дозволяє тільки визначені запити. POST дозволений лише для створення заявки; адміністративні API не успадковують цей виняток.

## Що виправлено

### Зв’язок і конфігурація

1. Заявка більше не залежить від browser CORS-запиту на домен дашборда. Вона надсилається через API власного сайту.
2. `DASHBOARD_INTERNAL_URL` і коректний bridge token обов’язкові. Прибрано тихе повернення до публічного HTTPS upstream за відсутності секрету.
3. Дашборд перевіряє token і Origin для POST. Переданий відвідувачем Authorization або cookie не копіюється в сервісний запит.
4. Адреса клієнта проходить через контрольований заголовок; ліміти заявок рахуються окремо для кожної адреси. Production-запит без коректного IP не надсилається далі. Nginx перезаписує `X-Real-IP`.
5. Внутрішні читання з правильним токеном не потрапляють у спільний анонімний bucket IP `unknown`. Публічні обмеження частоти збережено.
6. Канонічні URL дашборда передаються контейнеру з кореневого Compose env. CMS-preview використовує `PUBLIC_SITE_URL`.
7. Додано readiness із перевіркою токена, версії bridge, PostgreSQL та наявності таблиць `documents` і `site_content_media`.
8. Сайт відрізняє живість Node-процесу від готовності інтеграції. Деплой перевіряє обидва стани й намагається повернути попередній здоровий образ, якщо новий зв’язок не готовий.

### Заявки і статуси

9. Обидва проєкти мають однаковий валідатор і нормалізацію заявки. Парний тест порівнює файли побайтно.
10. Узгоджено регіон EU, Discord username, BattleTag для Horde, довжини полів, джерело знайомства, платформу, honeypot і згоду. Дашборд повторно перевіряє поля незалежно від браузера.
11. Повторні та одночасні надсилання одного персонажа/реалму/регіону з тим самим Discord протягом 10 хвилин використовують транзакційний запис дедуплікації. Інший контакт не отримує квитанцію попереднього заявника. У нумерації можливі пропуски — номер не є лічильником прийнятих заявок.
12. Публічна POST-відповідь має вузький набір полів квитанції, не кешується і не розкриває контактів. Некоректна відповідь upstream не показується як успішне створення.
13. Прибрано обрізання джерела заявок до останніх 300 записів: фільтри й лічильники працюють із повним сховищем. Сайт, як і раніше, показує до 100 збігів одного пошуку.
14. Ліміти тіла перевіряють фактичні байти, включно з chunked-відповідями. Помилка 429 зберігає cooldown.
15. Статуси й склад продовжують оновлюватися окремими фоновими запитами з ETag/304, без перезавантаження сторінки.

### CMS і медіа

16. Каталог CMS переведено на сторінки по 20 матеріалів із загальною ревізією. Сайт відхиляє неповний або змішаний знімок, якщо матеріали змінилися під час читання сторінок.
17. Замість необмеженого `response.text()` використано читання з перевіркою фактичного розміру. Кожна сторінка CMS обмежена 20 MiB.
18. При холодному збої CMS не повертається успішна порожня бібліотека. Для головної сторінки є окремий стан недоступності бібліотеки; статті не перетворюються на хибний 404 через підставлений порожній список.
19. Час використання останнього підтвердженого CMS-кешу при збої скорочено до 5 хвилин; звичайний TTL — 60 с.
20. Редагування й видалення перевіряють ревізію матеріалу. Застаріла форма не перезаписує нові зміни. Перейменування slug і перенесення між новинами/гайдами виконуються транзакційно.
21. Нові обкладинки зберігають відносну адресу, без прив’язки до `guild` або `admin`. Старі збережені адреси нормалізуються до ідентифікатора медіа; звернення до старого домену для них не потрібне.
22. Публічний сайт отримує обкладинку через власний домен, перевіряє тип, розмір до 8 MiB та відповідність SHA-256. Приватні заголовки upstream не видаються браузеру.
23. Виправлено preview обкладинки в редакторі: адреса `/api/site/media/...` відкривається на дашборді, а не помилково підставляється до адреси публічного сайту.
24. Ліміт Nginx для створення/оновлення CMS піднято до 10 MiB, що узгоджує 8 MiB зображення з текстом та multipart. Загальний ліміт інших endpoint-ів не збільшено.

### Повнота джерел і runtime

25. Прибрано статичний YAML-знімок гільдії. Немає підміни відсутніх актуальних даних старим складом. Холодний збій повертає 503; клієнт може повторити запит без перезавантаження.
26. Дашборд не оголошує неініціалізований склад новим порожнім live-знімком. Помилки джерела відображаються через стан застарілості, якщо підтверджені дані вже є.
27. Каталог рейдових ілюстрацій читається локально із комплекту дашборда, без GitHub Contents API.
28. Діагностика заявок перевіряє PostgreSQL, а не GitHub Issues.
29. Версії Next, React, React DOM і Sharp узгоджено з наданим сайтом та Docker-пінами: 16.3.5 / 19.2.8 / 19.2.8 / 0.35.4.
30. Для сайту явно задано корінь tracing/Turbopack. Наявність батьківського репозиторію або lockfile не повинна змінювати шлях standalone `server.js`.
31. Nginx отримав окремий `public-site.conf`, явно змонтований у Compose. Повторне оновлення дашборда не вимагає ручного дописування блоків сайту.
32. Додано HTTP/HTTPS-перенаправлення www на канонічний домен. Docker DNS використовується для оновлення адрес upstream після незалежного пересоздання контейнерів.

## Що видалено

- Jekyll-дерево, його сторінки, старі `_guides`/`_news` як локальні джерела сайту, CNAME та Python/update-data workflow старого статичного процесу.
- Статичні `_data/guild.yml` і `_data/raids.yml` як запасне джерело актуальної гільдії.
- Firebase Admin SDK і вибір Firestore як резервної БД.
- Read-through/backfill із Firestore для Discord-взаємодій.
- Панельний API й форму імпорту Firestore-профілів, старий runtime-скрипт міграції.
- Читання/запис старих поодиноких документів складу гільдії. Залишено чинне chunk-сховище.
- GitHub Issues/Contents як джерела заявок, перевірок або каталогу рейдових зображень.
- Застарілі назви модулів сховища: активні модулі тепер `documentDb`, `storageAccess`, `documentValues`, `applicationsStore`.

Збережено чинні PostgreSQL-колекції та ідентифікатори даних. Парсери історичних записів і redirects старих `.html` URL не запускають стару інфраструктуру. Вони зберігають доступність уже створеного вмісту. Одноразовий SQL-імпорт статей залишено окремо й не використовується як live-джерело. Довідники професій, спільнот і авторських персонажів лишаються статичними ресурсами сайту з відповідними позначеннями.

## Порядок оновлення VPS

Оновлювати обидва архіви в одному вікні обслуговування: старий сайт не підтримує новий CMS v2 і новий POST-транспорт.

### 1. Резервна копія перед заміною вихідних кодів

На чинній старій версії:

```bash
cd /srv/mistblossom
make backup
```

Зберегти також чинні env та `deploy/nginx`. У резервних копіях env є секрети: права мають бути 600, вони не повинні потрапляти до публічного каталогу. Запам’ятати поточні Docker image ID для обох проєктів.

### 2. Розпакувати парні архіви

Новий dashboard-архів має кореневу папку `mistblossom`, site-архів — `lihvodruida-site`. Вони призначені для `/srv/mistblossom` і `/srv/lihvodruida-site`.

```bash
unzip -o /tmp/lihvodruida-dashboard-v3.9.1-sync-fix.zip -d /srv
unzip -o /tmp/lihvodruida-site-v4.1.1-sync-fix.zip -d /srv
python3 /srv/mistblossom/deploy/prepare-unified-env.py --site-dir /srv/lihvodruida-site
```

За потреби використати sudo тільки для прав запису. Архіви не містять робочих `.env`, `.env.production`, секретів, node_modules чи `.next`.

Скрипт переносить `FIREBASE_*`/`FIRESTORE_*` налаштування робочого адаптера до `STORAGE_*`, прибирає непотрібні зовнішні ключі, зберігає решту параметрів і резервні копії env. При вже заданих різних токенах або різних значеннях старого й нового параметра він зупиняється до перезапису наявних файлів. Не обирає один із конфліктних секретів мовчки.

`DATABASE_URL` має вже вказувати на поточний PostgreSQL. Цей реліз не переносить живу Firestore-базу автоматично. Якщо PostgreSQL не містить потрібних даних, спочатку потрібне їх окреме перевірене перенесення з резервної копії.

### 3. Перевірити Compose та оновити дашборд

```bash
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
```

`make rebuild-dashboard` також застосовує актуальний `schema.sql`. Чинний бот не потребує зміни Discord custom_id-контракту для цього релізу. Після оновлення дашборда перевірити його healthcheck і журнали.

### 4. Оновити Nginx

Сертифікати обох доменів мають існувати у чинному letsencrypt volume. Для публічного сайту використовується сертифікат `lihvodruida.pp.ua`, який також містить www.

У новому `dashboard.conf` немає вручну дописаних блоків публічного сайту. Вони знаходяться в `public-site.conf`; не додавати ще одну копію. Якщо раніше використовувався окремий override із додатковим public-site mount, прибрати дублювання цього mount/server block.

```bash
cd /srv/mistblossom
docker compose -p mistblossom run --rm --no-deps nginx nginx -t
docker compose -p mistblossom up -d --no-deps --force-recreate nginx
```

Самого `nginx -s reload` під час першого переходу недостатньо: Compose має додати новий bind mount `public-site.conf`.

### 5. Оновити сайт

```bash
cd /srv/lihvodruida-site
make check
make deploy
curl --fail https://lihvodruida.pp.ua/site-api/v1/status
```

Відповідь має містити `{"ok":true,"integration":"ready","service":"lihvodruida-site","api_base":"/site-api/v1"}`. На відміну від healthcheck, вона підтверджує доступ до сумісного дашборда з потрібними таблицями БД. Readiness не підтверджує актуальність складу або доставку Discord-повідомлень.

### 6. Приймання на живому середовищі

- Відкрити склад і прогрес на ПК та телефоні, перевірити timestamp і фонове оновлення.
- Створити тестову заявку зі своїм контактом; перевірити квитанцію, запис у панелі та повідомлення в налаштованому Discord-каналі.
- Повторити заявку й переконатися у відсутності другого запису; змінити статус через панель і звірити сайт та Discord.
- Створити/відредагувати гайд з обкладинкою, дочекатися до 60 с кешу, перевірити сторінку, RSS і sitemap; видалити тестовий матеріал.
- Відкрити один матеріал у двох вкладках: після збереження першої друга має отримати конфлікт ревізії.
- Перевірити www → канонічний домен і відсутність 421/502 у журналах.

## Перевірки цієї поставки

- TypeScript і ESLint дашборда; повний `build:ci` з наявними регресійними перевірками та новим `check:site-integration`.
- Production standalone дашборда: 7 сценаріїв, включно зі стартом сервера, статикою й Sharp.
- Тести сайту: 27 сценаріїв із парною перевіркою справжнього dashboard route handler; БД/Discord у цьому сценарії контрольовані.
- Production standalone сайту: 7 сценаріїв із HTTP-запитами до зібраного сервера та контрольованого upstream.
- Оркестрація деплою: 16 сценаріїв із фальшивим Docker CLI, включно з відкатом при несправній інтеграції.
- Підготовка env: 4 сценарії — перенесення, повторний запуск і відмова при конфліктах.
- `git diff --check`, звіряння контракту заявки та перевірка відсутності Firebase SDK у dependency lockfile.

Docker CLI і локальний сервер тестового PostgreSQL у цьому середовищі недоступні. Повний `docker build`, фактичний `nginx -t`, справжні SQL-конкурентні сценарії, поточні дані VPS і жива доставка Discord тут не виконувалися. Вони не позначені як підтверджені. Перед запуском Nginx команду перевірки наведено вище.

Динамічний upstream оформлено за офіційною документацією Nginx: `resolve` потребує shared zone і resolver у http/upstream context; використовується образ 1.30.4. Джерело: https://nginx.org/en/docs/http/ngx_http_upstream_module.html#resolve.
