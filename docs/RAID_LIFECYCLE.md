# Raid lifecycle — per-record task scheduler

Автоматизація рейдів більше не покладається на широкий щохвилинний scan і не
чекає взаємодії користувача з Discord-кнопкою. Кожен опублікований рейд має
власні записи у `dashboardRaidLifecycleTasks` з абсолютними `scheduledAtMs` і
`dueAtMs`.

VPS-контейнер `cron` викликає `POST /api/raids/lifecycle` щохвилини. Звичайний
tick читає тільки задачі, де `dueAtMs <= now`, у порядку їхнього дедлайну.
На старті cron-контейнера і на початку кожної години запускається bounded
`?sweep=1&limit=100`: він не виконує стару lifecycle-логіку напряму, а
відновлює/звіряє task plan для legacy або пропущених raid records, після чого
обробляє вже due tasks.

## Окремі задачі одного рейду

Для кожного рейду плануються незалежні задачі:

- `registration_close` — точний час закриття запису. Якщо
  `registrationLockEnabled=true`, це `raid start - registrationLockMinutesBefore`;
  інакше — точний час старту рейду.
- `discord_close_sync` — окремий retry вимкнення Discord-компонентів, якщо БД
  вже закрита, а Discord не підтвердив оновлення повідомлення.
- `reminder_send` — `raid start - 15 хв`: публічне нагадування в текстовий канал + приватні DM усім активним записам (`БУДУ`, `50/50`, `ЗАТРИМАЮСЬ`), включно з лавою.
- `reminder_delete` — `raid start + 4 год`, якщо reminder був створений.
- `discord_delete` — `raid start + 24 год` для основного Discord-повідомлення.

Редагування дати/часу/текстового або голосового каналу перебудовує/оновлює reminder state тільки конкретного рейду.
Публікація створює задачі, ручне закриття прибирає `registration_close` та за
потреби створює `discord_close_sync`, а ручне видалення рейду прибирає всі його
lifecycle tasks.

## Виконання та повтори

Кожна due-задача claim-иться транзакцією (`lockId`, `lockedAtMs`) перед
виконанням. Це не дозволяє двом cron/process запускам виконати одну й ту саму
дію одночасно.

Після успіху видаляється тільки виконана task record, а task plan цього рейду
звіряється з його новим станом. Наприклад, після `registration_close` може
залишитися `discord_delete`, а після `reminder_send` автоматично з'являється
`reminder_delete`.

Якщо Discord або БД тимчасово недоступні, task не губиться: lock скидається,
`dueAtMs` переноситься на retry з bounded exponential backoff (1–15 хв), а
`scheduledAtMs` лишається незмінним — тобто видно первинний точний дедлайн.

## Discord та interaction path

Кнопка користувача більше не є механізмом, який «дозакриває» рейд. Якщо
дедлайн уже настав, interaction одразу відмовляє у зміні складу через
`isRaidClosed()`, але побічні дії — запис `status=closed`, вимкнення компонентів,
видалення reminder/основного повідомлення — виконує тільки task worker.

Це прибирає ситуацію, коли прострочене Discord-повідомлення лишається активним
до першого кліку.

## Recovery

Recovery sweep потрібен лише для:

- рейдів, створених до появи task scheduler;
- відновлення після тривалого простою або ручних змін у БД;
- ремонту відсутньої/застарілої task record.

Основний щохвилинний шлях не сканує рейди за датами або статусом — він працює
по індексованому `dueAtMs`. Для PostgreSQL document store є окремий
`documents_due_at_idx`.
