# Discord: єдине меню запису на рейд

Dashboard **3.8.86**, bot **3.6.8**, shared contract **1.1.0**. Дата: 14.10.2026.
Підготовлено вихідний код; на VPS не розгорнуто. Попередні зміни R1–R6.8 і hotfix 3.8.85 збережені. Цей реліз не завершує решту R6, R7 чи R8.

## Сценарій учасника

У повідомленні рейду залишається одна кнопка **«Записатися в рейд»**. Вона відкриває особисте меню, видиме лише учаснику. В обох випадках завжди доступні **«Мої персонажі»** та **«Інший / вручну»**. Без прив’язаних персонажів меню пояснює, як записатися вручну.

Після вибору свого персонажа або класу й спеціалізації вручну учасник відкриває форму Discord. У ній обирає участь, роль (танк / цілитель / DPS) та прапорець **«Нагадати в особисті за 15 хвилин»**. Роль можна змінювати в обох режимах. Ручний запис доступний без акаунта сайту і без підтвердження РЛ, зокрема для рейдів з мінімальним ilvl. Наявні правила перевірки ilvl прив’язаного персонажа збережені.

Вибір у меню не записує учасника в рейд. Запис і налаштування нагадування зберігаються разом після відправлення форми. Закриття форми без підтвердження нічого не змінює. Окрема кнопка «Пропустити рейд» також веде до підтвердження у формі.

## Особисті нагадування

Налаштування спільне для всіх рейдів конкретного Discord ID. Початкове значення — увімкнено. Канонічний запис зберігається в `discordNotificationPreferences/<discordId>` незалежно від існування профілю сайту. Реєстрація та наступні входи підтягують цей стан у профіль; паралельна реєстрація й вимкнення серіалізуються транзакцією.

Змінювати прапорець можна у формі запису або в налаштуваннях власного Discord-профілю на сайті. Старе відкрите меню не може повернути попереднє значення поверх новішої зміни. API не дозволяє редагувати іншого користувача або діяти через impersonation.

Виконавець нагадувань читає налаштування перед фактичним Discord-запитом, після очікування в черзі та обмежень швидкості. Вимкнені адресати пропускаються. Якщо БД недоступна, виконавець не надсилає повідомлення на основі припущення про згоду. Відкликати вже відправлений запит неможливо. Звичайні повідомлення рейду в каналі не залежать від особистого прапорця.

## Сумісність, збереження та реакція

Усі дев’ять старих сімейств кнопок/виборів запису переведено на відкриття нового меню. Вони не виконують старий запис без підтвердження. Візуальне оновлення збережених публічних повідомлень проходить через чинний lifecycle recovery: PATCH наявного повідомлення, до трьох спроб за прохід, повтор невдалої спроби через 15 хвилин. Нові публічні повідомлення для заміни меню не створюються.

Чернетки `discordRaidSignupMenus` зберігаються 20 хвилин. Власник, сервер, ревізія, строк дії, стан запису та ревізія глобальної переваги перевіряються до commit. Повторне або паралельне підтвердження не створює другого запису. Прострочені чернетки прибирає чинний logs-maintenance.

Підписана кнопка відкриття фінальної форми отримує безпосередню відповідь type 9 від бота, без проходу через БД або чергу. Modal submit type 5 спочатку потрапляє в збережений ingress і лише потім підтверджується; наявні receipt, lease та outbox збережено. Відкриття й підтвердження меню не запускають синхронне оновлення Blizzard: використовуються збережені персонажі. Дедлайни й прискорене пробудження черг з попередніх релізів збережені.

Використано нативні String Select і Checkbox (type 23) усередині Label у modal. Контракт перевірено за [Discord Component Reference](https://docs.discord.com/developers/components/reference#checkbox) і [Using Modal Components](https://docs.discord.com/developers/components/using-modal-components).

## Оновлення

Оновити **dashboard і bot разом**, разом зі спільним пакетом `shared/`. Перебудувати обидва образи за штатною процедурою. Нових секретів, окремої cron-задачі або SQL-міграції немає: використовується наявне сховище документів. Чинні lifecycle recovery та maintenance мають продовжувати виконуватися.

## Перевірки та межі

25 поведінкових перевірок меню, збереження нагадувань, API, старих кнопок, конкурентних змін і реєстрації; 54 тести бота, включно з HTTP-взаємодіями з реальними тестовими підписами. Додатково виконуються повний `verify`, строгий TypeScript, runtime security, production build і HTTP smoke. Остаточні результати наведено в `DISCORD_RAID_SIGNUP_MENU_VALIDATION_2026-10-14.json`.

Транзакційні сценарії перевірені на контрольованому сховищі з відкатом та вимогою читань перед записами. Живого інтеграційного прогону PostgreSQL/Firestore, відправлення повідомлень у Discord і перевірки мобільного Discord-клієнта не виконувалось. Локальна збірка використовує той самий security overlay залежностей, що 3.8.85. Два попередні попередження трасування динамічних filesystem-шляхів у `discordWelcomeCard.ts` не стосуються нового меню.
