# Історія сезонів і синхронізація — Dashboard 3.13.0 / Site 4.3.0

Повні оновлення поверх Dashboard 3.12.0 і Site 4.2.1. Збережено попередні виправлення заявок, CMS та відновлення зв’язку. Код виправлено й перевірено локально; робочий VPS у цьому сеансі не змінювався.

## Що спричиняло втрату даних

Під час читання публічного API дашборда 16.10.2026 сезон `mn-1` містив лише Sporefall: рейд `tier-mn-1` із фактичним прогресом гільдії **2/9M** був відсутній у сезоні. Аналогічно `tww-1` не містив Nerub-ar Palace. Статичні дані Raider.IO показують, що ці рейди відкрилися за тиждень до M+ сезону. Попередній відбір вимагав початку рейду після початку сезону й відкидав їх.

Стандартний `guilds/profile` повертав лише поточне доповнення. Непорожня часткова відповідь замінювала весь масив прогресу, тому старі рядки втрачалися. Кілька `raid_progression:slug` в одному запиті також не збирають історію: під час перевірки API повернув лише останній запитаний рейд. `raid_progression:all` повернув порожній об’єкт. Новий збір використовує окремий запит для кожного рейду.

Сайт показував відсутній прогрес як `0`. Тепер нуль означає отриманий і перевірений нульовий результат, а відсутність даних — `—` із поясненням.

Публічний `https://lihvodruida.pp.ua/site-api/v1/guild` під час цієї інспекції повернув **404 HTML**, тоді як `https://guild.lihvodruida.pp.ua/api/site/guild` повернув **200 JSON**. Отже, оновлену пару ще потрібно розгорнути: локальні тести не підтверджують працездатність нового маршруту на чинному домені.

## Нова поведінка

- Каталог основних сезонів від Legion до чинного доповнення будується зі статичних API Raider.IO. Майбутні й позасезонні події не потрапляють до вибору. Відомі часові інтервали рейдів і сезонів порівнюються за перетином; якщо закінчення рейду відсутнє, допускається відкриття до 14 діб перед початком сезону. Це обмежене правило для неповних метаданих, а не підміна відсутньої історичної інформації.
- Успішні метадані поточного сезону мають TTL 6 годин, минулих доповнень — 7 днів. Частковий збій повторюється після 5 хвилин. Збережений каталог не стирається; повний збій не змінює дату фактичного визначення сезону. Збій чинного доповнення не перемикає сайт на старий сезон.
- Історія гільдії зберігається незалежно від складу в PostgreSQL, колекція `guildRaidHistory`. Чинний cron `/api/guild/sync` раз на 120 секунд перевіряє до чотирьох рейдів, одночасно — не більше двох. Один профільний HTTP-запит має timeout 5 секунд і не повторюється всередині тієї ж спроби. Перевіряються назва гільдії, реалм, регіон і наявність саме запитаного рейду.
- Контрольні записи дозволяють продовжити збір після повторного завантаження процесу. Перевірені старі рейди оновлюються раз на 7 днів, поточні — раз на 6 годин; помилки мають паузу щонайменше 5 хвилин. Provider cooldown обмежує повтори після 429. Невдала перевірка залишає останні підтверджені значення й позначає їх збереженими.
- Неповна відповідь профілю зливається за slug із попередньою історією. Дата нового оновлення складу не видається за дату перевірки старого рейду. Недійсні лічильники не перезаписують перевірені дані.
- Читання сайтом і дашбордом використовує спільний збережений результат; браузер не збирає дані Raider.IO. Оновлення історії змінює публічну ревізію `guild`, тож сайт отримує їх до закінчення звичайного TTL. Порожній cron-прохід не переписує історію й не спричиняє зайве оновлення сайту. Чанки складу не перезаписуються для історичних рейдів.
- Сезони на сайті згруповано за доповненням. Вибір сезону зберігається під час фонових оновлень; якщо сезон більше не існує, вибирається поточний. Показано дату перевірки, невідомі та збережені результати, повідомлення про неповну історію. Readiness Site 4.3.0 вимагає capability `guild:raid-history:v2`.

Прогрес — поточні підтверджені дані **гільдії для конкретного рейду**. Це не сума досягнень персонажів і не незмінний знімок на дату закриття сезону. Доступні старі сезони залежать від метаданих Raider.IO; дані до Legion або відсутні в API не вигадуються. Початкове наповнення відбувається поступово, за кілька проходів cron, із паузами при помилках і лімітах API.

| Перевірка | Результат |

| ZIP: центральний каталог, CRC, SHA-256 кожного файла | Перевірка під час пакування та після збереження |

Браузер перевірив старі сезони, перехід від невідомого значення до перевіреного `0/8`, зміну `2/9M` на `3/9M` після ревізії, збереження вибору сезону та відсутність повного перезавантаження. Перевірено ширини 320/390/1440 px без горизонтального переповнення. Також пройшли форма заявки, зміна її статусу, відновлення онлайн/видимості вкладки, редагування й зняття публікації CMS та оновлення каталогу модів. Браузерний тест використовує контрольовані значення прогресу; це не зміна живих даних гільдії.

Новий набір дашборда запускається командою `npm run check:raid-history` і включений у `verify`/`build:ci`. Для повних парних тестів сайту задаються `PAIRED_DASHBOARD_ROOT` (каталог dashboard) та `SITE_SYNC_PG_MODULE` (абсолютний шлях до встановленого `@electric-sql/pglite`).

Використано справжній PostgreSQL document adapter, SQL ревізій і lease в ізольованій PostgreSQL WASM. Зовнішні відповіді в тестах контрольовані; тести не створювали живих заявок, матеріалів або Discord-повідомлень. Docker build, nginx -t, робоча PostgreSQL і фактичний деплой на VPS не виконувалися.

## Встановлення

Зберегти резервну копію БД, чинних `.env`, Nginx-конфігурації та попередніх образів. Архіви розпаковуються в чинні каталоги; `.env` до архівів не входять. Нових секретів, портів або окремої таблиці немає. Використовується чинна таблиця `documents`; штатний `make rebuild-dashboard` застосовує актуальну `schema.sql`.

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.13.0-raid-history.zip
unzip -t /tmp/lihvodruida-site-v4.3.0-raid-history.zip
unzip -o /tmp/lihvodruida-dashboard-v3.13.0-raid-history.zip -d /srv
unzip -o /tmp/lihvodruida-site-v4.3.0-raid-history.zip -d /srv
python3 /srv/mistblossom/deploy/prepare-unified-env.py --site-dir /srv/lihvodruida-site
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
docker compose -p mistblossom up -d --no-deps --no-build --pull never --force-recreate cron
make internal-check
make guild-sync
cd /srv/lihvodruida-site
make check
make deploy
node scripts/check-deployed.mjs
```

Спочатку Dashboard 3.13.0, потім Site 4.3.0. `make guild-sync` виконує штатну синхронізацію складу, а не лише історію; її запуск також може оновити персональні API-дані. Для звичайного поступового збору достатньо активного cron. Якщо старий парний перехід ще не завершено, перевірити приватну Docker-мережу, однаковий bridge token, маршрут Nginx і сертифікат за попередніми інструкціями інтеграції.

Після встановлення один раз перезавантажити вкладки для нового JavaScript. Перевірити `/site-api/v1/status` (`integration: ready`) та `/site-api/v1/guild` (200 JSON; `data.raid_seasons.schema_version: 2`, `data.metadata.raid_history`). Перемкнути минулі сезони: потрібні рейди мають бути в переліку, перевірені значення — відображатись, відсутні — залишатися рискою. У міру роботи cron показники `pending` і `failed` дозволяють відрізнити початкове наповнення від проблем API. Стан `partial` не означає втрату вже перевірених даних.

Публічні `/site-api/v1/*` не повинні кешуватися примусовими правилами CDN чи повертати HTML старого маршрутизатора. Скрипт деплою перевіряє нові публічні маршрути й readiness; healthy контейнера сам по собі не підтверджує інтеграцію.

Права стороннього CurseForge API та його HTTP 403 потребують чинного серверного ключа; цей реліз не змінює доступу до стороннього сервісу.
