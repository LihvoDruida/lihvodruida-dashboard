# Dashboard 3.10.1 — надійність CMS

Продовження релізу 3.10.0. Сумісний із Site 4.1.1; для цього оновлення достатньо замінити дашборд. Зміни підготовлено й перевірено локально. Живі матеріали, VPS та Cloudflare у цьому сеансі не змінювалися.

## Підтверджені помилки та виправлення

### 1. Стара вкладка могла перезаписати новий матеріал

Дефект відтворено на справжній логіці CMS із контрольованим сховищем: створити матеріал із ревізією `1`, видалити, створити інший за тією самою адресою. Другий матеріал також отримував `1`; стара вкладка проходила перевірку й перезаписувала новий запис.

Тепер кожне створення та збереження отримує унікальний токен ревізії. Сервер звіряє саме його. Повторне використання адреси не робить стару форму чинною; застарілі збереження та видалення повертають 409. Внутрішній числовий лічильник змін збережено, але він більше не є єдиним захистом.

Старі записи з числовою ревізією залишаються доступними. Перше успішне редагування додає новий токен. SQL-міграція не потрібна. Після встановлення слід перезавантажити редактори зі старим JavaScript; перед цим зберегти незбережений текст у .md або серверну чернетку.

### 2. Повтор створення після втрати відповіді

Редактор створює ідентифікатор однієї спроби й зберігає його разом із копією тексту. Відбиток форми враховує текстові поля й байти вибраної обкладинки, незалежно від випадкової multipart-межі.

Сервер в одній транзакції записує матеріал та коротке підтвердження операції в PostgreSQL. Операція прив’язана до облікового запису редактора й нормалізованого вмісту. Повтор повертає той самий матеріал і ревізію, якщо запис відтоді не змінювався. Повторне підтвердження не створює нового матеріалу або другого аудиту створення.

Якщо хтось уже змінив, перейменував або видалив запис, повтор не відновлює його й не перезаписує нову версію: він повертає конфлікт і просить перевірити бібліотеку. Інший вміст під тим самим ідентифікатором також відхиляється.

Це гарантія для створення. Для редагування після невизначеного результату залишається перевірка поточної ревізії та порівняння з актуальною версією; автоматичного злиття текстів немає.

### 3. Копія відновлення могла зникнути до рішення користувача

Поки показано пропозицію відновити незбережений текст, нове введення більше не перезаписує знайдену копію. Перед збереженням потрібно вибрати «Відновити текст» або «Відкинути копію». Якщо вже введено новий текст, відновлення запитує підтвердження його заміни.

Копія записується також під час приховування/закриття вкладки, тому швидке перезавантаження не чекає звичайної затримки 700 мс. Повернення всіх полів до збереженого стану прибирає застарілу копію. Недоступність browser storage тепер показується явно; можна зберегти серверну чернетку або експортувати .md.

Відновлення, як і раніше, діє в тій самій вкладці й для того самого користувача. Файл обкладинки після перезавантаження треба вибрати повторно. Якщо вибрано той самий файл і вміст форми не змінено, відбиток спроби залишається стабільним.

### 4. Некоректна відповідь могла зламати бібліотеку

Перед заміною бібліотеки перевіряється структура отриманого списку. Некоректна відповідь залишає попередні матеріали на екрані; повторне оновлення зберігає пошук і фільтри. Запит скасовується при виході зі сторінки й має часовий ліміт.

### 5. Збій сховища більше не маскується як помилка полів

Валідація повертає 400, конфлікт ревізії/адреси — 409, а недоступність сховища — 503 із безпечним повідомленням. Технічні подробиці підключення не потрапляють у відповідь редактора. Форма залишається відкритою.

| Production standalone дашборда | 7/7 |
| TypeScript, ESLint, `git diff --check` | Успішно |

Повний `build:ci` пройшов. Після остаточного уточнення відповідей 503 повторено цільові тести API, production-збірку, standalone, TypeScript і ESLint.

Нові серверні сценарії перевіряють повторне використання адреси, старі числові ревізії, 12 одночасних повторів одного створення, прив’язку операції до редактора, зміну вмісту, повтор після видалення й некоректний список.

Браузер працює зі справжніми компонентами й route handlers, а сесія та сховище контрольовані. Для перевірки невизначеного результату справжній handler спочатку записує матеріал, після чого тестовий транспорт обриває JSON-квитанцію. Після перезавантаження, відновлення тексту й повтору другого матеріалу немає. Окремо перевірено швидке перезавантаження та збереження копії до вибору користувача.

Ці перевірки не є прийманням на живій PostgreSQL чи VPS. Docker daemon і доступ до поточного сервера в цьому сеансі відсутні.

## Встановлення

Архів повний, кореневий каталог — `mistblossom`. Він містить усі попередні зміни CMS та синхронізації, без робочих env, секретів, node_modules і .next. Перед заміною зберегти БД, env і поточний образ.

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.10.1-content-reliability.zip
unzip -o /tmp/lihvodruida-dashboard-v3.10.1-content-reliability.zip -d /srv
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
```

Після оновлення перезавантажити відкриті редактори. Наявний Site 4.1.1 не потребує нового архіву. Якщо попередній перехід ще не виконано, налаштування токена, приватної мережі, старого Worker-route та CurseForge лишаються обов’язковими за `SYNC_INSPECTION_2026-10-16_UA.md`.

Не повертати 3.9.1 поверх колекції з чернетками без окремої підготовки: той producer ще не фільтрує стан чернеток. Цей ризик відкату описано також у звіті 3.10.0.

## Приймання після встановлення

1. Створити й видалити тестову чернетку; створити іншу за тією самою адресою. Стара вкладка має отримати конфлікт збереження та видалення.
2. Відкрити матеріал у двох вкладках, змінити його в першій, перевірити відмову застарілого збереження в другій без втрати тексту.
3. Ввести текст і відразу перезавантажити вкладку. Перед відновленням ввести інший текст і перезавантажити ще раз: початкова копія має зберегтися.
4. Перевірити створення чернетки, публікацію, обкладинку й оновлення бібліотеки. Сайт підхоплює публікації за правилами попереднього CMS-кешу.
