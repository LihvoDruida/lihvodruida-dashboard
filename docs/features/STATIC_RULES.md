# Статик — інструкція розгортання та безпека

## Маршрути

- `/discord/static` — редактор правил, реєстр, 24-годинні запрошення, журнал подій; потрібна Dashboard Discord-сесія.
- `/static/accept?t=...` — публічні правила за **спільним** токеном; ніякої авторизації на сайті.
- `/api/static/accept` (GET/POST), `/api/static/status` (GET) — публічні, з перевіркою токена, обмеженнями та no-store.
- `/api/static/manage` — авторизований API; запис лише для РЛ із налаштованою Discord-роллю, адміністратора або власника.
- `/api/internal/discord/static-confirm` — лише внутрішній запит бота, `INTERNAL_API_TOKEN`.

## Підготовка

1. Підключіть `DATABASE_URL` (PostgreSQL) або активну Firebase Firestore конфігурацію; нові документи зберігаються в чинному документному сховищі.
2. Налаштуйте `DISCORD_GUILD_ID`, `DISCORD_BOT_TOKEN` у dashboard, `INTERNAL_API_TOKEN` **однаковий** в dashboard і bot, `DASHBOARD_INTERNAL_URL=http://dashboard:3000` для бота (або власний внутрішній hostname), `DISCORD_GATEWAY_ENABLED=1`.
3. Бот повинен працювати в Discord Gateway (GUILDS, GUILD_MEMBERS, DIRECT_MESSAGES) і мати дозвіл **Manage Roles**. Роль бота має бути вище ролі «Статик».
4. Власник/адміністратор панелі переходить у `/discord/static` і задає ID двох різних ролей: **учасник Статика** та **відповідальний РЛ**. Альтернативно можна початково встановити `STATIC_MEMBER_ROLE_ID` і `STATIC_MANAGER_ROLE_ID` у dashboard env.
5. Уповноважений РЛ або власник додає окремі правила Статика, після чого створює спільне запрошення на 24 години. **Скопіюйте URL відразу**: сервер зберігає тільки SHA-256 токена.

## Прийняття

Кандидат відкриває URL без входу, читає правила, позначає згоду, отримує короткочасний випадковий код (10 хвилин або до закінчення посилання), надсилає боту **в особистому повідомленні** `статик КОД`. Авторитетним джерелом Discord ID є лише gateway event бота. Панель live-перевіряє наявність користувача на сервері, налаштованість і керованість ролі, чинність токена, актуальність версії правил, блокування після виключення. Тільки тоді видає Discord-роль і записує згоду. Публічна сторінка опитує статус за кодом + окремим 256-бітним секретом браузера.

**Не підтримується** прийняття введенням довільного Discord ID або передача користувацьких ID через спільний URL. Посилання можна переслати будь-якому учаснику Discord-сервера: ця схема не є персональним запрошенням від РЛ.

## Доступи

- РЛ з ID налаштованої Discord-ролі: перегляд і редагування **лише** Статика, генерація/відкликання токенів, керування його учасниками.
- Адмін і власник сервера: те саме + налаштування ID ролей.
- Офіцери та інші авторизовані Discord-користувачі сервера: тільки перегляд.
- Анонімний відвідувач із чинним токеном: тільки читання правил і створення заявки на прийняття.

## Важливі обмеження

- Роль **не знімається автоматично у всіх існуючих рейдерів** під час деплою: це потенційно руйнівна міграція, для якої необхідне окреме підтвердження/план.
- Видалення з реєстру блокує повторне прийняття навіть через чинне посилання. Для повернення РЛ має скасувати блокування, а кандидат прийняти правила повторно.
- Після оновлення тексту правил нові заявки підписують нову версію; вже видані ролі не зникають автоматично.
- Масове оновлення ролей/рольової ієрархії виконуйте окремо; API забороняє зміну ID ролі Статика при наявності активних підписантів.
- Автоматизоване тестування без діючого Discord guild, БД та секретів не доводить успішну реальну видачу ролей. Перед production проведіть end-to-end DM-тест у тестовій ролі.
