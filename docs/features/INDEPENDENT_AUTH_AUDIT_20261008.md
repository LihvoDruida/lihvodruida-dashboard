# Незалежний аудит авторизації — v3.8.58 (08.10.2026)

## Метод

Замість існуючих `check-login`, `check-api-security`, `check-*` та інших проєктних скриптів створено **новий окремий** інструмент `qa/independent-auth-lifecycle.cjs` на Node.js `node:test`.

Інструмент транспілює **реальні вихідні** TypeScript-файли за допомогою TypeScript та запускає їх в окремих VM-контекстах. Зовнішні межі (`cookies()`, Discord API, `NextResponse`, `fetch`, ролі/сховище) підмінюються контрольованими відповідями, тому не потрібні токени реальних користувачів. Маршрути `api/auth/discord/start`, `api/auth/logout`, глобальний `proxy` і клієнтський session-check тестуються як виконуваний код, а не пошуком рядків. Проводився також незалежний синтаксичний розбір TS/TSX через TypeScript AST.

**Вихідна версія:** v3.8.57, від якої відгалужені ці правки.

## Фактично відтворені дефекти

1. При Discord API 500 і відсутності попередньої успішної перевірки `getSession()` повертав підписану cookie-сесію з правом `dashboard.view`.
2. Та сама помилка при quota/circuit-breaker: відсутність відповіді Discord не блокувала власника cookie.
3. Відсутність Discord bot/guild credentials у production трактувалась як достатня підстава довіряти сесії.
4. `impersonatedBy` оминав live Discord-перевірку взагалі: колишній власник міг зберігати видану раніше сесію в режимі «перегляд як група».
5. При недоступності Discord створювався новий «fallback»-кеш з неперевірених даних, який міг продовжувати життя старих доступів.
6. Явно вимкнений `SESSION_LIVE_ACCESS_SYNC_ENABLED` у production повертав поведінку без актуальної перевірки членства.
7. Сторінка `/applications` була дозволеною ціллю OAuth, але не входила до захисту серверного proxy і клієнтського session guard.
8. HTTP 5xx відповіді session API трактувалися клієнтським guard як валідний login, а не невизначений стан.
9. Після додавання нової ролі `ensureDiscordNewcomerBootstrapRole` live-сесія отримувала `member.roleIds` до bootstrap замість актуального `liveRoleIds`.

## Зміни

- `dashboard/src/lib/auth.ts`: правило fail-closed при відсутності підтвердженого членства; переперевірка власника під час impersonation; заборона вимкнення production-перевірки через env; відмова від кешування невдалих перевірок; правильні ролі після bootstrap.
- Під час короткого збою Discord можна використати **виключно вже підтверджені** права: максимум `DISCORD_LIVE_ACCESS_GRACE_SECONDS` (за замовчуванням 600 с) для звичайного читача, до 60 с для власника, адміна та будь-якої групи з правами запису/керування. Відсутність позитивного кешу означає відмову в доступі.
- `dashboard/src/proxy.ts`, `dashboard/src/components/ClientAuthGuard.tsx`: однаковий захист `/applications`, а також 5xx session-check — помилка, не підтвердження входу.
- Оновлено документацію конфігурації та повідомлення перевірки деплою.

## Результат автономної перевірки

Запуск з кореня репозиторію:

```bash
node --test qa/independent-auth-lifecycle.cjs
```

**24 із 24 нових тестів пройдено.** Ці тести не запускають і не використовують жоден з існуючих проєктних `check-*` скриптів. Вони перевіряють підпис/HMAC, строк дії, OAuth-state, open-redirect, успішне й помилкове членство, кеш позитивної перевірки та його старіння, impersonation, bootstrap, підозрілі cookies, два паралельні OAuth-входи, проксі-редирект, POST/GET logout, заборону міжсайтового logout та реакцію на 503.

Окремий синтаксичний скан TypeScript AST — **315 файлів TS/TSX/JS у src**, нуль помилок TS/TSX-синтаксису. Також `bash -n deploy/scripts/start.sh`, `node --check qa/independent-auth-lifecycle.cjs` і `git diff --check` — без помилок.

## Межі перевірки й залишкові ризики

- **Повний `npm ci` / TypeScript typecheck / Next.js production build тут не виконано:** залежностей Next.js у локальному середовищі немає. Синтаксичний розбір не заміняє компіляцію, а mocks не замінюють реальний Discord API.
- **Живий OAuth з Discord, reverse-proxy Cloudflare, браузерні cookies на справжньому HTTPS-домені та реальне відновлення сесії після перезапуску контейнера** потрібно окремо перевірити на staging/VPS.
- Підписана stateless-cookie після logout видаляється з браузера, але **копія токена, викрадена до виходу, не відкликається сервером миттєво**: доти діють строк його життя і перевірка Discord. Для гарантії серверного відкликання кожної сесії потрібен централізований реєстр revocation/session-id у БД.
- При недоступності Discord відвідувач без раніше успішної перевірки отримує тимчасову відмову в доступі. Це навмисний вибір на користь безпеки.
- Верифіковані кешовані ролі мають коротку затримку відкликання: у штатному режимі до `DISCORD_LIVE_ACCESS_SYNC_SECONDS` (типово 90 секунд), під час збою — див. grace вище. Для миттєвого блокування потрібне server-side revocation на зміні ролі.

## Перевірка після деплою

1. `make up` з v3.8.58, дочекатися повного `build:ci` й `health`.
2. У браузері інкогніто зайти через Discord учасником із дозволеною роллю, відкрити `/applications`, вийти, перевірити cookie й `GET /api/auth/session` → 401.
3. Перевірити повернення після OAuth до `/discord/static` і `/applications`, вхід двома вкладками та відмову сторонньому Discord-акаунту.
4. Переконатися, що зміна/зняття ролей позначається на доступі після TTL, а недоступність Discord не створює нових прав.
5. Перевірити режим «перегляд як група» власника, а потім його повернення; жоден звичайний учасник не повинен отримувати impersonation-права.
