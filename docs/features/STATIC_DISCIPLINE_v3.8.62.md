# Статик — склад, порушення, ban enforcement (v3.8.62)

## Навігація

- У глобальному меню видалені «Рейд-пули» (`/polls`) і «Формування складу» (`/roster`). Маршрути й API збережені.
- На `/raids` під правами керування рейдами є кнопки «Рейд-пули» та «Збір рейдового складу на сезон».
- Картку Raid Polls також прибрано з Discord-хабу, щоб єдиний шлях із навігації був через рейди.

## Склад Статика

- `/discord/static` — компактна таблиця у ритмі Guild: Discord-аватар, імʼя/username/ID, статус ролі, дата й версія прийняття, порушення 0–3, дії РЛ.
- Discord-імена й актуальні ролі беруться з кешованого server API (TTL 60 с). При збої показуються збережені імена й повідомлення про втрату live-синхронізації.
- Пошук і фільтри: у складі, усі, виключені, з порушеннями; адаптивний мобільний формат.
- РЛ і адмін можуть зафіксувати порушення або прибрати зі Статика. Для решти — лише перегляд.

## Порушення й банліст

- `/discord/static/bans` показує кожного учасника з хоча б одним поточним порушенням.
- У кожного три слоти, причина до 128 символів; зняти порушення може лише РЛ із призначеною роллю або адмін/власник.
- Третє порушення виконує Firestore-транзакцію, записує `banUntil` на **один календарний місяць (UTC, з коректним обмеженням дня місяця)**, змінює `status` на `removed`, після чого намагається зняти Discord-роль.
- Якщо Discord недоступний, заборона залишається в БД, операція повідомляє про відкладене зняття, бот повторить спробу.
- `blocked` (ручне виключення) — безстроковий доступний для розблокування прапор; `banUntil` — автоматичний дисциплінарний строк. Обидва забороняють повторну видачу ролі.
- Скасування порушення, що спричинило бан, знімає часовий бан, **але роль не повертає автоматично**. Після завершення місячного бану при новому підтвердженні правил чинні порушення обнуляються (журнал подій зберігає історію).

## Discord-бот і захист

- Внутрішній `POST /api/internal/discord/static-enforce`, доступ лише через INTERNAL_API_TOKEN і правильний guildId.
- На `GUILD_MEMBER_UPDATE` і `GUILD_MEMBER_ADD` бот запитує перевірку заборони та ролі (обмеження частоти — 15 с на учасника).
- Після Ready бот робить початковий sweep; далі щогодини перевіряє реєстр виключень і чинних банів. Зайві Discord DELETE не виконуються, якщо ролі фактично немає.
- Перевірка повторного прийняття правил відмовляє під час чинного `banUntil`, навіть якщо роль призначили вручну.
- Журнал зберігає додавання/зняття порушень, блокування, виконане або відкладене зняття ролі.

## Перевірки та межі перевірки

- 12 незалежних поведінкових тестів Firestore/Discord, 9 незалежних тестів HTTP-перевірки RBAC/токена/CSRF.
- 47/47 доступних `check:`/`audit:`/`inspect:` скриптів; 33/33 Node-тестів бота.
- TypeScript/TSX transpile syntax-перевірка змінених файлів — пройдена.
- **Повний `tsc --noEmit`, Next.js production build та інтеграція з реальним Discord API тут не підтверджені**, оскільки потрібні встановлені залежності й робочий сервер/бот.

## Після деплою

1. Переконатися, що в налаштуваннях панелі є роль Статика та роль РЛ, а роль Статика нижче найвищої ролі бота.
2. Перевірити видалення ролі при третьому порушенні, повторне ручне призначення та отримання `role.enforced` у журналі.
3. Перевірити, що прострочений бан не блокує нового прийняття правил, але не видає роль автоматично.
4. Перевірити 1× годинний sweep і системні логи після перезапуску Gateway.
