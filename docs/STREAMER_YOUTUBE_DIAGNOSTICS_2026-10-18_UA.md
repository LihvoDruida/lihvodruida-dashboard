# Dashboard 3.15.1 — діагностика та виправлення додавання каналів

18 жовтня 2026 року. Сумісний із Site 4.6.1.

## Відтворені причини відмови

1. Старий парсер відхиляв реальні YouTube-посилання з `?si=…`, вкладками `/videos`, `/streams`, мобільним доменом, закодованими не-латинськими символами, а також нік без `@`.
2. За наявності ключа API збереження нового YouTube/Twitch-каналу синхронно залежало від доступності й авторизації платформи. Відмова Google, вичерпана квота або мережевий збій перешкоджали збереженню правильно заповненої конфігурації.
3. Нова форма завжди створювала порожню обов’язкову платформу Twitch. Для додавання лише YouTube її доводилося вручну прибирати.
4. Введення вже наявного Discord ID у новій формі приводило до конфлікту замість зрозумілого переходу до його платформ.
5. Різні адреси того самого YouTube-каналу могли залишатися різними неперевіреними записами до отримання канонічного ID. Потрібен захист у точці підтвердження й публікації.

Ці сценарії відтворено локально на фактичному коді. Доступу до виробничих токенів і VPS у цій роботі не було; конкретну серверну квоту або правильність установленого ключа API тут не підтверджено.

## Нове додавання

Натисни «Додати учасника», введи Discord ID і вибери потрібні платформи. Початкової обов’язкової Twitch-платформи більше немає. Кнопки вибору розташовані над полями. Під посиланням показано нормалізовану адресу, яка буде збережена.

У картці чинного учасника є прямі кнопки «Додати YouTube», «Додати Twitch» або «Додати TikTok» для відсутніх платформ. ID учасника й ревізії наявних каналів підставляються автоматично. Є також «Перевірити учасника» для цільової фонової перевірки.

Якщо у новій формі введено вже наявний Discord ID, з’являється пропозиція приєднати введені платформи до його картки. Введені значення зберігаються. Надсилання застарілої порожньої ревізії блокується до цього явного переходу.

## Збереження і перевірка — окремі операції

Збереження синтаксично правильних Twitch/YouTube-каналів більше не викликає API цих платформ. Доступність Google, правильність ключа або квота не є умовою збереження конфігурації. Discord-членство та права адміністратора/власника перевіряються як раніше.

Після збереження канал має стан очікування перевірки. Коли увімкнено моніторинг, worker підтверджує існування каналу, його ID, відео й LIVE. Відмова API зберігається як окремий зрозумілий статус із часом спроби та повтору; налаштування не зникають. Після відновлення API той самий запис відновлюється без повторного додавання.

Наявний успішно перевірений ID і стан незміненого каналу зберігаються під час додавання іншої платформи. Нова авторизація TikTok із явно введеними токенами, як і раніше, перевіряється перед їх шифруванням і збереженням. Можна підготувати TikTok-канал із порожніми токенами та підключити автора пізніше.

Тексти інтерфейсу розрізняють «канали збережено» і «платформу перевірено». Якщо моніторинг вимкнено, після збереження показано дію для його ввімкнення.

## Прийняті адреси

| Приклад | Результат |
|---|---|
| `@lihvo_druida` або `lihvo_druida` | YouTube handle |
| `https://www.youtube.com/@lihvo_druida?si=…` | Параметри поширення прибираються |
| `https://m.youtube.com/@lihvo_druida/videos` | Мобільний домен і вкладка нормалізуються |
| `youtube.com/@lihvo_druida/streams` | HTTPS додається, вкладка прибирається |
| `https://www.youtube.com/channel/UC…` | ID каналу |
| `https://www.youtube.com/user/LegacyUser` | Перевірка через офіційний forUsername |
| `https://www.youtube.com/c/LegacyName` | Обмежене визначення нового каналу через YouTube redirect/canonical, далі офіційний API |
| Посилання з закодованим українським handle | Декодування та нормалізація Unicode |

Підтримано звичайні вкладки каналу: videos, streams, shorts, featured, playlists, community, about, courses, podcasts. Для старого `/c/…`, який YouTube не дає визначити через дозволені перенаправлення або canonical, показується вимога відкрити його в браузері та скопіювати адресу з `@handle` чи `/channel/UC…`. Чужий канал за приблизним пошуком не вибирається.

Посилання на відео, Shorts, конкретний ефір або плейлист відхиляються з окремою підказкою скопіювати канал автора. Зберігаються лише нормалізовані адреси, параметри поширення не потрапляють у конфігурацію чи журнал.

Для Twitch також підтримано мобільну адресу і вкладки videos/about/schedule, для TikTok — посилання на канал або його `/live`. Перевірена Twitch LIVE-адреса використовує актуальний `user_login` API, щоб зміна ніка не направляла глядача на стару адресу.

## Захист підтвердження й доставки

Офіційний ID провайдера закріплюється за записом атомарно в documents-колекції `guildStreamerIdentities` разом зі станом і створенням подій. Два адресні варіанти одного каналу не можуть одночасно підтвердити LIVE і створити нові сповіщення. Пізніше виявлена копія отримує статус «Цей канал уже додано» та прибирається з публічних ефірів. Після видалення попереднього власника запису перевірка може безпечно передати закріплення іншому запису.

Нові ID подій залежать від платформи, підтвердженого ID каналу та ID відео/ефіру. Повторне додавання іншої адреси того самого поточного ефіру не створює другого повідомлення. Існуючі записи черги та журнал публікацій не переписуються.

YouTube LIVE у публічному API посилається на канонічний `/channel/UC…`; контракт Site 4.6.1 залишається сумісним. Приватні токени та налаштування не додаються до публічного payload.

Довільні хости, IP-адреси, HTTP, URL з логіном/паролем, нестандартні порти й закодовані роздільники шляху не приймаються. Legacy `/c/…` перевіряється лише на дозволених YouTube-хостах: до 4 переходів, спільний таймаут 9 секунд, HTML до 2 MiB. Редиректи на сторонні хости не виконуються; ключ API передається тільки офіційному API Google.

## Установлення

Оновити файли повного стека з архіву 3.15.1, зберігши чинні env-файли та дані. З кореня стека:

```bash
cd /srv/mistblossom
make rebuild-dashboard
```

Якщо встановлена версія до 3.14.0, виконати `make up`, щоб також оновити розклад cron. Окрема міграція не потрібна; використовуються чинні PostgreSQL documents/system_logs. Site 4.6.1 сумісний із цим релізом. Наявні записи платформ залишаються доступними.

Для реальних статусів YouTube потрібні увімкнений YouTube Data API v3 і чинний `STREAMER_YOUTUBE_API_KEY` у `dashboard/.env.production`. Наявність ключа не доводить його доступність; результат реального запиту відображається в статусі й журналі. Виправлення додавання не скасовує вимог провайдера до авторизації та квоти.

## Перевірки

38 серверних сценаріїв перевіряють фактичний код із PostgreSQL/PGlite, транзакціями, proxy, API, провайдерами й журналом публікацій. Нові сценарії: різні формати YouTube-адрес, YouTube без Twitch, збереження при HTTP 403/відсутньому ключі без жодного provider-запиту, подальше відновлення, legacy URL/forUsername, заборонені перенаправлення, копії каналу та зміна Twitch-ніка.

Браузерні сценарії виконують реальні React-компоненти й стилі на 320/390/1440 px: YouTube-only, пряма кнопка додавання платформи, приєднання до наявного Discord ID, збереження введених значень, локальна помилка video URL, фонові оновлення та LIVE-блок сайту. Скріншоти — лише для внутрішньої перевірки.
