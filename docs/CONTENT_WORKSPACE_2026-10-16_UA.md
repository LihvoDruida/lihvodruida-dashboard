# Dashboard 3.10.0 — створення та керування контентом

Оновлення для `/content`, сумісне з Public Site 4.1.1. Архів містить повний дашборд з усіма попередніми виправленнями синхронізації 3.9.1. Живий VPS у цьому сеансі не змінювався.

## Що змінилося

| Ділянка | Нова поведінка |
|---|---|
| Бібліотека | Пошук за заголовком, описом, автором, категоріями, тегами та адресою; фільтри типу й стану; сортування; по 15 матеріалів на сторінці |
| Оновлення списку | Окремий запит у фоні раз на хвилину у видимій вкладці, кнопка повторної перевірки, збереження пошуку та фільтрів |
| Чернетки | Збереження від одного заголовка; текст і опис можна доповнити пізніше. Чернетки не входять до публічного CMS-каталогу |
| Публікація | Окрема дія з перевіркою опису й тексту; повторне збереження вже опублікованого матеріалу зберігає його стан |
| Зняття з публікації | Матеріал стає чернеткою; дія має підтвердження. Публічний сайт підхоплює зміни після оновлення свого кешу |
| Редактор | Режими Markdown / текст і перегляд / перегляд; заголовки, жирний, курсив, списки, цитати, посилання, код і таблиці |
| Попередній перегляд | Той самий `react-markdown` + `remark-gfm`, що на сайті; небезпечний HTML не виконується |
| Файли тексту | Імпорт .md/.markdown/.txt до 800 KB і 200 000 символів; експорт поточного тексту .md |
| Обкладинка | JPG/PNG/WEBP/GIF до 8 MB, перевірка формату й розміру, локальний перегляд, заміна або прибирання |
| Метадані | Тип, транслітерована адреса, дата матеріалу, автор із підказками, категорії й теги; показ майбутнього URL |
| Збереження | Форма залишається відкритою; повертається фактично записаний матеріал і нова ревізія. Ctrl/Cmd+S зберігає поточний стан |
| Помилки | Введений текст зберігається у формі; зрозуміле повідомлення, повторна спроба без виходу зі сторінки |
| Конфлікти | HTTP 409 для застарілої ревізії; можна експортувати свій текст і відкрити актуальну версію в іншій вкладці |
| Відновлення | Незбережений текст копіюється в sessionStorage цієї вкладки; після перезавантаження пропонується відновлення |
| Видалення | Окремий блок із підтвердженням; сервер повторно перевіряє поточну ревізію |
| Адаптація | Бічні налаштування на ПК, послідовні блоки на телефоні, доступна панель збереження, системна палітра дашборда |

## Виправлені дефекти

1. Звичайний редірект після помилки збереження більше не закриває активний редактор. Новий клієнт отримує структурований JSON і залишає поля на місці.
2. Компонент обкладинки зберігає `/api/site/media/:hash` на домені дашборда. Старі абсолютні адреси `guild`/`admin` цього формату також нормалізуються. Вони не підставляються помилково до адреси публічного сайту.
3. Некоректний multipart і невідомий тип матеріалу обробляються як помилки форми. Реальний потік тіла обмежено навіть без `Content-Length`.
4. Застарілий редактор або вікно видалення отримує 409 замість неявного редіректу; чужі зміни не перезаписуються.
5. Копія для відновлення слідує за зміною адреси матеріалу. Це перевірено перейменуванням і наступним перезавантаженням вкладки.
6. При збереженні обкладинки немає очікування другої pooled PostgreSQL-сесії всередині транзакції статті. Перевірка ревізії повторюється перед записом.
7. Публікації не губляться через те, що перед ними завантажилися 500 чернеток: бібліотека читає повний набір, публічний каталог окремо фільтрує стан.
8. «Нещодавно оновлені» використовує фактичний timestamp зміни, а не лише дату без часу.
9. Дати перевіряються без автоматичного перетворення неможливих значень на інший день. Типова дата нового матеріалу відповідає Києву.
10. Старі невикористані стилі бібліотеки й полів обкладинки видалено. Чинні Discord-сторінки зберігають спільні стилі своїх полів.

## Дані та сумісність

Зберігання залишається у PostgreSQL `siteArticles`; новий стан запису — `draft` або `published`. Наявні записи без поля стану трактуються як опубліковані, тому оновлення не приховує старий контент. Окрема SQL-міграція для стану не потрібна: записи зберігаються як JSONB.

Публічний контракт лишається `mistblossom.public-content.v2`; Site 4.1.1 змінювати для цього оновлення не потрібно. Чернетки не входять до публічного списку або його лічильника; редагування лише чернетки не змінює ревізію публічного каталогу. Медіа залишаються адресованими за хешем, без автоматичного видалення спільних обкладинок.

Поточний контракт Site 4.1.1 допускає до 500 опублікованих матеріалів. Перевищення цього розміру тепер повертає помилку замість тихого обрізання; чернетки не витрачають цей ліміт. Розширення контракту понад 500 потребує парного оновлення сайту.

Назва «Дата матеріалу» означає дату відображення, а не планувальник. Публікація відбувається окремою кнопкою. За нормальної роботи CMS-кешу зміни доходять до наступного запиту сторінки сайту приблизно за 60 секунд; при збої сайт може тимчасово показувати позначені збережені дані за правилами попереднього релізу.

SessionStorage — відновлення тексту в тій самій вкладці та для поточного облікового запису. Воно не замінює серверну чернетку, не переносить вибраний файл зображення та може бути недоступним через налаштування браузера. Після успішного збереження відповідна копія видаляється. При конфлікті відновлена стара ревізія не підміняється новою мовчки.

Відкат до 3.9.1 після створення чернеток потребує окремої підготовки: старий публічний producer не фільтрує новий стан. Не запускати його поверх колекції з чернетками без сумісного виправлення або перевіреного відновлення саме даних CMS із резервної копії.

## Встановлення

Спочатку зберегти резервну копію БД, чинних env та поточний image ID. Архів має кореневий каталог `mistblossom`; робочі env й секрети до нього не входять.

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.10.0-content-workspace.zip
unzip -o /tmp/lihvodruida-dashboard-v3.10.0-content-workspace.zip -d /srv
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
```

Відкрити `/content` під обліковим записом із правами керування матеріалами. Перезавантажити старі відкриті редактори після оновлення.

Якщо попередній парний реліз ще не встановлено, спочатку виконати його налаштування Site 4.1.1, однакового bridge token і приватної Docker-мережі. Стара прив’язка Cloudflare Worker та доступ CurseForge лишаються окремими налаштуваннями середовища. Цей реліз не змінює їх автоматично; інструкція `SYNC_INSPECTION_2026-10-16_UA.md` збережена в комплекті.

## Перевірки

- TypeScript та ESLint дашборда.
- Повний `npm run build:ci`, включно з перевірками наявних функцій, аудитами стилів/UI, production-збіркою та standalone-пакуванням.
- `check:site-integration`: 8/8 сценаріїв, зокрема lifecycle чернетки, публічна ревізія, старі записи, перейменування, медіа та бібліотека з понад 500 чернетками.
- `check:content-workspace`: 8/8 сценаріїв справжніх route handlers: JSON-квитанція, публікація, конфлікт, видалення, malformed multipart, права/Origin, ліміт фактичного потоку й адреса обкладинки.
- `check:content-browser`: 8/8 сценаріїв у Chromium, із мобільною бібліотекою та desktop-редактором. Браузер виконує справжні компоненти; збереження проходить справжні route handlers, сховище та сесія контрольовані. Перевірено мережевий збій, retry, двох редакторів, завантаження обкладинки, зняття з публікації, відновлення та підтверджене видалення.
- Парні тести Site 4.1.1 із цим дашбордом: 27/27.
- ZIP: центральний каталог, CRC і SHA-256 кожного файла, також після збереження готового архіву.

Усі сценарії запису виконані в ізольованому контрольованому сховищі; живі матеріали та Discord не змінювалися. Docker daemon і жива PostgreSQL цього VPS недоступні в сеансі, тому фактичне встановлення контейнера та приймання на живому сайті треба виконати після завантаження архіву.

Для звичайної перевірки вихідних кодів:

```bash
cd dashboard
npm ci --no-audit --no-fund
npm run build:ci
npm run lint
```

Браузерна перевірка — окремий QA-сценарій. Вона потребує esbuild і Playwright/Chromium, заданих через `CMS_QA_ESBUILD`, `CMS_QA_PLAYWRIGHT`, `CMS_QA_CHROMIUM` або доступних у середовищі перевірки. Ці інструменти не додаються до production runtime.

## Приймання після розгортання

1. Зберегти чернетку з одним заголовком і переконатися, що вона відсутня у публічних новинах/гайдах.
2. Додати опис, Markdown-таблицю та обкладинку, перевірити перегляд, опублікувати. Звірити сторінку сайту після оновлення кешу.
3. Змінити матеріал у двох вкладках: зберегти першу, у другій отримати конфлікт без втрати тексту.
4. Перейменувати тестовий матеріал; змінити текст, перезавантажити вкладку й відновити незбережену копію.
5. Зняти з публікації й перевірити зникнення з каталогу. Потім видалити лише тестовий матеріал через підтвердження.
