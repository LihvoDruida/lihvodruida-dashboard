# Чому список був готовий, а учасники не виключалися

Для стандартної конфігурації Docker знайдено й відтворено дефект middleware:
endpoint `/api/dashboard/discord/member-cleanup/automation` не входив до
точного списку внутрішніх bearer-маршрутів у `dashboard/src/proxy.ts`.
Запит cron на `http://dashboard:3000` отримував HTTP 421 «Blocked host» ще до
handler. Водночас ручне сканування через публічний сайт працювало, тому
список заповнювався й залишався в очікуванні.

Кнопка «Оновити список» виконує перевірку без виключення. Саме автоматичний
handler має обробити чергу відповідно до збереженого правила. Пропущений
маршрут зупиняв цей етап; це помилка інтеграції, а не свідчення, що строки
ще не спливли.

## Виправлення

- Додано тільки конкретний endpoint до внутрішнього списку. Секрет перевіряє
  handler; звичайний API налаштувань не отримав внутрішнього винятку.
- Активне сканування й готова черга отримують наступний цикл через 10 секунд,
  до 5 виключень за цикл, у межах часу виконання й обмежень Discord.
- Без готових дій наступний виклик — через 60 секунд. У такому виклику стан
  перевіряється в базі, без читання ролей, сервера чи учасників через Discord.
  Перший запуск після появи роботи може чекати завершення цього інтервалу;
  наступні порції переходять на швидку обробку. Повний список оновлюється
  щогодини або на ручний запит.
- Актуальні ролі, дата вступу, ієрархія та права бота перевіряються перед kick.
  Ця перевірка захищає учасника, який уже отримав іншу роль або вступив знову.
- Панель показує час останнього автоматичного виклику й попереджає, якщо
  планувальник не виходив на зв’язок понад 3 хвилини після сканування.
- `make up` перевідтворює cron-контейнер після запуску здорової панелі. Це
  завантажує поточний bind-mounted скрипт і скидає стару затримку після 421.
  До перевірки цілісності релізу додано обов’язковий `run-job.sh`.

## Оновлення VPS

Після встановлення оновлених файлів проєкту виконай:

```sh
make up
docker compose logs --tail=50 cron
```

На сторінці очищення має оновитися час виклику планувальника. У журналі
cron для `/api/dashboard/discord/member-cleanup/automation` очікується
HTTP 200. Налаштування автоматичного виключення повинне бути увімкнене;
боту потрібен Kick Members та роль вище вибраної ролі. Відмова Discord
показується в панелі, а неоднозначні запити не повторюються автоматично.

## Перевірки

Виконано 101 поведінкову перевірку, включно з відтворенням старого 421,
новим проходженням middleware, правами, виключенням порціями, відсутністю
Discord REST-запитів у спокої, таймерами та незалежним shell dispatcher.
Пройшли повна `build:ci` на файлах Docker builder, lint, shell syntax та
перевірка інтерфейсу на 9 ширинах із пагінацією, вкладками й паузою.

Окремо запущено готовий Next standalone сервер і виконано 6 HTTP-сценаріїв
із справжніми Host-заголовками. Правильний внутрішній токен проходить до
handler; у цьому тесті handler очікувано повертає 503 через навмисно порожній
DISCORD_GUILD_ID. Неправильний токен дає 401; відсутній bearer, невідомий Host
і внутрішній запит до API налаштувань — 421; публічний запит без Cloudflare —
403. Відмова через відсутній Discord у тесті підтверджує проходження proxy
та авторизації, а не успішне виключення реального учасника.

Discord та документне сховище в поведінкових тестах змодельовані. Docker
недоступний; Docker-образ і робочий VPS тут не запускалися. Реальні учасники
не виключалися. Результати: `DISCORD_CLEANUP_CRON_VALIDATION_2026-10-11.json`.
