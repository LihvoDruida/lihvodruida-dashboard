# Чекліст виправлень і розвитку Site / Dashboard

**Вихідна база:** Site 4.6.1, Dashboard 3.15.1, Bot 3.6.9. **Етап 1:** Site 4.6.2, Dashboard 3.15.2, Bot 3.6.9. **Дата:** 19.10.2026.

Зв’язаний документ: `lihvodruida-audit-2026-10-19.md`. Позначки F/L/R посилаються на його знахідки, обмеження й ризики. Позначені пункти реалізовані та перевірені локально. Це не підтверджує розгортання чи виробничу перевірку на VPS. Інші пункти залишаються відкритими.

P1 — першочергові виправлення; P2 — надійність і керованість; P3 — розширення. Орієнтири складності S/M/L є порівняльними, не оцінкою строків. BE — серверна частина, FE — інтерфейс, OPS — розгортання, QA — перевірки.

## 1. Першочергові виправлення

- [x] **C41 · P1 · BE/QA · M — Не видаляти профіль через Discord 403 (F11).** Відокремити відмову OAuth/відсутність scope від підтвердженого виходу з сервера. Готово, коли реальний callback при 401/403/429/timeout не викликає видалення профілю або прив’язок, а достовірний вихід перевіряється незалежним актуальним джерелом. Цей пункт виконати першим.

- [x] **C01 · P1 · BE · M — Повний Retry-After (F01).** Зберігати справжній `retryAt`, не скорочувати його до 60 секунд. Якщо очікування перевищує бюджет worker — відкладати роботу. Готово, коли тести 600 секунд, HTTP-date, рестарту та скасування підтверджують відсутність ранніх повторів.

- [x] **C02 · P1 · BE/FE · M — Таймаути Discord OAuth (F02).** Один бюджет входу, обмежене тіло й перевірена схема на token/user/member. Готово, коли зависання будь-якого етапу завершується зрозумілою помилкою, OAuth code не пересилається автоматично повторно, тимчасова недоступність не видаляє профіль.

- [x] **C03 · P1 · BE/OPS · M — Загальний дедлайн стрімерів (F03).** Передавати спільне скасування в усі залежності, резервувати час для commit/lease release. Готово, коли повільні membership/resolve/feed/search/videos/Discord не виходять за погоджений бюджет нижче cron timeout, а прогрес і неоднозначна доставка не губляться.

- [x] **C04 · P1 · BE · M — Retention метаданих YouTube (F05).** Розділити API-метадані й мінімальний запис дедуплікації, додати очищення/оновлення за строком. Готово, коли штучно зістарені записи обробляються за перевіреною політикою, а pending/uncertain/sent не спричиняють повторних повідомлень. Не видаляти історію без плану збереження ідемпотентності.

- [x] **C05 · P1 · OPS/BE · S — Одна чинна інструкція (F07).** Узгодити версії/сумісність, місця env, порядок Dashboard → cron → Site; прибрати Firebase з чинних налаштувань, дубль `INTERNAL_API_TOKEN` і неіснуючі команди. Готово, коли нове встановлення можна виконати за одним документом, а автоматична перевірка знаходить повторні env-ключі та невідомі npm-команди.

## 2. Надійність API й сповіщень

- [ ] **C06 · P2 · BE · M — Провайдерні cooldown (F04).** Зберігати `Retry-After`, Twitch `Ratelimit-Reset`, причину й можливість повтору; об’єднати паузи споживачів одного провайдера. Готово, коли один 429 не породжує паралельні повтори іншими модулями, а рестарт не скидає паузу. Залежність: C01.

- [ ] **C07 · P2 · BE · S — Перевірка Twitch token (F10).** Додати початкову/періодичну `/validate`, звірку client ID та обробку відхилення. Готово, коли відкликаний токен не залишається «готовим», оновлення не створює шторму запитів, секрети відсутні в логах.

- [ ] **C08 · P2 · BE · M — Обмежені відповіді API (F08).** Спільний reader із лімітом байтів, скасуванням, Content-Type і схемою. Готово, коли великі тіла, HTML, обірваний потік і пошкоджений JSON дають безпечні типізовані помилки для OAuth, Discord, Battle.net та Raider.IO. Залежність: C02 для шляху входу.

- [x] **C09 · P2 · BE/QA · M — Сумісність старих event keys (F09).** Міграція або читання старих sent/pending/uncertain за ідентичністю медіа. Готово, коли оновлення зі старої БД, перейменування handle та видалення/повторне додавання каналу не дублюють той самий LIVE. Перед випуском — резервна копія й dry run міграції.

- [ ] **C10 · P2 · BE/FE · M — Стійка ручна перевірка (F06).** `jobId`, стани й результат по каналах; зрозумілий busy/skipped. Готово, коли кожне натискання має простежуваний результат і відновлюється після рестарту, не оминаючи lease чи мінімальні інтервали.

- [ ] **C11 · P2 · BE/QA · M — Справедливий YouTube search-бюджет (R02).** Окремо записувати спробу пошуку та успішне спостереження. Готово, коли збій resolve/feed/API/commit не дозволяє одному каналу витратити всі слоти, інші канали отримують перевірки, ліміт 80 не перевищується.

- [ ] **C12 · P2 · BE/OPS · M — Метрики черги й навантаження (R04).** Вимірювати тривалість циклу, вік найстарішої події, due/deferred/uncertain та вік LIVE-підтвердження. Готово, коли сценарій 30 каналів і повільного провайдера показує контрольований час доставки без її нескінченного відкладання. За результатами — окремий бюджет/worker доставки.

- [ ] **C13 · P2 · BE/FE · M — Повний шлях діагностики (R03).** ID запиту/завдання, фільтри по учаснику/платформі/статусу, сторінки журналу, остання спроба й останній успіх. Готово, коли адміністратор знаходить причину конкретної невдалої дії без доступу до сирого upstream-тексту чи секретів.

## 3. Перевірка зовнішніх сервісів на VPS

Ці пункти не виконані в поточному середовищі. Результат зберігати як статус, час і безпечний код; значення секретів у звіт не копіювати.

- [ ] **C14 · P1 · OPS · S — Фактичні версії та cron.** Зіставити образи/контейнери з релізами, перевірити PostgreSQL і регулярні ticks streamer/guild/application workers. Готово, коли відомі фактичні версії, час останнього успіху кожної задачі та відсутність пропущеного нового cron-скрипту.

- [ ] **C15 · P1 · OPS/QA · M — Внутрішній bridge і публічний край.** Перевірити private `/api/site/status`, `/api/site/streamers` та публічні `/site-api/v1/{status,sync,guild,applications,streamers}`. Готово, коли коректні JSON/схеми/no-store й немає редіректу на login, старого Worker чи challenge. Негативний тест недійсного токена не відкриває приватні API.

- [ ] **C16 · P1 · OPS · M — Cloudflare.** Знайти застосовані правила за Security Events/Ray ID; перевірити API, callback-и, Discord interactions. Готово, коли потрібні машинні запити не отримують HTML challenge, кеш не змішує приватні відповіді, а прикладні авторизація й rate limit залишаються чинними. Винятки робити вузькими.

- [ ] **C17 · P2 · OPS/QA · M — Discord.** Звірити OAuth redirect/scopes, public key/application ID, Server Members Intent, права каналів та ієрархію ролей. Готово, коли контрольний вхід і взаємодія на тестовому сервері працюють, а неправильний підпис/replay/відсутні права дають коректну відмову. Надсилання тестового повідомлення — лише в явно визначений тестовий канал.

- [ ] **C18 · P1 · OPS/BE · M — Battle.net.** Прочитати актуальні OAuth/namespaces/API instructions у developer portal, який не вдалося повністю отримати під час аудиту. Звірити регіональні host, callback, `openid wow.profile`, app/user доступ. Готово, коли контрольний акаунт і гільдія читаються; privacy/403/404 відрізняються від мережевого збою й не стирають підтверджені дані.

- [ ] **C19 · P2 · OPS/BE · S — Raider.IO.** Перевірити доступ, правильну гільдію/region/realm, реальні 429/cooldown і посилання-атрибуцію. Готово, коли відомі доступні квоти проєкту, дані мають час джерела, ранніх повторів немає. Залежності: C01/C06.

- [ ] **C20 · P2 · OPS/QA · M — Twitch/YouTube.** Перевірити ключі серверними read-only запитами, зареєстровані канали й Cloud Console quota. Готово, коли online/offline та нове public video відрізняються від API outage, старі відео не розсилаються, а фактична затримка виміряна.

- [ ] **C21 · P2 · OPS/QA · M — TikTok.** Перевірити app review, три scopes, дозвіл саме потрібного автора, refresh і збереження ротації. Готово, коли нове public video читається після рестарту й оновлення токена; revoked/expired access пояснюється користувачу. Не очікувати LIVE від Display API.

- [ ] **C22 · P1 · OPS/BE · S — CurseForge.** Перевірити API key у Site `.env`, HTTP 200, `authorId`, результати й час оновлення. Готово, коли джерело справді `curseforge`, а 401/403 не видається за актуальні дані. Окремо перевірити поведінку після рестарту й під час відмови.

- [ ] **C23 · P2 · OPS/QA · M — Виробнича БД і відновлення.** Запустити передбачені проєктом PostgreSQL-тести на ізольованій БД тієї самої major-версії, перевірити backup/restore та ключ шифрування. Готово, коли відновлена тестова копія містить CMS, заявки, історію сезонів, черги/receipts; секрети не втрачені. Жодних destructive тестів на production.

- [ ] **C24 · P2 · OPS · S — Аудит залежностей.** Повторити `npm audit --omit=dev` для трьох пакетів у середовищі з доступом до registry. Готово, коли є реальний результат і розібрано застосовність кожного advisory; перевірка мінімальних версій runtime не замінює цього пункту.

## 4. Повнота синхронізації та основні сценарії

- [ ] **C25 · P1 · BE/QA · M — Минулі сезони від БД до сторінки.** Зіставити catalog → history collection → `/api/site/guild` → Site UI для кожного відомого минулого сезону. Готово, коли немає втрати рядків при оновленні поточного сезону; нуль убивств, невідомі дані, partial і stale показуються різними станами; назва/дата/прогрес підтверджені джерелом.

- [ ] **C26 · P2 · BE/FE/QA · M — Життєвий цикл заявки.** Форма → збереження → receipt → публічний статус → рішення → Discord edit/notification. Готово, коли дубль, подвійне натискання, втрата відповіді, тимчасовий збій Discord і конкурентна модерація дають одну заявку й одне рішення з видимим станом доставки. Перевірити всі варіанти «Звідки дізнався про нас?» і варіант власної відповіді.

- [ ] **C27 · P2 · BE/FE/QA · M — CMS і кеші.** Створити чернетку, перегляд, публікація, правка, зняття з публікації, обкладинка, RSS/sitemap. Готово, коли кожна зміна стає видимою на Site у погоджений строк без повного перезапуску; конфлікт ревізій зберігає текст і пояснює відновлення; draft не потрапляє у публічний API.

- [ ] **C28 · P2 · QA/FE · S — Навігація та masthead.** Перехід із гільдії/новини на головну, reload, Back/Forward, hash, клавіатура, мобільне меню. Готово, коли звичайне натискання «Головна» починає сторінку згори; навмисний hash і браузерне повернення поводяться передбачувано; назва гільдії веде на сторінку Site, банер не перекриває меню.

- [ ] **C29 · P2 · QA/BE · M — Рейди та Discord-взаємодії.** Створення/зміна/закриття рейду, signup, зміна спеціалізації, opt-out нагадувань, attendance і черга публікації. Готово, коли зміна в одному інтерфейсі відображається в іншому, старі кнопки або працюють безпечно, або дають пояснення; повтор callback не створює дубль.

- [ ] **C30 · P1 · QA/BE · M — Захист очищення як незмінний критерій.** Обов’язкові сценарії: лише Мурлок; без ролей; Мурлок+Козак; інші ролі; невідомі ролі; роль з’явилася під час очікування; pause; rejoin; timeout/невідомий результат. Готово, коли додаткова роль завжди блокує DELETE у контрольованих сценаріях, перед відправленням є два актуальні підтвердження, неоднозначний DELETE не повторюється. Реальних учасників для перевірки не виключати.

## 5. Поліпшення функціоналу та інтерфейсу

- [ ] **C31 · P2 · BE/FE · L — TikTok OAuth-майстер (L03).** Адмін обирає учасника, автор надає дозвіл через офіційний потік, callback перевіряє state/прив’язку/scopes; показуються строки й перепідключення. Готово, коли не треба вручну переносити access/refresh token, а право додавання залишається лише в адміна/власника. Реальний `expires_in` замінює умовні 15 хвилин.

- [ ] **C32 · P2 · BE/OPS · L — Швидше виявлення YouTube (L01).** Узгодити вимірювану ціль затримки; оцінити WebSub для завантажень/змін із перевіркою videos.list і резервним polling. Готово, коли є renew/challenge, захист callback, дедуплікація й вимір на кількох каналах. Push метаданих не оголошувати гарантією точного live-start.

- [ ] **C33 · P3 · BE/OPS · L — Twitch EventSub.** `stream.online/offline`, перевірка HMAC/timestamp/message ID, відновлення підписок і резервний Helix. Готово, коли повтор/підробка webhook не створює сповіщення, підписки переживають рестарт, затримка виміряна. Залежності: C06/C07/C16.

- [ ] **C34 · P2 · BE · M — Стійкий знімок CurseForge (R01).** Зберігати останній успішний результат поза пам’яттю процесу. Готово, коли рестарт під час 403 залишає останні дані з правильною датою/позначкою stale, а наступний успіх оновлює їх без ручного втручання.

- [ ] **C35 · P3 · FE/QA · M — Єдина картка стрімера на сайті.** Групувати одночасні платформи одного учасника з чіткими переходами, не розкривати Discord ID. Готово, коли multi-stream не дублює картки людини, блок доступний клавіатурою і не перекриває форму чи контент на 320 px.

- [ ] **C36 · P2 · FE/QA · M — Доступність керування.** Фокус на помилковому полі, читабельні error/status повідомлення, збереження введення, контроль незбережених змін і зрозумілий revision conflict. Готово, коли основні форми можна пройти клавіатурою/екранним читачем, background refresh не стирає чернетку, відновлення після збою не потребує повторного введення.

## 6. SEO, швидкість і випуск

- [ ] **C37 · P2 · OPS/FE · M — Новий PageSpeed та польові виміри.** Зняти нові mobile/desktop результати для головної, гільдії, списку матеріалів та статті. Готово, коли зафіксовані дата, версія, LCP/INP/CLS і умови; окремо лабораторні й доступні польові дані. Орієнтири добрих CWV: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 на 75-му перцентилі за наявності достатніх польових даних. Не вимагати вигаданого балу зі старого недоступного звіту.

- [ ] **C38 · P2 · FE/OPS · M — SEO гільдії та індексація.** Перевірити Search Console/Bing, sitemap/canonical/robots, реальні title/description та зміст про українську WoW-гільдію, EU/Terokkar, набір, рейди/Mythic+. Готово, коли сторінка має корисний підтверджений текст і валідну схему, чернетки/службові сторінки не індексуються, sitemap не оголошує відсутні дані порожнім успіхом під час збою.

- [ ] **C39 · P2 · OPS/QA · M — Повторювана чиста збірка.** Запускати повний `build:ci` в чистому середовищі; окремо перевірити прогрітий кеш. Готово, коли обидва сценарії мають повний журнал і справжній exit code, локальна помилка Turbopack не маскує падіння й не веде до очищення даних застосунку.

- [ ] **C40 · P2 · QA/OPS · M — Критерій готовності парного релізу.** CI Site/Dashboard/Bot, парні тести без пропусків, браузерні сценарії, upgrade/dedupe, схеми, readiness і публічний edge. Готово, коли конкретні версії/контрольні суми записані, rollback перевірено на тестовому стенді, приватні env/ключі/БД не включено в архів, нові архіви доступні користувачу.

## Рекомендована послідовність

Код C41, C01–C05 і сумісність читання старих ключів C09 завершені на етапі 1. Далі — C06–C08 та C10–C13. На VPS залишаються C14–C18, C22, C25, а також резервна копія, перевірка старих записів, cron і приймання парного релізу C40. Після контрольних сценаріїв — розширення C31–C38.

**Приймання наступного випуску:** усі P1 закриті або мають явно зафіксовану причину відкладення; жоден пропущений чи недоступний тест не позначений PASS; відтворені F01/F02/F03/F09/F11 перетворені на регресійні перевірки. Цей чекліст сам по собі не змінює код чи налаштування production.

Джерела API й детальні докази — у звіті. CWV: https://developers.google.com/search/docs/appearance/core-web-vitals ; https://web.dev/articles/vitals

## Результат етапу 1

- C41: 401/403/429/timeout та непідтверджений 404 не видаляють профіль; bot guild/member повинні незалежно підтвердити код 10007. Джерело доказу записується в аудит.
- C01: повний `retryAt`, HTTP-date, переривання backoff; Raider.IO guild worker зберігає cooldown у PostgreSQL та читає його після рестарту. Спільні паузи інших провайдерів/споживачів залишаються C06.
- C02: спільний OAuth upstream deadline 25 с, до 10 с на fetch, ліміт 128 KiB, перевірка token/user/member, без повтору code.
- C03: спільний AbortSignal для membership, provider resolve/feed/search/videos/token та Discord send/reconcile; зовнішній I/O припиняється на 33-й секунді типового бюджету 38 с. Фіналізація SQL/lease має резерв 5 с; збої БД не отримали універсальної гарантії тривалості. Невідправлений POST лишається retryable, відправлений із невідомою відповіддю — uncertain.
- C04: 29-денний retention, 100 подій за tick, очищення копій метаданих у квитанціях та застарілого стану каналів, збереження хешів дедуплікації. Працює за вимкненого моніторингу, але потребує чинного cron. Існуючі Discord-публікації автоматично не видаляються.
- C05: одна чинна інструкція, версії й env узгоджені; перевірка дублів ключів та невідомих npm-команд включена в CI.
- C09: читання legacy media identity та компактних хешів без зміни ID подій/квитанцій; sent/pending/uncertain не породжують повтор після перевідтворення каналу. Міграцію ключів production БД не запускали; резервна копія й приймання на VPS залишаються обов’язковими.
