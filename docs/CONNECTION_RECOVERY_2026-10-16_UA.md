# Відновлення зв’язку та підтвердження заявок — Dashboard 3.11.1 / Site 4.2.1

Повні пакети продовжують попередній парний реліз Dashboard 3.11.0 / Site 4.2.0 і містять усі його зміни. На робочому VPS нічого не розгорталося; живі заявки та Discord-повідомлення не створювалися.

## Виправлені збої

### Підтвердження заявки залежало від Discord

Раніше POST записував заявку в PostgreSQL, потім очікував Discord і лише після цього віддавав квитанцію сайту. Затримка Discord могла перевищити час очікування між сервісами. Виняток під час отримання налаштувань Discord міг повернути HTTP 500 після успішного запису заявки.

Тепер квитанція формується після успішного запису в PostgreSQL. Сповіщення виконується через штатний Next.js `after` після відповіді. Його помилка не змінює результат створення заявки. Повторне надсилання в межах чинного 10-хвилинного вікна дедуплікації повертає ту саму квитанцію та не планує друге сповіщення.

Збереження посилання на Discord-повідомлення перевіряється окремо. Якщо повідомлення надіслано, але посилання не записалося в БД, журнал містить `public_site.applications.discord_reference_failed`, а не неправдиве підтвердження повного зв’язку. Збій журналювання також не перетворює збережену заявку на HTTP-помилку.

`after` не є довговічною чергою. Примусове завершення процесу може перервати сповіщення; заявка залишиться в PostgreSQL і буде доступна офіцерам у дашборді. Цей реліз не гарантує автоматичної повторної доставки в Discord після перезапуску. Зафіксовані помилки доставки й запису посилання потребують перевірки; повторне надсилання заявки не використовується як повторна доставка повідомлення.

### Втрачався сигнал відновлення з’єднання

Раніше швидке offline → online або приховування → показ вкладки могло відбутися, поки скасований запит ще завершувався. Обробник повернення бачив активний запит і губив сигнал. Подальше оновлення чекало наступного таймера; скасування могло виглядати як перевищення часу очікування.

Тепер повернення з мережі або фону ставить повторне читання в чергу, якщо попереднє ще завершується, та скидає накопичену затримку повторів. Навмисне скасування через паузу не показує повідомлення про таймаут. Таймер скасовує лише власний запит. Фонові дані, фільтри й поточна сторінка зберігаються.

| Поведінка створення заявки з повільним/недоступним Discord, повтором, збереженням посилання та збоєм журналу | 5/5 |
| Справжній Chromium зі зібраним production-сайтом | 8/8 |

| ESLint та перевірка diff | Успішно |

Браузерна перевірка включає коротке відключення/відновлення мережі та повернення вкладки під час завершення скасованого запиту. Сигнали браузера контрольовані для відтворення конкретної гонки; використовуються справжні AbortController, React-компоненти й сервер Next.js. Нове читання починається без очікування звичайного 30-секундного інтервалу, без навігації й хибної помилки таймауту. Решта сценаріїв перевіряє форму, приватну квитанцію, фонову зміну статусу заявки, CMS, зняття публікації, RSS/sitemap і каталог модів.

Повільний Discord відтворено керованим незавершеним Promise: до виправлення тест падав через блокування квитанції; після виправлення HTTP-відповідь надходить до завершення сповіщення. Route та функції сховища справжні; сховище й Discord контрольовані, без зовнішніх повідомлень. Це не перевірка живої PostgreSQL на VPS або фактичної доставки Discord.

## Встановлення

Оновити обидва проєкти, спочатку Dashboard 3.11.1, потім Site 4.2.1. Нових секретів, портів або обов’язкових міграцій у цьому кроці немає. Частковий індекс ревізій із попереднього релізу залишається у штатному schema.sql.

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.11.1-application-receipt.zip
unzip -t /tmp/lihvodruida-site-v4.2.1-connection-recovery.zip
unzip -o /tmp/lihvodruida-dashboard-v3.11.1-application-receipt.zip -d /srv
unzip -o /tmp/lihvodruida-site-v4.2.1-connection-recovery.zip -d /srv
python3 /srv/mistblossom/deploy/prepare-unified-env.py --site-dir /srv/lihvodruida-site
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
cd /srv/lihvodruida-site
make check
make deploy
node scripts/check-deployed.mjs
```

Після встановлення оновити відкриті вкладки, щоб вони завантажили новий JavaScript. Звірити статус `/site-api/v1/status`, фонові дані та журнали доставки погодженої тестової заявки.

Попередні інструкції про приватну Docker-мережу, однаковий bridge token, Nginx і старий Cloudflare Worker залишаються у `SITE_DASHBOARD_SYNC_2026-10-16_UA.md` та `SYNC_INSPECTION_2026-10-16_UA.md`. HTTP 403 зовнішнього CurseForge API не виправляється змінами механізму заявок; потрібні чинні ключ і дозволи на стороні цього API.
