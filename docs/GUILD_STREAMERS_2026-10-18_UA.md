# Стрімери гільдії — Dashboard 3.14.1 + Site 4.6.1

Дата: 18 жовтня 2026 року.

## Доступ і поведінка

Керування — `/dashboard/streamers`. Додавати, редагувати й видаляти канали, вибирати Discord-канал, змінювати сповіщення та запускати ручну перевірку можуть **лише власник сервера й адміністратор**. Сторінка та кожен API-запит окремо перевіряють активну сесію. Модератор, наставник і звичайний учасник доступу не отримують.

Адміністратор указує Discord ID учасника, платформу й посилання на канал. Перевіряється присутність учасника на налаштованому Discord-сервері; це не є підтвердженням володіння зовнішнім каналом. Для TikTok додатково перевіряється дозвіл саме вибраного автора. Загальний ліміт — 30 каналів, серед них не більше 5 YouTube.

| Платформа | LIVE на сайті та початок ефіру в Discord | Нове відео в Discord |
|---|---|---|
| Twitch | Так, підтвердження Helix API | Завантаження та хайлайти; автоматичні записи ефірів ігноруються |
| YouTube | Так, публічний ефір із підтвердженим фактичним початком | Публічні звичайні відео; анонси та записи ефірів ігноруються |
| TikTok | Не реалізовано: використаний Display API не надає LIVE-стан | Так, після дозволу автора та підключення токенів |

На сайті компактний LIVE-блок розміщений унизу праворуч на всіх сторінках. Його можна згорнути; він не зсуває контент і не прокручує сторінку. Немає автоматичного програвання, сторонніх плеєрів чи завантаження прев’ю. Прострочений LIVE прибирається також під час втрати зв’язку. Публічний API не містить Discord ID, токенів чи службових налаштувань.

## Ключі платформ

Зберегти серверні значення в `mistblossom/dashboard/.env.production`, не в `NEXT_PUBLIC_*`. Не замінювати весь чинний env-файл прикладом.

```dotenv
STREAMER_TWITCH_CLIENT_ID=
STREAMER_TWITCH_CLIENT_SECRET=
STREAMER_YOUTUBE_API_KEY=
STREAMER_TIKTOK_CLIENT_KEY=
STREAMER_TIKTOK_CLIENT_SECRET=
STREAMER_TOKEN_KEY=
```

**Twitch:** зареєструвати застосунок у https://dev.twitch.tv/console/apps і скопіювати Client ID та Client Secret. Сервер сам отримує app access token; токен особистого акаунта стрімера не потрібен.

**YouTube:** у https://console.cloud.google.com/ увімкнути YouTube Data API v3, створити API key і обмежити його цим API. Для моніторингу використовуються публічна стрічка, перевірка метаданих videos.list та обмежений пошук LIVE. Квота цього застосунку спільна з іншими його споживачами.

**TikTok:** потрібен застосунок у https://developers.tiktok.com/ із Login Kit та Display API і дозволами `user.info.basic`, `user.info.profile`, `video.list`. Автор має пройти офіційну OAuth-авторизацію цього застосунку. Отримані access token та refresh token адміністратор додає в захищені поля каналу. Вбудованого майстра OAuth/redirect callback у цьому релізі немає: отримання початкових токенів виконується окремо через офіційний потік TikTok. Refresh token рекомендований для автоматичного поновлення доступу; без нього потрібне ручне перепідключення.

Для TikTok згенерувати сталий ключ шифрування:

```bash
openssl rand -hex 32
```

Результат записати у `STREAMER_TOKEN_KEY` і захищено зберегти резервну копію. Токени автора шифруються AES-256-GCM у PostgreSQL і не повертаються через API. Заміна або втрата ключа потребує повторного підключення авторів. Новий refresh token зберігається до наступного API-запиту. Порожні поля токенів під час редагування зберігають наявний доступ.

## Розгортання

1. Оновити **весь** проєкт Dashboard із парного архіву, зберігши чинні env-файли, дані та резервні копії. Це також оновлює `deploy/cron/run-cron.sh`.
2. Додати потрібні ключі в `dashboard/.env.production`.
3. Із каталогу повного стека виконати `make up`. Ця команда також перевідтворює cron із новим диспетчером. Самого `make rebuild-dashboard` для встановлення нового фонового завдання недостатньо.
4. Оновити Site з парного архіву, зберігши його `.env`, і виконати `make up` в каталозі сайту. Site 4.6.1 перевіряє наявність можливості `streamers:read:v1` у Dashboard 3.14.1 перед заміною контейнера.
5. У `/dashboard/streamers` додати канали, вибрати Discord-канал і явно ввімкнути потрібні перемикачі. Автоматизація за замовчуванням вимкнена.

Використовується чинне PostgreSQL document-сховище; окремої міграції для стрімерів немає. Налаштування сайт↔дашборд і `PUBLIC_SITE_BRIDGE_TOKEN` залишаються чинними. Ключі платформ на публічному сайті не потрібні.

Боту в цільовому текстовому каналі або каналі оголошень потрібні View Channel, Send Messages, Embed Links і Read Message History. Масові згадування вимкнені. Після встановлення перевірити статус фонового завдання «Стрімери гільдії», результати перевірки каналів і журнал останніх сповіщень.

## Перевірки й доставка

Планове завдання запускається щохвилини; до 8 каналів за один прохід. Twitch і відомі активні ефіри перевіряються приблизно щохвилини, звичайні відео — раз на 5 хвилин. Сайт опитує власний API кожні 30 секунд. Це інтервали планування, а не гарантія доставки в цей строк: впливають черга, кількість каналів, помилки та обмеження платформ.

YouTube: пошук раніше невідомих LIVE обмежений 80 викликами за рухомі 24 години на цей проєкт. За 5 каналів резервний пошук кожного відбувається приблизно раз на 100 хвилин; доступна публічна стрічка може виявити ефір раніше. Уже відомі ефіри перевіряються частіше. LIVE зникає після завершення або через 5 хвилин без успішного підтвердження. Збільшення кількості каналів чи зменшення інтервалів без оцінки квот не рекомендоване.

Перше успішне читання створює базову історію: старі відео не розсилаються. Поточний ефір може створити повідомлення. Події та черга зберігаються в PostgreSQL; повторний цикл не створює дубль тієї самої події. Після неоднозначної відповіді Discord система звіряє наявне повідомлення за журналом публікацій замість сліпого повторного надсилання. Вимкнення, видалення, зміна каналу/налаштувань та вихід учасника з сервера припиняють відповідні очікувані сповіщення. Події старші 24 годин не доставляються.

Проведені локальні перевірки: 17 сценаріїв бекенду з PGlite, справжніми модулями збереження та підміненими API; браузерні сценарії керування і LIVE-блоку на 320/390/1440 px; парний контракт і bridge; збірки та standalone-перевірки обох застосунків. Також перевірено відмову в доступі модератору/учаснику, повтори доставки, шифрування й оновлення токенів та зникнення прострочених ефірів. Реальні ключі, виробничі запити до платформ та надсилання у справжній Discord тут не перевірялися.

Для розробника: `npm run check:streamers` у Dashboard; парні тести Site — `PAIRED_DASHBOARD_ROOT=/path/to/mistblossom/dashboard SITE_SYNC_PG_MODULE=/path/to/mistblossom/dashboard/node_modules/@electric-sql/pglite node --import tsx --test tests/content-pair.test.ts tests/pair.test.ts tests/streamers.test.ts`. Браузерна перевірка `node scripts/check-streamers-browser.cjs` потребує `PAIRED_SITE_ROOT=/path/to/lihvodruida-site`, `SITE_QA_CHROMIUM=/path/to/chromium` та Playwright. У виробничий Docker-образ браузер не додається.
