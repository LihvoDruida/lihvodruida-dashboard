# 3.8.66 — спільні стилі та захист ролі Статика

## Інтерфейс

- Визначено явний порядок семи CSS-шарів. Спільні компоненти й сторінки мають вищий пріоритет за старі правила, що розпізнають компоненти за фрагментами назв класів.
- Повторні та перекриті декларації прибрано; геометрію поверхонь, форм, кнопок, відступів і hero зведено до спільних токенів.
- Desktop-файл змінює параметри, а не дублює правила сторінок. Збережено темну теплу палітру й бурштинові акценти.
- Заголовки Статика використовують `PageIntro`; текст не потрапляє у порожню другу колонку.
- Виправлено область видимості спільних `.btn` у CSS Modules та невалідні псевдоелементи всередині `:where()`.
- Для телефона: шрифт полів від 16 px, сенсорні кнопки від 44 px, перенос довгих назв і дій, прокручування табів/меню, безпечні області екрана.
- Hover обмежено пристроями з точним вказівником; додано єдиний клавіатурний фокус, reduced motion і forced colors.
- `check:style-system` включено до `verify` і `build:ci`. Інструкція для наступних змін: `dashboard/docs/UI_SYSTEM.md`.

## Статик

Gateway уже підтримує зміни учасників. Події `GUILD_MEMBER_ADD` і `GUILD_MEMBER_UPDATE` ставлять учасника в окрему чергу перевірки.

Якщо людина має налаштовану роль Статика без дійсного запису `acceptedAt`, роль знімається. Відсутній запис у реєстрі означає відсутність згоди. Видаляється лише роль Статика окремим DELETE; інші ролі зберігаються.

Законна видача ботом захищена порядком операцій: підтвердження Discord-коду → транзакційне збереження згоди → видача ролі. Перед зняттям повторно читаються згода й конфігурація. Помилка БД не означає, що правил не прийнято.

Повторна видача під час перевірки не пропускається; помилки мають три спроби. Є звірка після підключення/відновлення Gateway і щогодини, яка читає власників ролі в Discord, а не тільки людей із записом про вступ. Бани й блокування продовжують діяти.

Подія зміни учасника не містить автора зміни; журнал аудиту для цієї перевірки не потрібний. Попередня згода лишається дійсною після редакції правил.

## Межі перевірки та запуск

Реальні Discord-ролі, ваша БД і всі авторизовані сторінки з production-даними тут не перевірялися. Локальний production HTTP preview не став доступним; браузерні перевірки виконано на локальних макетах і згенерованому production HTML/CSS. Збірка використовувала наявні залежності середовища (Next.js 16.3.5); package/lock архіву зберігають заявлений Next.js 16.3.3. Чисте встановлення за lock-файлом та Docker-збірка тут не виконувалися.

Для бота потрібні увімкнений **Server Members Intent**, право **Manage Roles** та роль бота вище ролі Статика. У контейнері бота має бути увімкнений Gateway, задані Discord token/guild ID, адреса dashboard та той самий `INTERNAL_API_TOKEN`, що й у панелі. Роль учасника Статика має бути налаштована.

Після розгортання перевірити:

1. Учаснику без прийнятих правил вручну видати роль Статика разом з іншою тестовою роллю. Знімається лише Статик; у журналі є `role.enforced` із `rules_not_accepted`.
2. Прийняти правила через запрошення та команду в DM. Роль лишається після події Gateway.
3. Учаснику з чинною згодою повторно вручну видати роль. Вона лишається, якщо немає бану/блокування.
4. Швидко повторити несанкціоновану видачу. Черга повторно перевіряє та знімає її.
5. Якщо бот був вимкнений, видати роль без згоди та запустити його. Стартова звірка виявляє порушення.
6. На ПК й телефоні відкрити склад Статика, правила, форму порушення, довге меню й редактор; перевірити на реальних даних.

Зміни підготовлено в архіві вихідного коду; сервер автоматично не оновлювався.
