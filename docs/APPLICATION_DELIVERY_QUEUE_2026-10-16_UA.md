# Dashboard 3.12.0 — стійка доставка заявок у Discord

Повний реліз після 3.11.1. Сумісний із Site 4.2.1; перевстановлювати сайт для цього кроку не потрібно. Архів містить попередні виправлення PostgreSQL, CMS, приватного API та синхронізації сайту. На робочому VPS змін не виконано.

## Результат

Заявка й задача її доставки тепер записуються в одній транзакції PostgreSQL. Квитанція сайту й далі повертається після збереження заявки, без очікування Discord. Next.js `after` запускає швидку спробу доставки, а cron відновлює незавершені задачі незалежно від пам’яті процесу.

Старий одноразовий виклик `notifyDiscordNewApplication` видалено. Для нових заявок залишається один шлях надсилання через чергу та чинний механізм квитанцій Discord-публікацій.

| Ситуація | Поведінка |
|---|---|
| Перезапуск після запису заявки до виконання after | Задачу знаходить cron |
| Два працівники обробляють одну заявку | PostgreSQL lease допускає одного видавця |
| Відповідь Discord втрачена | Спочатку звірка збереженого nonce; новий CREATE не надсилається навмання |
| Discord створив повідомлення, але посилання не записалося | Збережений ID або nonce дозволяє завершити зв’язування без нового повідомлення |
| 429 або явне відхилення | Збережена затримка повтору; повтору POST усередині цієї спроби немає |
| Бот або канал не налаштовані | Задача залишається в стані перевірки налаштувань |
| Офіцер змінив рішення під час надсилання | Повідомлення отримує актуальний стан із БД; повторна зміна залишає задачу для наступної перевірки |
| Власник видаляє заявку під час доставки | Видалення використовує той самий lease та не обходить незавершену публікацію |
| Старі заявки без задачі доставки | Автоматичне повторне надсилання історичних повідомлень не запускається |

## Стан доставки в дашборді

У картці заявки офіцер бачить стан доставки та посилання на підтверджене повідомлення. Панель оновлює стан окремими GET-запитами приблизно раз на 30 секунд; сторінка й список не перезавантажуються. Читання не запускає доставку.

Для відкладеної задачі є «Повторити доставку». Для неоднозначного результату — «Звірити з Discord» та поле посилання на вже створене повідомлення. POST не повторюється клієнтом автоматично; подвійний клік заблокований. Помилки не стирають введене посилання.

Звірка перевіряє сервер, канал, автора-бота, час створення та nonce або унікальне посилання цієї доставки. Приймаються повні HTTPS-посилання офіційних доменів Discord. Чужий канал або повідомлення не можуть підмінити квитанцію заявки. API потребує прав керування заявками; POST перевіряє Origin, частоту викликів і фактичний розмір тіла до 2048 байтів.

Контакти кандидата, payload повідомлення й nonce залишаються на сервері. Публічний список заявок і приватна квитанція сайту зберігають попередній формат.

## Протокол і межі

Задачі зберігаються в `guildApplicationDeliveries`; квитанції — в чинній `discordPublications`. Використовується наявний індекс `dueAtMs`. CREATE відправляє збережений nonce, `enforce_nonce: true` і `retry: never`; налаштування каналу після підтвердження створення не спричиняє нового повідомлення під час завершення тієї самої задачі.

Стани задачі: pending, processing, retry, blocked, uncertain, delivered, cancelled. Плановий обробник вибирає максимум три готові задачі за виклик, застосовує часовий бюджет і обмежені дедлайни мережевих запитів. Перший звичайний повтор відкладається приблизно на хвилину; наступні — до години. Для неоднозначного результату або налаштувань перевірка відкладається щонайменше на п’ять хвилин. Cron викликає обробник раз на хвилину.

Це відновлення обробки, а не безумовна гарантія миттєвої доставки або exactly-once зовнішнього API. Якщо історія Discord недоступна, nonce зник або повідомлення не знайдено в обмеженому вікні історії, задача залишається для звірки. Відсутність повідомлення в доступній історії не доводить, що Discord його не створив. Сліпого нового CREATE в такому стані немає.

Видалення заявки з незавершеною неоднозначною публікацією повертає 409 і пропонує звірити доставку. Після успішного видалення прибираються запис кандидата й payload завершеної квитанції, а задача позначається скасованою.

Існуючі заявки не отримують автоматичного backfill: старі сповіщення могли вже потрапити в Discord без збереженого посилання. Такі записи позначаються як старі без запланованого повтору.

Використано справжні функції PostgreSQL document adapter, створення заявки, lease, квитанції публікації та Discord REST. PostgreSQL працює через ізольований WASM-рушій; HTTP-відповіді Discord контрольовані. Перевірки перезапуску повторно завантажують працівника зі збереженими записами БД; це не аварійне вимкнення живого VPS. Браузер перевіряє панель доставки з реальним API й цим самим сховищем. Парний тест використовує незмінений серверний споживач Site 4.2.1.

Docker build, nginx -t, фактичне розгортання, робоча PostgreSQL VPS і жива доставка Discord у цьому сеансі не перевірялися. Жодних живих повідомлень або заявок не створено.

## Встановлення на VPS

Нових секретів і відкритих портів немає. Потрібні чинні PostgreSQL, налаштування бота й каналу заявок та `INTERNAL_API_TOKEN` для cron. Саме контейнер cron треба створити заново після оновлення файлів: довготривалий shell-процес не зобов’язаний перечитати змінений розклад.

```bash
cd /srv/mistblossom
make backup
unzip -t /tmp/lihvodruida-dashboard-v3.12.0-durable-applications.zip
unzip -o /tmp/lihvodruida-dashboard-v3.12.0-durable-applications.zip -d /srv
cd /srv/mistblossom
docker compose -p mistblossom config --quiet
make rebuild-dashboard
docker compose -p mistblossom up -d --no-deps --no-build --wait --wait-timeout 90 dashboard
docker compose -p mistblossom up -d --no-deps --no-build --pull never --force-recreate cron
make internal-check
```

`make internal-check` містить захищений GET нового cron endpoint і не відправляє заявки. Новий маршрут: `/api/dashboard/discord/applications/automation`; тільки його авторизований POST виконує планову чергу.

Після встановлення оновити вкладку дашборда для нового JavaScript. Перевірити картку погодженої тестової заявки та стан автоматизації. Site 4.2.1 продовжує працювати без перевстановлення; якщо його попереднє оновлення ще не встановлено, скористатися чинним пакетом 4.2.1 і попередніми інструкціями приватного bridge.

Помилка доступу CurseForge HTTP 403 і правила старого Cloudflare Worker залишаються окремими налаштуваннями, описаними в попередніх звітах. Цей реліз не змінює права стороннього CurseForge API.
