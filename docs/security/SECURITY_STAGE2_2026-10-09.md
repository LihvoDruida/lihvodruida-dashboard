# Етап 2 — посилення безпеки панелі та Discord-бота (3.8.66)

Дата: 2026-10-09. База: архів `lihvodruida-dashboard-security-hardening-v3.8.65.zip`.

## Модель загроз і зміни

| Ризик | Реалізоване зменшення ризику |
| --- | --- |
| Повторна доставка signed Discord interaction між різними ботами або після перезапуску | У `POST /api/discord/interactions` після автентифікації внутрішнього сервісу, перевірки Ed25519 та звірки interaction ID виконується атомарний `claimVerifiedDiscordInteraction`. Ідентифікатор зберігається у спільній базі. Повтор не запускає бізнес-дію. Коли база недоступна — `503`, а не небезпечний пропуск перевірки. Локальний replay guard бота залишається додатковим першим бар'єром. |
| Повторне використання скопійованого cookie після logout | Токен сесії отримав випадковий `jti`. Logout записує SHA-256 від підписаного токена у спільний реєстр відкликань, *до* повідомлення про успішний вихід. Кожен production `getStoredSession` перевіряє цей реєстр; помилка БД означає відмову в доступі. |
| Обхід обмеження спроб отримання коду Статика через перезапуск процесу або різні репліки | Квоти зберігаються транзакційно: 16 запитів на 15 хв для пари «запрошення + довірена IP» та 300 запитів на 15 хв для одного запрошення загалом. Сирі IP в реєстрі не зберігаються. При перевищенні — HTTP 429 із `Retry-After: 900`. |
| Підроблення IP у клієнтських заголовках | `static/accept` і `static/status` використовують чинну централізовану `getClientIp`, що враховує лише підтверджений довірений проксі в production. |
| Необмежене зростання короткоживучих записів | Внутрішній `/api/dashboard/logs/maintenance`, який уже викликається cron кожні 30 хв, очищує прострочені replay-claims, відкликані сесії і квоти запрошень. Результати наведено в `securityRetention`. |

## Межі та свідомі рішення

- Запрошення Статика залишилися **спільними на 24 години**: механіка видачі персонального коду через DM і перевірка реального членства в Discord не змінювалися.
- Ролі, банліст, три порушення і права РЛ не змінювалися. Додаткових дозволів бот не отримує.
- Реєстр replay-claims гарантує **at-most-once виконання бізнес-дії**, а не повторне повернення минулого результату. Якщо панель закомітила дію, але з'єднання перервалося, транспортний повтор отримає «вже оброблено». Це навмисний компроміс проти дублювання змін; для гарантованого повторного повернення результату потрібна окрема durable outbox архітектура.
- Перевірка відкликання сесії передбачає один додатковий запит до спільного сховища для кожної авторизованої серверної операції у production. При збої БД авторизація тимчасово недоступна (fail-closed). Контролюйте latency та кількість DB connections.
- Запис про відкликання зберігається до 30 днів, тобто покриває максимальний дозволений час життя підписаної сесії навіть після зміни `SESSION_MAX_AGE_SECONDS`.
- Квота по IP може вплинути на відвідувачів за спільним NAT; її доцільно перевірити з реальними учасниками гільдії та скоригувати окремим релізом, якщо є хибні 429.
- Нові колекції використовують існуючу таблицю документів PostgreSQL або сумісний Firestore API; схема таблиці не змінюється.

## Результати перевірок

- 13 із 13 незалежних сценаріїв (включно з рівнем HTTP, конкурентними запитами, відмовою БД, серверним logout та очищенням квот).
- 34 із 34 тестів бота після коректного підключення локального пакета `shared`.
- Перевірки існуючих маршрутів Статика: 20/20, дисципліна: 12/12, права: 9/9, auth lifecycle: 13.
- Статичні перевірки імпортів, дій, форм, безпеки API та платформи пройшли.
- Повний TypeScript typecheck і Next.js production build **не підтверджені**: `npm ci --offline` не знайшов `zod-validation-error`, онлайн `npm ci` завершився внутрішньою помилкою npm. Виконайте `make up` на VPS, перш ніж вважати реліз розгорнутим.

## Впровадження та операційний чекліст

1. Застосувати Git-патч від базового архіву 3.8.65 або повний реліз; перевірити `git diff` перед комітом.
2. Виконати `make up` на VPS, дочекатися `typecheck`, `build:ci` та healthy всіх контейнерів.
3. Перевірити вхід Discord, вихід із наступною спробою повторно використати *старий* cookie (має відмовити), а також повторний вхід (має працювати).
4. Прийняти правила Статика через активне 24-годинне посилання та DM-код, переконатися, що лише реальний Discord-учасник отримав роль. Перевірити `429` після контрольованого ліміту в тестовому середовищі.
5. Перевірити повторну signed взаємодію на тестовому Discord-сервері: бізнес-операція виконується лише раз.
6. Через 30 хвилин перевірити `securityRetention` у логах результатів maintenance і стан PostgreSQL.
7. Контролювати `503` авторизації та `discord.interaction.dedupe_unavailable` у випадках збою БД; встановити сповіщення для таких подій.

**Не перевірено**: реальні Discord API інтеграції, навантаження з декількома production-репліками, DB failover, Cloudflare edge, обхід nginx та зовнішній пентест. Відсутність цих перевірок не варто трактувати як доведену захищеність усіх компонентів.
