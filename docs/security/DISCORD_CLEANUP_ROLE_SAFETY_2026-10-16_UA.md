# Дашборд 3.13.3 — безпечний відбір для очищення Discord

Правило: після заданого в налаштуваннях строку очищення допускає лише учасників без ролей або лише з однією вибраною роллю. Неявна роль @everyone не рахується. Вибрана роль разом із будь-якою іншою роллю завжди виключає учасника з кандидатів, доки додаткова роль присутня. Порядок, назва та права додаткової ролі не мають значення. Боти й власник захищені.

| Фактичні ролі | Результат |
| --- | --- |
| Тільки «Мурлок», якщо це вибрана роль | Кандидат після заданого строку |
| Немає ролей, крім @everyone | Кандидат після заданого строку |
| «Мурлок» + «Козак» | Пропуск |
| «Мурлок» + одна або більше інших ролей | Пропуск |
| Лише інша роль | Пропуск |
| Неповні, невідомі або некоректні дані ролей | Виключення заблоковане |

## Додатковий захист у 3.13.3

Кік потребує двох послідовних незалежних читань того самого учасника й вступу. Обидва читання мають показати однаковий допустимий набір ролей: лише задана роль або жодної, без @everyone. Навіть зміна між двома допустимими станами скасовує поточну спробу; наступна потребує нової однакової пари підтверджень. Некоректні, дубльовані або розріджені масиви ролей та некоректний ID заданої ролі не дають дозволу.

Свіжість підтвердження вимірюється монотонним годинником, на який не впливає переведення системного часу. Додано синхронний контроль безпосередньо перед HTTP-відправленням: якщо транзакція або процес затримались і підтвердження старше секунди, DELETE не відправляється. Підготовлена, але гарантовано не відправлена спроба переходить у retry, очищує inFlight та не створює хибний результат «виключено» чи «невідомо». Журнал містить verificationCount=2 і policyVersion=exact-role-set-v3.

Перевірка ролей та видалення залишаються окремими запитами до Discord. Цей захист не є гарантією атомарності при одночасній зміні ролей іншим ботом або адміністратором; абсолютні 100% у такому проміжку не обіцяються.

## Знайдені прогалини та зміни

У попередній версії сам відбір за кількістю ролей уже був суворим. Однак після останнього читання учасника запит DELETE міг чекати в REST-черзі, а перевірка перед відправленням перевіряла налаштування і lease, не перечитуючи ролі. Відтворено на попередньому worker: додаткова роль, отримана під час очікування, не зупиняла кік. Той самий регресійний тест проходить на виправленому worker без відправлення DELETE. Це підтверджена прогалина коду, але без журналу аудиту вона не доводить причину конкретних уже виконаних кіків.

Для очищення додано окреме суворе читання учасника без кешування, фільтрації або обрізання списку ролей. Відсутня roles, некоректний ID ролі, невідповідність ID учасника чи некоректне значення bot блокують дію, замість перетворення відповіді на «без ролей».

Після початкового очікування REST-черги worker повторно читає членство і застосовує повне правило. Додаткова роль, повторний вступ або зміна на бота скасовують дію без запису відправленого кіку. Під час читання не утримуються REST-дозволи: перевірено concurrency=1 та спільний bucket для GET/DELETE. Після остаточного отримання дозволів транзакція знову перевіряє призупинення, revision, token, lease та час перевірки членства. Перевірка, старша за одну секунду, не допускає відправлення.

Журнал нових спроб зберігає verifiedRoleIds, rolesVerifiedAt і policyVersion=exact-role-set-v3. Це відображає дані, на підставі яких дозволено дію; старі записи не отримують вигаданих історичних ролей. Таймаути та неоднозначні відповіді DELETE як і раніше не повторюються автоматично.

Між останнім читанням Discord і DELETE залишається короткий мережевий проміжок; локальні перевірки не роблять ці два запити однією атомарною операцією.

## Перевірки

- check:discord-member-cleanup: 119 поведінкових перевірок та 11 додаткових сценаріїв на PostgreSQL-движку PGlite з реальними document adapter, worker, strict reader і REST client. Усі Discord-запити перехоплені локальним транспортом; живі учасники не змінювались.
- check:discord-rest: 17 сценаріїв, включно з вкладеним читанням за concurrency=1 та спільного GET/DELETE bucket.
- npm run typecheck, npm run lint, check:imports, inspect:ci: успішно.
- check:cleanup-view: 17/17.
- npm run build: успішно; check:standalone: 7/7, включно зі стартом запакованого сервера та healthy liveness.
- Нові перевірки відтворюють затримку commit, застаріле підтвердження, переведення годинника назад та зміну між двома допустимими наборами ролей. У всіх цих випадках DELETE не надсилається.
- Попередній worker перевірено тим самим регресійним тестом: тест падає саме на додатковій ролі, отриманій під час очікування; виправлений worker проходить.

## Встановлення й перевірка інциденту

1. У дашборді /dashboard/discord/cleanup натиснути «Призупинити». Код у цьому архіві самостійно не змінював стан вашого сервера.
2. Оновити файли саме проєкту дашборду зі збереженням наявних .env та даних PostgreSQL. У корені, де є Makefile, виконати `make rebuild-dashboard`.
3. Перевірити версію дашборду 3.13.3, оновити список кандидатів під час призупинення та переконатися, що учасники з вибраною і будь-якою додатковою роллю відсутні. Сканування не вмикає автоматичні кіки.
4. Для встановлення причини минулих кіків потрібен приклад запису з Discord «Налаштування сервера → Журнал аудиту»: виконавець, причина, час і ID учасника. Автоочищення записує причину `Guild cleanup ...`; інший наявний шлях при самостійній відмові від правил записує `Rules declined by ...`. Не надсилайте токени або .env.

Змінено лише дашборд. Жодних живих кіків, розсилок, змін ролей або деплою на VPS під час цієї перевірки не виконувалось.
