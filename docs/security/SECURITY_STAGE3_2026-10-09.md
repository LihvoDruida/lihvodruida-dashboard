# Етап 3: Відновлювана доставка Discord interaction-відповідей

**Версія панелі:** 3.8.67 · **База:** 3.8.66 · **Область:** Next.js + Discord-бот + спільне документне сховище (PostgreSQL на VPS).

## Реалізовано

1. **Атомарний запис interaction ID** перед виконанням бізнес-логіки. Запис одночасно містить зашифрований AES-256-GCM токен короткострокового Discord webhook, ідентифікатор та час дії. Токен не записується відкритим текстом у БД і не з'являється в логах.
2. **Збереження відповіді до HTTP-результату:** Next.js фіксує готовий callback у спільному сховищі *до* того, як повідомляє боту про результат. Повторне підписане звернення повертає той самий callback замість повторного виконання операції. Поки операція виконується, повторний запит отримує HTTP 202.
3. **Відновлювана доставка:** бот кожні 5 секунд перевіряє захищений `/api/internal/discord/interaction-deliveries`. Worker отримує обмежену кількість результатів із транзакційною 30-секундною орендою (lease), PATCH-ить Discord `@original` і фіксує підтвердження в БД.
4. **Безпечні повтори:** мережеві збої, Discord 429 і 5xx призводять до відкладеного повтору з exponential backoff (до 8 спроб). Discord 400/401/403/404 завершують доставку без безглуздих повторів. Через 14 хвилин токен вважається непридатним.
5. **Очищення:** maintenance видаляє записи після 24 годин і очищує зашифровані токени для прострочених доставок. Після успішної доставки tokenCipher видаляється одразу.
6. **Захист API:** обидва методи нового ендпоінта вимагають внутрішній Bearer та `x-mistblossom-source: bot`; запити не кешуються, результат доставки підтверджується тільки відповідним lease UUID. Бот не дозволяє `allowed_mentions` під час PATCH.

## Гарантії та обмеження

- Це **durable outbox для результатів уже прийнятих і виконаних дій**, а не повна транзакційна exactly-once обробка Discord. Бот досі відправляє миттєвий ACK і асинхронно передає запит панелі. Якщо процес бота зникне між ACK і записом дії в панелі, запит може загубитися — для усунення потрібен окремий етап із синхронним durable ingress до ACK.
- Якщо бізнес-логіка встигла змінити дані, але процес панелі впав **до збереження callback**, interaction лишається в `processing` і **не запускається повторно**, щоб не дублювати модерацію/голоси. Відповідь не відновиться автоматично, необхідна діагностика за interaction ID.
- PATCH `/messages/@original` ідентичним payload є **ідемпотентною доставкою відображення**: якщо Discord прийняв PATCH, а ACK у БД не записався, інший worker може виконати PATCH ще раз до того самого original message (бізнес-операція не повторюється).
- Зміна `SESSION_SECRET` робить невідправлені токени неможливими для розшифрування. Обертайте секрет з урахуванням вікна 14 хвилин. Ключ походить із SESSION_SECRET через SHA-256 з окремим domain separator.
- Плановане сканування до 150 записів у кожному стані оптимізоване для малого/середнього Discord-сервера. Для значно більших навантажень потрібні окремі PostgreSQL outbox-таблиця й SQL `SKIP LOCKED`/індекси черги.

## Порядок деплою

1. Створити резервну копію PostgreSQL; `SESSION_SECRET` залишити незмінним.
2. Оновити одночасно образи **dashboard і bot**: старий бот не читає outbox, тому після оновлення лише панелі користувач бачитиме вічний deferred ACK.
3. Запустити `make up`, дочекатися healthcheck усіх сервісів.
4. Натиснути тестову кнопку Discord; перевірити, що відкладене повідомлення заповнилося й не дублюється. Перезапустити **bot** після завершення обробки панеллю, але до спроби доставки; worker має відновити відповідь.
5. На помилках Discord спостерігати події `Discord outbox delivery failed`, `Discord outbox poll deferred`, `discord.interaction.outbox_write_failed`; **не копіювати webhook-токени в логи**.
6. Не робити `git push` чи автоматичний деплой без підтвердженого production typecheck/build — тестове середовище не змогло встановити npm залежності.

## Перевірки

- Незалежні сценарії з транзакційною фальш-базою: атомарність, шифрування, повтори, оренда, відновлення, завершення, очищення, автентифікація ендпоінта.
- Незалежні HTTP-тести worker Discord з контрольованими відповідями `200`, `429`, `404`, `503`.
- Наявні тести бота та перевірки API, форм, маршрутів і платформи.
